# 软件设计哲学

以《软件设计的哲学》的复杂性、信息隐藏和深模块视角判断设计，不把原则变成代码形状或组件清单。

## 共同判断

- 从真实修改或调用任务判断**变更放大、认知负荷和未知依赖**，按任务频率与失败影响权衡。行数、层数、类数和依赖环只是线索。
- **深模块**用较低的接口负担提供较强能力；**信息泄露**是同一决定需要多处独立解释并保持一致。薄适配器、值类型和同一 schema 生成的副本不自动有错。
- 优先当前简单实现；只为有证据且日后昂贵难逆的变化预留窄接缝，不为推测需求建框架。
- 封装不能隐藏调用者必须决定的正确性、权限、持久化或生命周期语义。需要逃逸时先查核心接口是否缺少能力。

## 执行边界

用户明确要求优先于默认流程。设计咨询交付方案与建议，不自行转为实施；审计覆盖与目标相关的性能、兼容和部署取舍。实施请求继续完成已授权改动及相称验证，已提供的目标不重复询问。

结论交代证据、结构机制、决定及代价、验证方式；区分事实、推演与待验证假设，保留影响决定的证据缺口。不强制矩阵、计划或额外文档。

先从已有目标、动机和材料推导约束，不把能自行完成的推理交给用户。仍有不确定性时，快速给出少数关键场景下的条件结论，不穷举；只对影响决定、无法可靠推导的缺失信息请求补充或确认。

验证针对改变的行为与边界，不默认用 TDD 生成架构，也不为设计评估一律新增测试。必要检查完成后，只有新改动、失败或具体未决疑点才支持扩大或重复验证。

长任务交接保留决定、证据位置、代码基线与未决项。目标改变时保留有效工作，重评受影响契约；迟到结果按需求和代码版本判断适用性。调整要求或停止等待不证明已启动的工具及副作用已撤销。
