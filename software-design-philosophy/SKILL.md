# 软件设计哲学

用真实任务检验设计：它让调用者和维护者少知道了什么、把哪些变化集中到了哪里，又引入了哪些状态、协调和失败成本。以《软件设计的哲学》的复杂性、信息隐藏和深模块视角为主，书中原则用于判断，不作为代码形状或组件清单。

## 判断尺度

- 复杂性体现为**变更放大、认知负荷和未知依赖**。按任务频率与失败影响衡量整体成本；行数、层数、类数、依赖环只是调查线索。
- **深模块**以较低的接口学习与调用成本提供较强能力；**信息泄露**是同一设计决定要求多处独立解释并保持一致。薄适配器、值类型或由同一 schema 生成的副本不因此构成问题。
- 优先当前简洁、低复杂度的实现。只有已有证据且日后昂贵难逆的变化才值得预留窄接缝，不为推测需求预建通用框架。
- 封装不能隐藏调用者必须决定的正确性、权限、持久化或生命周期语义。先检查核心接口是否缺少能力，再考虑显式高级入口。

## 从任务进入

已有明确问题时直接处理；根因不清时，从实际修改或调用工作流追踪知识与责任。事实、推演和待验证假设分别表达，不要求用户重复已提供的目标或约束。

| 当前要解决的问题 | 按需读取 |
|---|---|
| 审计仓库或子系统、区分架构问题与局部缺陷 | [架构审计](references/audit-software-architecture.md)；其中含直接发现判据，无需先读所有方法 |
| 不知道为何难以理解或修改、规则多处解释、决定职责如何组合或拆分 | [模块与知识边界](references/design-module-boundaries.md) |
| 设计 API、减少调用者胶水、明确契约、默认路径与插件扩展 | [深模块与接口](references/design-deep-modules.md) |
| 正常接口已定，只需整理异常与恢复责任 | [错误处理边界](references/reduce-exception-surface.md) |
| 比较重要结构候选，或在期限和兼容约束下演化 | [方案比较与演化](references/evolve-design-strategically.md) |
| 性能证据影响边界、批量能力、数据布局或高级接口的取舍 | [性能约束下的设计](references/design-measured-critical-paths.md) |
| 设计跨进程、异步任务、复制状态或故障恢复的契约 | [系统边界与失败契约](references/design-system-boundaries.md) |

按任务联合相关内容，不设主辅配额，也不逐份加载。审计 reference 的发现判据与专题 reference 的设计细节用途不同；不要把读取、执行和输出视为同一义务。

## 执行与交付

当前用户明确要求优先于本 skill 的默认工作流。审计请求交付发现和建议；实施请求继续完成已授权改动及相称验证。背景中的性能、兼容性或部署偏好只约束判断，不自动增加专项任务。

长任务交接保留当前决定、证据位置、代码基线与未决项。用户中途调整目标时，保留仍有效的工作，重评受影响的契约和验证；尚未返回的任务结果须按其需求或代码版本判断是否仍适用。调整要求或停止等待，不证明已启动的工具和副作用已经撤销。

结论说明**证据 → 结构机制 → 决定及代价 → 验证方式**，保留会影响决定的证据缺口。使用用户需要的篇幅和格式，不强制方法清单、多张矩阵、计划或额外文档。

验证针对改变的行为与边界：可用调用方演练、变更推演、已有契约测试、静态依赖规则或必要基准。这里不默认推荐 TDD 来生成架构，也不要求为了设计评估增加测试；先明确目标抽象，再选择能检验它的最小充分验证。完成必要检查后，只有新改动、失败或未解决的具体疑点才支持扩大或重复验证。
