# 软件设计哲学

把软件设计问题转化为可观察的复杂性证据，再选择最窄、最合适的方法处理。不要把本技能当作原则清单，也不要在一次任务中机械套用全部方法。

主书 John Ousterhout 的《软件设计的哲学（第二版）》决定评价尺度和方法边界；Robert C. Martin 的《架构整洁之道》补充案例、依赖判据和实现细则。两者发生张力时，遵循本文件的裁决和 [来源裁决](references/source-decisions.md)，主书优先。

## 执行流程

### 1. 先判断是否应介入设计

先确认用户面对的是需要理解、修改或选择结构的设计问题。

- 生产事故仍在扩大时，先止血、隔离和恢复；稳定后再讨论长期结构。
- 纯语法、框架参数、单次机械修改或无行为收益的风格偏好，直接完成任务，不展开本技能。
- 只有“感觉系统很乱”而没有明确根因时，先从真实任务采样，不凭代码行数、层数或类数量下结论。
- 用户已经给出明确设计问题时，直接进入对应方法，不强制先做全系统诊断。

### 2. 收集最小充分证据

优先检查真实代码、接口、变更记录、调用方胶水、错误路径、运行测量或用户给出的实际用例。把事实、假设和待验证项分开。不要仅凭抽象原则要求重写。

至少明确：

1. 当前任务与期望结果；
2. 谁在使用或修改该设计；
3. 已观察到的成本、失败或约束；
4. 哪些决定已确定，哪些仍待选择；
5. 改动范围以及必须保留的行为。

### 3. 选择一个主方法

先选一个主方法，并完整读取对应 reference 后再执行。只有当主方法明确依赖另一个判据时，才额外读取一到两个辅助 reference；不要一次加载全部文件。

| 首要问题或证据信号 | 主 reference | 第一动作 |
|---|---|---|
| 局部修改牵动多处、背景知识过多、经常遗漏隐蔽依赖，但根因尚不清楚 | [复杂性加权诊断](references/diagnose-software-complexity.md) | 重放近期真实任务，区分变更放大、认知负荷与未知依赖 |
| 给现有系统加功能或修缺陷，需要在期限内改善结构而不是留下永久补丁 | [战略式演化设计](references/evolve-design-strategically.md) | 写出目标抽象、最小结构切口和分期退出条件 |
| 要用少量接口覆盖多数真实需求，调用方胶水或配置膨胀，并要治理长尾能力 | [深模块设计闭环](references/design-deep-modules.md) | 建立加权用例、知识、覆盖和逃逸表 |
| 同一格式、规则、状态机或内部表示在多个模块重复解释 | [信息泄露审计](references/audit-information-leakage.md) | 以设计知识为单位画出依赖图并指定唯一权威 |
| 纠结两个类、函数、服务或组件该合并还是拆分 | [组合或拆分](references/decide-combine-or-split.md) | 比较共享知识、变化轴、共同使用和边界成本 |
| API 异常过多，各层反复捕获、转换、重试或包装 | [缩减异常处理面](references/reduce-exception-surface.md) | 依次判断能否定义消除、就地恢复、边界聚合或明确失败 |
| 第一个重要方案看似可行，却缺少真正不同的候选和统一比较 | [设计两次](references/design-it-twice.md) | 画出至少两个结构不同的候选并用同一组真实用例评分 |
| 新接口难以说清行为、约束、副作用、不变量或失败语义 | [注释优先的抽象设计](references/design-abstractions-comment-first.md) | 在实现前写面向调用者的简短完整契约 |
| 核心概念和契约已经选定，但读者仍猜错名称、控制流或代码入口 | [读者易理解性闭环](references/make-code-obvious-to-readers.md) | 记录首次阅读的误解路径，再减少必须知道的信息 |
| 有明确延迟、吞吐、CPU、内存或 I/O 目标及运行证据，准备引入缓存、并行或快速路径 | [证据驱动的关键路径设计](references/design-measured-critical-paths.md) | 固定代表性负载，建立基线并定位少数热点；没有目标或运行证据时不选此方法 |
| 参数、配置和概念太多，尚不知道什么应成为系统中心；或上层以未经测量的性能理由要求穿透底层对象 | [围绕重要性设计](references/design-around-what-matters.md) | 找出少数杠杆点；遇到底层穿透时先用真实用例反查通用接口是否遗漏核心原语 |

术语含义不清或多个方法使用同一概念时，按需读取 [共享术语词典](references/glossary.md)。

### 4. 处理容易混淆的路由

按以下优先级裁决，不要因为关键词相同就同时展开多个方法：

1. **尚不知道哪里复杂**：先做复杂性诊断；已定位为某项共享知识散落时，直接做信息泄露审计。
2. **不知道什么最重要**：先围绕重要性设计；核心概念已经确定、只是不易被读者看见时，做读者易理解性闭环。
3. **边界在哪里尚未确定**：先裁决组合或拆分；边界已确定、需要设计有限接口及长尾出口时，做深模块设计。
4. **接口整体尚未形成**：做深模块设计；接口总体稳定、只剩错误和恢复责任时，做异常处理面设计。
5. **重要候选需要纸面比较**：做设计两次；性能候选的去留依赖实际收益时，必须转入关键路径测量。
6. **实现前无法表达契约**：做注释优先设计；契约已清楚但实现仍让读者误解时，做易理解性闭环。
7. **已有明确变更且受交付约束**：以战略式演化为主，按根因补充一个专门方法，而不是把诊断报告当交付物。
8. **以性能为由要求穿透底层，但没有目标、基线或剖析**：先用围绕重要性设计反查通用接口是否失当。只有确认接口没有遗漏核心原语，并取得真实热点证据后，才转入关键路径测量或设计受控逃逸。

### 5. 按任务组合，但保持单一主线

复杂任务可以形成短链，每一步都必须有进入条件：

- 新模块：重要性设计 → 设计两次 → 深模块 → 注释优先。
- 遗留系统变更：复杂性诊断 → 根因专门方法 → 战略式演化。
- API 重构：深模块 → 异常处理面；需要证明契约时再补注释优先。
- 边界重组：信息泄露审计 → 组合或拆分；只有确定新边界后才设计深接口。
- 性能改造：关键路径测量；只有测量证明结构问题时，才追加重要性或深模块方法。

箭头表示条件满足后的下一步，不表示每次必须执行完整链条。

## 全局裁决

这些规则覆盖各 reference 中可能产生歧义的辅助观点：

- 以真实任务造成的整体理解和修改成本评价设计，不把行数、层数、类数、组件指标或“策略/细节”标签当自动结论。
- 当前实现优先简洁、低代码量和低复杂度。只为已有证据且未来难以逆转的变化保留窄接缝或受控逃逸，不预建全部未来选项。
- 用例和参与者是发现知识与变化轴的证据，不自动等于模块、端口、服务或部署边界。
- 出现底层依赖时，先反查核心接口是否遗漏重要原语；只有调用者确实承担该决策且模块无法推断时，才显式暴露。
- 首版先保证主流程正确。性能穿透、缓存、并行和快速路径只在测量证明热点，或确有数量级收益且顺序不可反转时进入设计。
- 测试是按风险配置的行为安全网，不是架构生成器。先写目标抽象和行为契约，再决定测试预算；不要用私有分支全覆盖替代设计。
- 拒绝通过多个含状态基类或模板方法实现插件扩展；优先组合、接口、trait 或 C++ concept，并保持状态和调用顺序的唯一所有者。
- 设计深模块时，必须主动询问设计者是否需要独立测试/Agent 调试面。未获明确要求不得创建；获准后才设计与生产严格隔离、具有 schema、幂等、限权、审计和自动回收的 CLI/API。

需要追溯两书分歧、用户原始裁决或 Linux 文件系统补充模型时，完整读取 [来源裁决](references/source-decisions.md)。

## 输出约定

除非用户指定其他格式，交付应包含：

1. **问题与证据**：真实任务、观察事实、约束和仍待验证的假设；
2. **方法路由**：主方法、选择理由，以及为什么没有选择最相近的方法；
3. **分析产物**：使用所选 reference 要求的表、图、契约、矩阵或实验；
4. **设计决定**：具体边界、接口、责任、演化步骤或保留/撤销结论；
5. **边界与逃逸**：不能覆盖的情况、责任归属、风险和重新收编条件；
6. **验证方式**：调用方演练、变更演练、读者测试、基准或其他可复现证据。

给出可执行决定，不要只复述书中原则。若证据不足以裁决，明确缺口和最小验证动作，不用权威口吻补齐未知事实。

## 完成检查

- 是否从真实任务或测量出发，而不是从流行原则出发？
- 是否只选择了一个主方法，并按需读取了最少 references？
- 是否把事实、假设和偏好分开？
- 是否同时考虑调用者成本、实现成本和长期修改成本？
- 是否说明不能覆盖的情况及其受控处理方式？
- 是否尊重当前简单性、显式高风险决策和用户已裁决的边界？
- 若涉及深模块，是否主动询问调试面需求且未擅自创建？
- 是否提供了能够推翻或验证当前决定的证据？
