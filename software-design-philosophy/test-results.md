# software-design-philosophy 测试结果

测试日期：2026-07-29
被测版本：0.4.0

## 结论

本轮继续修复“蒸馏细则在广义架构审计中不可达”的真实失败：

- 架构审计会先判类别、再判严重度；高严重度相邻风险不再自动进入架构主表。
- performance-first 等背景只修正当前判断、约束候选和证据强度，不会自行增加性能优化交付。
- 用户明确要求性能设计或架构性能裁决时，性能方法仍会完整执行。
- 方法按证据联合，没有“唯一主方法”、固定诊断前置或数量上限。
- 面向仓库/子系统的广义架构审计在候选发现前逐一完整读取全部 11 个方法；不能用摘要或触发词替代。
- 每个方法都参与筛查并给出问题、候选、健康或不适用结论；只有证据命中的方法才执行深入产物。
- 完整加载不等于固定流程、十一条问题或十一份专项手册，用户目标仍决定交付范围。
- 强制检查不等于强制定罪：薄适配器、值类型、纯函数和内部辅助层可以合理地浅。
- 运行时材料不含用户仓库名、回归样本专名、精确迁移数据或预设审计答案。

当前 `test-prompts.json` 含 57 个回归用例：14 个应触发、7 个不应触发、36 个边界用例。该数字表示测试集规模，不伪装成全部已经由模型逐题执行的通过率。

## 0.1.0 真实失败

### 失败一：严重度替代了问题类别

架构报告把一个可立即局部修复的高危安全/配置问题直接列为最高优先级架构问题。问题不在于严重度判断过高，而在于报告没有证明边界、依赖、知识归属、接口或生命周期责任产生了系统性机制。

### 失败二：背景接管了用户目标

用户只要求在性能约束下审计架构，旧行为却自动展开 benchmark、热点、转换成本、缓存、SIMD 和 fast path 路线，形成性能优化手册。性能背景没有用于修正架构判断，反而擅自增加了交付目标。

### 失败三：单一主方法限制真实任务

旧入口要求选择一个主方法，再少量加载辅助方法。这会把真实任务强行压成一条固定流程，也让“读取性能方法”容易被误解为“必须输出完整性能专项”。

## 0.2.0 真实失败

### 失败四：细则只在候选已经被发现后才可达

用户要求广义架构审计时，旧入口只强制读取审计工作流。深模块等方法只有在 agent 已经先发现“接口覆盖与长尾”信号后才会加载；但 agent 正需要这些判据才能识别浅接口、调用者胶水、知识泄露和失控逃逸。结果是蒸馏内容虽然存在于 references，实际候选发现却可能完全绕过它，报告也没有义务显式说明模块深度检查结果。

## 0.3.0 真实失败

### 失败五：只提升了深模块，其余细则仍停留在摘要筛查

0.3.0 只要求完整读取深模块；复杂性、重要性、信息泄露、组合/拆分、异常面、候选比较、契约、读者验证、战略演化和关键路径仍要先由简化覆盖表命中，才读取完整 reference。它修掉了一个召回循环，却保留了另外十个，不能证明原书细则真正进入了 agent 的候选发现过程。

## 根因与通用修订

| 根因 | 当前修订 | 防过拟合方式 |
|---|---|---|
| 用户目标、背景、约束和证据混在一起 | 原样固定用户目标；背景只能修正、否决或约束，不自行扩题 | 不枚举有限的用户目标类型 |
| 没有架构发现准入 | 增加结构对象、系统性机制、结构性改进三门准入 | 门禁适用于任意领域，不含特定框架或仓库答案 |
| 先排严重度再贴架构标签 | 类别先于严重度；架构与相邻风险双轨排序 | 允许同一事实拆成两条独立因果链 |
| 方法被当成互斥路由 | 按证据联合方法，分别说明发现、设计、约束或验证职责 | 无主/辅、数量上限和固定前置 |
| 性能 reference 自动展开完整流程 | 完整流程由用户目标准入；作为背景时只约束当前候选 | 性能逃逸仍按目标、测量、契约和不变量裁决 |
| 静态形状被直接定罪 | 依赖图、跨层引用和目录形状只作线索；用真实变更或演练证明机制 | 证据不足时进入候选与最小验证动作 |
| 先发现候选、后加载发现判据 | 广义架构审计在候选前完整读取全部 11 个方法，再按证据选择深入产物 | 加载、筛查、深入和交付四层分离；不要求凑问题或套统一流程 |
| “模块”被误解成每个类/文件 | 按知识与责任边界取样高权重公共、跨模块、工作流和生命周期接口 | 明确排除仅因薄适配器、值类型、纯函数或方法数而定罪 |

## 隔离前向测试

独立 agent 只允许读取运行时 `SKILL.md` 和 references；明确禁止读取 `test-prompts.json`、本文件、Git 历史、旧报告和其他 agent 输出。测试场景使用匿名证据，运行时材料不含真实仓库专名和具体题解。

| 测试 | 自行构造的输入特征 | 结果 | 关键观察 |
|---|---|---|---|
| 架构类别泛化 | 一个局部最高危漏洞、一个有多次真实变更传播的知识归属问题、一个只有静态引用的候选 | 通过 | 分别进入相邻 P0、架构 A1、证据缺口；没有把严重度复制成架构等级 |
| 性能上下文边界 | 匿名原生/跨语言库；已证实的受控零拷贝入口；多表示；一次知识漏改；未测得的转换成本 | 通过 | 性能判据保护合理逃逸并约束架构建议；未输出热点、benchmark 建设或优化路线 |
| 任意目标与方法联合 | 边界判断、已测热点优化、受期限约束的知识收口、插件接口与长尾四种目标 | 初测部分失败，修订后通过 | 初测发现 5 处 `depends-on` 可能被解释为固定前置；改为证据复用或可选联合后复测通过 |
| 元数据触发 | 5 个架构/设计正例与 3 个库查询/机械实现负例 | 8/8 通过 | `description` 只描述适用问题和负例；未暴露内部方法、具体优化手段或执行步骤 |
| 架构/实现边界 | 匿名离线流通系统中的 9 项高低层决定、质量目标、技术选型和局部高危缺陷 | 9/9 通过 | 正确区分上游约束、质量责任分配、架构决定、实现细节与架构问题；技术层级和严重度均未替代边界判断 |
| 来源一致性 | 完整对照三份材料与当前定义 | 初测发现 2 项边界过窄，修订后通过 | 补全纵向设计链与横向系统关系；允许各阶段和组件内部存在架构；快速裁决覆盖系统级保证及低频高后果任务 |
| 未点名细则的广义架构审计 | 匿名公共 SDK；高频调用方顺序胶水、双重策略解释、薄适配器和受控插件入口 | 通过 | 主动给出模块深度结论；浅公共入口与知识泄露进入 A1，薄适配器和可重新汇入的逃逸列为健康设计，未扩张性能专项 |
| 浅对象对照分类 | 单方法翻译适配器、跨团队顺序式公共 API、隐藏生命周期且有受控批量入口的公共存储边界 | 通过 | 分别归为不适用、已确认架构问题、值得保留；没有按方法数或对象大小定罪 |
| 11 方法联合召回 | 匿名归档平台；规则多点解释、浅工作流、错误扩散、错误入口、长期旁路、单一难逆方案和已测跨进程成本 | 通过 | 11/11 个方法均进入覆盖；确认 3 个 A1、1 个 A2，并把候选比较与性能证据限制在架构交付内 |
| 全量加载范围守卫 | 匿名单进程批处理工具；大部分边界健康，只有远程同步扩大启动失败域 | 通过 | 只确认一个生命周期架构问题；其余方法给出健康、不适用或证据不足，没有虚构接口重构、服务拆分、性能计划或候选方案 |

性能上下文测试所构造的专有名词、类型名和修改数字均未出现在运行时材料中。类别测试也没有复用旧报告中的固定管理员、工作流或认证题面。

## 成对行为比较

另设匿名候选比较，同一请求只允许交付架构审计：

- 候选甲用最高风险替代架构类别，因 performance-first 自动输出性能治理路线，并限制一个主方法。
- 候选乙先验证结构因果链，单列相邻风险，用性能约束修正架构判断，并按证据联合方法。

独立 judge 以范围忠实、架构类别准确、真实约束利用、多方法协作和可验证性五项评分：候选甲 `0/10`，候选乙 `10/10`。judge 同时保留三项限制：

- 架构裁决确实依赖性能时，仍可做最小必要测量，但不扩张为完整优化项目；
- 一个局部风险若另有结构因果链，必须拆成相邻发现和架构发现，不能遗漏后者；
- 多方法联合仍受用户目标约束，不能从“只选一个”滑向“全部加载”。

本轮另让独立 judge 在同一次评估中比较已提交版与工作树版，只读取两版根文件、架构审计和深模块 reference。结论为工作树版 `better / clear`：旧版只有看见接口覆盖信号后才加载深模块，存在召回循环；新版通过覆盖合同、强制模块深度证据和四态结论消除了盲区。judge 提醒窄范围审计可能被清单拖累，因此最终把完整强制检查限定为面向仓库/子系统的广义架构审计；用户已明确指定的局部设计问题仍直接进入对应方法。

0.4.0 再与 0.3.0 做同 judge 成对比较，结论仍为 `better / clear`：0.3.0 只完整读取深模块，其余十个方法仍存在“摘要未命中便永不加载”的闭环；0.4.0 在候选前完整读取 11 个方法，并把加载、筛查、深入和交付分开。judge 确认新版没有规定固定先后，也允许健康、不适用和证据缺口；残余风险是全量阅读的上下文/时间成本，以及逐项覆盖可能增加报告长度。

## 历史结果的处理

0.1.0 曾记录 50/50 的触发与路由盲测，但其中包含“唯一主 reference”这一现已否决的评分前提，不能作为后续版本的有效通过证据。本轮保留失败史和测试隔离原则，不沿用旧通过率。
