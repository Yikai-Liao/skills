# 模块与知识边界

用于诊断难以理解或修改的根因，或裁决职责应集中、合并还是拆开。分析单位是一项设计知识和真实任务，不是文件大小。

## 从变化追到知识

选择具有代表性的修改、调用或故障恢复路径，标出必须一起理解和更新的位置。区分：

- **变更放大**：一个决定变了，多个位置必须同步改。
- **认知负荷**：完成局部任务前必须学习无关表示、状态或装配规则。
- **未知依赖**：维护者无法从入口、类型或契约发现会被影响的位置。

根因已清楚时无需重做全系统诊断。优先追踪高频任务与低频高后果任务，不用运行时请求热度替代开发变更权重。

反复误改时，区分必要知识不可达、契约表达不足、已知契约下的实现错误和验证遗漏。缺知识才补知识；不能用更多上下文或步骤替代根因修复。生成代码更快也不能抵消审查、返工、集成与迁移成本。

把“订单模块太乱”收窄为一个可改变的决定，如“什么状态允许取消”。追踪谁定义、解释、验证和转换它，包括代码不同但语义相同的副本。问一次规则变化为什么必须改每处。

**相似不等于共享**：法规金额与展示金额可能独立演化；生成代码可以共享唯一 schema。对不能封装进同一模块的跨组织协议，保留一个版本化契约与兼容责任，而不是强求单一物理实现。

## 决定知识所有者与边界

| 倾向 | 有价值的证据 | 需要计入的代价 |
|---|---|---|
| 集中/合并 | 共享规则或状态机，总需共同理解、修改；合并能删掉中间表示、配对调用和重复恢复 | 无关依赖、共同发布、权限扩大、形成万能模块 |
| 拆分 | 不同变化原因和所有者，能够独立理解；消费者只需一部分却被迫依赖全部 | 新接口、状态传递、导航、版本、序列化和部署协调 |
| 保留边界 | 翻译外部协议、隔离信任或故障、保护稳定契约，即使实现很薄 | 确认隔离收益实际存在，不仅是层名或图中的一条线 |

以拥有信息、能够维护不变量的一侧作为权威。接口表达调用者意图，让策略不必反复解释供应商或存储表示。若上层索取底层对象，先查公共接口是否遗漏事务、批量或一致性原语。

重要概念应能解释多个当前用例或让其他信息可推导。模块能可靠决定的选项放回内部；调用者独有且影响结果的选择留在契约。不要用“高层/低层”预先决定什么重要，也不按执行顺序、组织图或每个用例自动建模块。

本 skill 保留的个人取舍：**不采用多基类实现继承**。插件和可替换实现优先组合、接口、trait 或 concept；单继承只有在契约稳定、子类无需依赖父类内部状态及调用顺序时才考虑。状态与调用顺序应有明确所有者。

源码隔离与部署隔离分别判断。只有独立发布、容量、信任或故障收益足够时才引入进程/服务边界；低延迟、大中间数据或本地事务可能支持保持同进程。

## 验证边界是否有用

用原来的变更或调用路径演算候选：权威规则是否只改一处，必要适配是否留在边缘，无关调用者是否仍须理解内部知识。不要只比较类图。

对实际会再次泄露、且项目工具能表达的边界，用模块可见性、类型或静态依赖规则保护；不能机械表达的跨方契约保留就近说明。不是每次评估都需要新增架构测试。

让入口能指向权威实现、相关消费者和有效验证方法。类型、schema 或检查器负责可稳定表达的不变量；就近文档解释无法可靠推导的理由、兼容承诺与取舍，仓库指导指向这些权威，避免多份规则全文漂移。若调用者反复靠提示词补做事务、清理或顺序步骤，应重评接口责任，而不只是增加提醒。

若问题只剩入口难找或名称歧义，用一个读者任务检查它：只看入口和契约能否找到真实修改点、预测行为？先减少隐藏约定和跳转，再补名称、类型与说明，不强制安排额外读者或多轮盲审。
