# 模块与知识边界

## 追踪知识，而非文件形状

沿代表性修改、调用或恢复路径，找出必须一起理解、更新的规则及其解释者。优先高频或高后果任务，不用运行时请求热度代替开发变更权重；根因明确时不重做全系统诊断。

相似代码不等于共享知识：法规金额与展示金额可以独立演化；同一 schema 的生成物可以共享唯一权威。跨组织协议无法收进同一实现时，保留版本化契约与兼容责任。

反复误改要区分知识不可达、契约不足、实现错误与验证遗漏，不一律追加上下文或步骤。生成速度不能抵消审查、返工、集成和迁移成本。

## 选择边界

- **合并**：同一规则或状态机总需共同理解、修改，合并能消除中间表示或重复恢复；同时检查是否引入无关依赖、共同发布或权限扩大。
- **拆分**：责任有独立变化原因，拆后可以独立理解；计入新接口、状态传递、导航与协调成本，不按执行顺序、组织图或每个用例自动建模块。
- **保留**：薄边界确实翻译外部协议、隔离信任或故障、保护稳定契约，不因“浅”而强行增加职责。

权威放在拥有信息、能维护不变量的一侧。核心概念应支撑多个当前用例或让其他信息可推导；模块可可靠决定的选项收回内部，调用者独有的选择留在契约，不按“高层/低层”预判重要性。

个人取舍：**不采用多基类实现继承**。插件优先组合、接口、trait 或 concept；仅在契约稳定且子类不依赖父类内部状态及调用顺序时考虑单继承。

源码边界不自动成为服务边界；只有独立发布、容量、信任或故障收益足以支付通信和恢复成本时才拆进程。

## 检验实际收益

重放原任务，看权威规则是否收拢、必要适配是否留在边缘、无关调用者是否少学内部知识，而不只比较类图。

类型、schema、可见性或现有检查保护可表达的不变量；就近说明不可推导的理由与兼容承诺，仓库指导指向权威，不复制多套全文。不机械新增架构测试。

入口应能引向真实修改点和有效验证；先减少隐藏约定与跳转，再补名称和说明，不强制外部读者实验。若调用者仍靠提示词补做事务、清理或顺序步骤，应重评接口责任。
