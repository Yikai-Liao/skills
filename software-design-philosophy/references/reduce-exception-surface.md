## R — 原文

> 减少必须处理异常的位置的数量。
>
> — John Ousterhout，第 10 章

---

## I — 方法论骨架

异常也是接口：每增加一种异常，就增加调用者必须理解和测试的状态。
第一选择不是多写一个 `catch`，而是检查操作定义能否让边界情况成为正常结果。
无法消除时，由最了解机制且能可靠恢复的层屏蔽，例如有限重试或替换副本。
若多种失败最终都需要同一响应，让它们传播到一个共同边界统一处理。
若故障极少、无法恢复且继续运行会产生错误结果，明确中止可能比遍地防御更安全。
但只要调用者拥有模块没有的信息，或必须据故障保证正确性，错误就不能被隐藏。
好设计减少的是需要处理错误的位置和分支，不是减少诊断信息。
每种屏蔽都要有预算、幂等性、可观测性和失败升级路径。

## A1 — 书中的应用

### 案例 1：Tcl `unset` 通过定义消除异常

- **问题**：删除不存在的变量原本抛错，调用者为了“确保变量不存在”必须先检查。
- **方法论的使用**：把操作定义从“删除一个存在的变量”改为“确保变量不存在”。
- **结论**：变量原本不存在也可视为成功结果，不再是特殊状态。
- **结果**：消除了查询与删除之间的竞态和大量防御代码。

### 案例 2：TCP/NFS 屏蔽可恢复故障，Web 顶层聚合错误

- **问题**：丢包、服务器短暂不可达、参数和权限错误若逐层暴露，会让每个调用者重复处理。
- **方法论的使用**：TCP/NFS 在掌握恢复机制的底层重试；Web 服务器让请求错误传播到能统一生成响应的边界。
- **结论**：恢复应在最知情层完成，相同外部响应应在共同边界聚合。
- **结果**：高层逻辑不再被传输细节和重复响应代码淹没。

### 案例 3：过度屏蔽会丢失重要故障语义

- **问题**：学生网络模块试图隐藏所有异常，连无法恢复、会影响正确性的故障也吞掉。
- **方法论的使用**：作者检查调用者是否需要错误信息做出正确决定。
- **结论**：模块无法可靠恢复、调用者又关心结果时，必须显式暴露；“少异常”不能压过正确性。
- **结果**：该案例成为错误屏蔽的边界，而不是继续扩大屏蔽范围。

## A2 — 触发场景

### 用户会在什么情境下需要这个方法？

1. API 对空集合、重复删除、越界范围等情况抛出大量可避免异常。
2. 相同错误在控制器、服务、仓储层被反复捕获和重新包装。
3. 每个业务调用者都实现相同的重试、回退或错误响应。
4. 团队争论应返回空结果、错误值、异常还是中止进程。
5. 错误处理代码比正常路径更长，且难以判断谁真正能恢复。

### 语言信号

- “不存在到底算成功还是异常？”
- “这个错误应该在哪一层处理？”
- “能不能把这些异常都隐藏掉？”
- “每层都 catch 再 throw，有必要吗？”
- “重试应该放 SDK 还是业务层？”

### 与相邻方法 的区分

- 与 `design-deep-modules` 的区别：本方法 专注错误状态和恢复责任；深模块处理整个接口覆盖与逃逸设计。
- 与 `design-measured-critical-paths` 的区别：重试风暴或异常开销若已成为性能问题，需另用测量流程定位。
- 与 `diagnose-software-complexity` 的区别：这里已有明确错误面；诊断方法 用于尚不清楚复杂性来源时。

## E — 可执行步骤

1. **建立错误清单**
   - 对一个真实工作流列出错误状态、发生位置、当前处理者、最终用户可见结果和处理重复次数。
   - 区分无效输入、正常边界、短暂机制故障、资源耗尽、数据损坏和程序不变量破坏。
   - **完成标准**：每类错误有具体触发条件，不能只写“未知错误”。

2. **判断谁拥有恢复所需信息**
   - 记录模块能否自行判断正确动作，调用者是否掌握事务、持久化、安全或业务容忍度等额外信息。
   - **完成标准**：每类错误明确标注“可在本层恢复 / 必须上报 / 不可安全继续”。

3. **按顺序走缩减阶梯**
   - **定义规避**：把“删除存在项”改为“确保不存在”，把范围操作定义为有效交集。
   - **底层屏蔽**：本层能可靠恢复时执行有限重试、切换副本或自动修复。
   - **边界聚合**：不同内部错误若对外是同一响应，在请求、任务或事务边界统一转换。
   - **明确失败**：不变量已破坏、无法恢复且继续运行危险时，记录充分诊断后终止最小故障域。
   - **显式暴露**：调用者必须据此决策时，返回稳定、可判别的错误契约。
   - **完成标准**：每类错误恰好选择一种主策略，并说明为什么前一层策略不适用。

4. **设计恢复约束**
   - 重试必须有幂等性依据、次数/时间预算、退避和取消。
   - 屏蔽必须保留指标、日志、追踪和最终失败升级。
   - 聚合时使用简单稳定的边界错误，不把框架或数据库异常对象穿透核心边界。
   - **完成标准**：不会无限重试、重复副作用或把诊断全部丢失。
   - **判停条件**：无法证明幂等性或恢复安全时，禁止自动重试/吞错，改为显式暴露。

5. **缩减调用者分支**
   - 删除已经由新语义、底层恢复或边界聚合覆盖的预检查、重复 `catch` 和包装。
   - **完成标准**：常见路径只处理它真正能决定的失败，不再复制机制细节。

6. **用故障注入验收**
   - 覆盖正常边界、短暂故障、预算耗尽、永久故障和内部损坏。
   - **完成标准**：正常边界无需异常分支；可恢复故障透明恢复且可观察；重要故障准确到达正确决策者；不可恢复故障停止在最小安全范围。

## B — 边界

### 不要在以下情况使用此 方法

- 目标是让错误“看不见”而不是降低处理复杂性；必须保留可观测性。
- 财务、医疗、安全、持久化或权限错误需要调用者确认，不能用默认成功替代。
- 分布式操作没有幂等性或补偿语义，不得机械增加重试。

### 作者在书中警告的失败模式

- 用异常表示空选区、缺失项等可定义为正常结果的边界。
- 每层捕获后只换一个名字再抛出，扩大异常处理面。
- 屏蔽所有错误，使重要故障语义和数据损坏消失。
- 为绝不可能安全恢复的内存耗尽等情况铺设遍地分支，反而让常见代码更难验证。

### 作者的盲点 / 时代局限

- 分布式系统中的超时可能代表成功、失败或未知结果；简单屏蔽需要幂等键、去重和一致性设计。
- 合规系统可能要求保留每次失败和决策链，即使这增加接口复杂性。
- 进程中止是否安全取决于隔离、编排和恢复机制，不能照搬单进程案例。

### 容易混淆的邻近方法论

- “通过定义规避错误”不是返回默认值掩盖错误，而是为边界情况给出满足调用者意图的稳定语义。
- “异常聚合”不是把所有错误变成同一字符串；内部诊断可以丰富，对外契约应稳定。
