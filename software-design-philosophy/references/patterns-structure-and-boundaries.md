# 结构与边界模式

## 本页导航

1. 使用范围与五种边界
2. 模块化单体、分层、六边形与深模块
3. 流水线、微内核与插件
4. 服务/微服务与 API 聚合边界
5. 协议、进程角色和仓库边界
6. 认证状态与授权策略
7. 案例使用方法与审计输出

## 使用范围

当问题涉及源码模块、进程、服务、仓库、团队所有权、API 聚合、插件或信任策略边界时使用。先读 [模式选择器](select-system-design-patterns.md)。

本页不规定“系统应该分层”或“应该拆服务”。核心问题是：

> 哪些知识、决策和变化应共同拥有；哪些边界的自治收益足以支付接口、通信、部署和运维成本？

## 先分清五种边界

| 边界 | 提供的隔离 | 新增成本 | 不能自动推出 |
|---|---|---|---|
| 函数/类/包 | 命名、可见性、知识封装 | 接口与跳转 | 独立发布、故障隔离 |
| 同进程模块 | 明确责任、依赖规则、可替换实现 | 组合与生命周期协调 | 网络自治 |
| 进程/容器 | 地址空间、资源和崩溃隔离 | IPC、序列化、启动与观测 | 团队自治 |
| 服务/部署单元 | 独立发布、扩缩、故障和所有权 | 网络失败、版本、数据和运维治理 | 低耦合或高可用 |
| 仓库 | 权限、版本和工具链边界 | 跨仓变更与依赖发布 | 服务边界或领域边界 |

源码边界可以很清晰而仍部署在一个进程；多个服务也可能因共享数据库、同步发布和聊天式调用而没有真实自治。

## S01 模块化单体、分层与六边形边界

### 适用压力

- 系统仍适合共同部署，但业务知识、框架、I/O 和入口彼此污染；
- 高频变更不知道从哪里进入，或数据库/传输表示反向约束核心规则；
- 需要替换外部适配器、测试核心行为或让依赖方向明显。

### 结构动作

- **模块化单体**：按知识与变化轴形成同进程模块，通过显式接口和组合根协作。
- **分层**：按稳定责任组织依赖方向；层只有隐藏知识并减少调用者负担时才存在。
- **六边形/端口与适配器**：由需要外部能力的一侧拥有窄契约，适配器翻译技术协议。

### 代价与失效

- 为每个用例制造 Controller/Service/Port/Adapter 透传链，会形成浅模块和小模块综合症；
- 把所有数据库、Web 或运行后果叫“细节”，会隐藏调用者必须知道的保证；
- 目录看似分层但构建、数据和知识仍双向穿透，只得到形式隔离。

### 验证与退出

重放一个核心变更和一次适配器替换，记录修改点、必须知道的知识和透传层。若新边界没有减少知识传播，合并无收益层；若已经出现独立发布/扩缩/故障要求，再比较物理拆分。

## S02 深模块边界

深模块不是一种目录风格，而是接口负担明显小于其隐藏能力。具体构造仍使用 [深模块设计闭环](design-deep-modules.md)：

- 用高频与高影响完整工作流设计有限原语；
- 把格式、策略、生命周期和默认决策收进唯一所有者；
- 为长尾需求提供类型化、可治理、能重新汇入的逃逸；
- 不强迫刻意简单的值类型、纯函数或协议适配器变“深”；
- 有证据的性能入口可以显式表达所有权、布局或批量语义。

在结构模式中，深度用来评价每一个模块、服务和 Gateway 是否真正隐藏了复杂性，而不是只搬运调用。

## S03 流水线与过滤器（Pipes and Filters）

### 适用压力

数据按稳定阶段转换，每阶段可独立理解、复用、重排或并行；阶段间能用小而明确的数据契约连接。

### 结构动作

让每个阶段拥有一种转换知识，管线拥有顺序、取消、背压和整体结果。批处理、编译、媒体处理和数据加工常见，但“执行顺序”本身不应成为唯一拆分依据。

### 代价与失效

- 阶段共享大量隐式状态、必须成对修改或频繁来回转换时，拆分泄露了共同知识；
- 每一步都跨进程会增加复制、序列化和部分失败；
- 管线失败、重试和中间结果归属不清时，调用者承担全局状态机。

### 验证与退出

演练新增、合并、重排一个阶段以及中途失败；若修改总需跨越多个阶段，按共享知识重新组合。关键路径按代表性数据测量同进程与跨进程代价。

## S04 微内核与插件（Microkernel / Plugin）

### 适用压力

稳定核心需要承载多种可选能力，扩展由第三方或独立团队演化，且插件可通过有限契约完成完整工作流。

### 结构动作

- 核心拥有身份、生命周期、权限、资源、错误和扩展注册等稳定不变量；
- 插件以组合、接口、trait 或 concept 接入，不依赖多个含状态基类和模板方法顺序；
- 扩展数据、版本、能力发现和失败隔离成为公共契约；
- 高频长尾能力重新收编为核心原语，避免形成第二套平行生态。

### 代价与失效

插件会增加兼容承诺、版本矩阵、沙箱、资源治理和调试成本。插件必须读取核心内部对象图、绕过身份/生命周期或大量复制胶水时，扩展点过浅或放错位置。

### 验证与退出

用两个结构不同的真实插件和一次核心升级做兼容演练；统计逃逸频率、插件私有胶水和无法重新汇入的状态。没有真实独立扩展者时，不预建完整插件平台。

## S05 服务与微服务边界

### 准入条件

至少有一项已观察收益：

- 团队需要独立拥有和发布一组知识与不变量；
- 负载、资源或可用性要求需要独立扩缩和故障隔离；
- 安全或法规要求独立信任边界；
- 共同部署持续阻断高频变更。

还要证明收益大于网络 hop、序列化、版本兼容、分布式事务、数据复制、可观测性和 on-call 成本。

### 结构动作

服务拥有自己的行为、不变量和生命周期；若声称自治，不能把真正的写入权威留在共享数据库或要求同步发布。服务粒度按共同知识和变化轴，而不是“一个动作一个服务”。

### 常见失效

- 分布式单体：聊天式同步调用、共享数据库、共同发布；
- 纳米服务：接口数量和运维成本大于隐藏能力；
- 团队图直接复制成服务图，业务工作流反而跨越更多所有者；
- 仅因代码量、模块数或“云原生”标签拆分；
- 低延迟、大中间数据或强内存状态路径被无证据地网络化。

### 验证与退出

比较同进程模块、粗粒度服务和细粒度服务三个候选。重放发布、扩容、故障和高频业务变更；测端到端 hop、跨边界事务、依赖 fan-out 和团队协调。收益不成立时保持模块化单体或重新聚合为较粗服务。

## S06 API 聚合、Gateway、BFF 与 Federation

| 候选 | 适用压力 | 主要代价/失效 |
|---|---|---|
| 客户端直连 | 服务少、契约稳定、fan-out 小 | 客户端知道服务图，多次往返 |
| API Gateway / Aggregation | 多服务共同组成常见工作流，跨切面策略需集中 | 额外 hop、单点容量、中央团队排队 |
| BFF | 客户端形态和发布节奏显著不同 | 重复聚合与多套维护 |
| 领域 Federation | 领域团队成熟且需拥有各自 schema，调用方仍需统一图 | schema 组合、成本控制、版本与治理复杂 |

先找聚合规则权威：

- 多个客户端重复拼装同一业务语义时，应由知道该语义的边界隐藏；
- 各客户端只有展示差异时，BFF 可以拥有适配而不复制核心规则；
- 中央 Gateway 同时承担业务规则、鉴权、协议转换和所有领域聚合时，可能成为浅而宽的瓶颈；
- Federation 只有在领域所有权真实存在且契约治理可执行时成立。

验证 client fan-out、端到端延迟、网关变更等待、schema 重复和故障传播。新增 Gateway 若只是反向代理多一跳，不是架构改进。

## S07 REST、RPC、GraphQL 与实时连接

协议名不能决定边界：

- **REST/稳定资源接口**适合简单、一致、易缓存的公共契约；
- **RPC/gRPC**适合内部强类型命令、低开销调用或流式通信，但调用者更容易依赖服务方法与部署拓扑；
- **GraphQL**适合客户端字段需求快速变化、跨源聚合和减少往返，但查询成本、授权、缓存、滥用和 schema 所有权成为核心责任；
- **WebSocket/SSE**是连接与更新通道，不能替代业务命令、顺序、重连和恢复契约。

用真实客户端工作流比较调用次数、字段变化、服务端查询复杂度、兼容性和故障语义。URL 数量、端点数量或“现代”不是裁决维度。

## S08 进程角色分离

API、worker、定时任务、一次性 bootstrap、迁移和管理面可以：

1. 同进程、同生命周期；
2. 同一制品按角色启动；
3. 独立制品与部署。

只有启动失败域、幂等、独立扩缩、故障隔离、发布节奏、权限或关闭顺序有真实差异时才分离。先把副作用集中到显式组合位置和角色契约，再决定是否物理拆进程；否则会为尚不存在的运行需求增加部署面。

验证每个角色的依赖、readiness、幂等、扩容副作用、优雅关闭和失败传播。一个进程承担多项责任不是自动问题。

## S09 Monorepo 与 Multi-repo

| 选择 | 主要收益 | 主要成本 |
|---|---|---|
| Monorepo | 跨模块原子变更、统一依赖和规则、共享工具 | 构建/检出/权限工具必须规模化，被迫共同变更风险 |
| Multi-repo | 独立版本、权限和发布节奏 | 版本漂移、跨仓协调、兼容矩阵和依赖治理 |

仓库拓扑不应机械复制服务拓扑。先抽样近期跨域功能、依赖升级和发布，记录协调轮次、构建时间、被迫发布范围和策略重复。若瓶颈只是检出工作集或构建配置，先修工具；不要把工具性能问题误判为必须迁仓。

## S10 认证状态与授权策略边界

这类问题只有影响跨边界状态和政策所有权时进入架构：

- **服务端 session**便于即时撤销和集中控制，但需要高可用状态存储；
- **自包含 token**便于离线验证和横向扩展，但撤销、过期、密钥轮换与 claim 解释更复杂；Cookie 只是可能的运输方式；
- **ACL**适合少量资源例外，规模大时维护昂贵；
- **RBAC**适合稳定职能，过多例外会产生角色爆炸；
- **ABAC**表达动态上下文，但规则组合和可解释性成本高；
- **MAC/DAC**分别偏向强制标签和资源所有者自治。

先写即时撤销、跨服务信任、默认拒绝、政策变化轴和审计解释要求，再选模型。具体加密算法、token 库或一个错误默认值通常属于安全实现；政策由谁拥有、各入口是否重复解释和撤销状态如何跨边界传播才是架构问题。

## 演化案例怎样使用

System Design 101 的公司案例只生成问题，不提供可直接复制的答案：

| 案例信号 | 可借用的判断 | 不能推出 |
|---|---|---|
| Airbnb 从单体拆服务后又聚合部分服务 | 服务粒度要同时考虑所有权与认知负荷 | 当前仓库也应经历同一路线 |
| Prime Video 将分布式组件共置 | 逻辑模块不等于独立进程，通信成本可改变部署边界 | 所有 serverless 都昂贵 |
| Netflix API 从聚合到 BFF 再到联邦 | 聚合权威随客户端差异与领域所有权演化 | GraphQL Federation 是终局 |
| Levels.fyi 以简单工具支撑早期规模 | 架构复杂度应跟随已证实压力 | 任何产品都应使用同样工具 |
| TikTok/Pinterest 优化仓库工具 | 工具瓶颈不自动要求改变仓库拓扑 | Monorepo 总是更优 |

案例事实必须回查原始来源或当前仓库证据；不能把二手快照当成现状。

## 审计输出

| 边界 | 共同知识/变化轴 | 自治收益 | 接口与通信成本 | 当前证据 | 结论与验证 |
|---|---|---|---|---|---|

结论不写“违反分层”“应该微服务化”“建议加 Gateway”。要写清新旧知识所有者、边界移动、减少的真实任务成本、新增故障和撤回条件。
