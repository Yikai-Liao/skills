## R — 原文

> 如果方法的接口注释提供使用它所需的全部信息，并且既简短又简单，就表明该方法具有简单的接口。
>
> — John Ousterhout，第 13 章

---

## I — 方法论骨架

接口的完整抽象不只存在于类型签名中，还包括语义、约束、副作用、错误和设计理由。
在实现前写这些内容，会迫使设计者站到调用者位置，提前发现职责混杂和浅接口。
先描述类或模块代表什么、隐藏什么，再描述主要方法做什么；不要先写内部步骤。
若一个接口必须用长篇实现细节才能说明，通常不是“文档难写”，而是抽象还不完整。
关键状态和不变量也应先被命名，使实现围绕明确模型展开。
实现过程中出现的新参数、状态或异常，必须回到契约层判断它是否属于抽象。
注释应记录代码本身不能明显表达的信息，不复述语法。
完成后由不看实现的读者仅凭契约使用接口，才能证明抽象真正成立。

## A1 — 书中的应用

### 案例 1：IndexLookup 的迭代式接口注释

- **问题**：分布式索引查询涉及 RPC、缓存、批次和节点切换，接口表面却只是迭代结果。
- **方法论的使用**：作者用接口注释说明调用顺序、返回语义和隐藏保证，而不向调用者展开内部网络流程。
- **结论**：深模块可以有复杂实现，但契约必须给出正确使用所需的完整视图。
- **结果**：调用者按简单迭代模型使用查询，不必了解分布式检索机制。

### 案例 2：作者先写类和方法注释

- **问题**：直接编码容易让签名跟随第一个实现，等实现完成才发现抽象难以解释。
- **方法论的使用**：作者先写类总体注释和主要公开方法注释，反复修改签名与职责，再写成员和方法体。
- **结论**：无法简短完整描述是设计反馈，应先重构抽象而不是堆叠说明。
- **结果**：文档成为设计工具，而不是实现后的补写任务。

### 案例 3：RAMCloud 集中设计说明

- **问题**：僵尸服务器协议等跨模块决策无法放进单个接口注释，复制到各处又会漂移。
- **方法论的使用**：在唯一 `designNotes` 中保存整体设计理由，相关代码就近链接；局部状态清单放在权威枚举旁。
- **结论**：文档的粒度和位置应匹配知识范围，并保持单一权威。
- **结果**：维护者能从代码找到设计背景，而不会面对多份互相冲突的解释。

## A2 — 触发场景

### 用户会在什么情境下需要这个方法？

1. 新 API 签名已写好，但团队对参数、返回值或副作用理解不一致。
2. 类名很抽象，没人能用一句话说明每个实例代表什么。
3. 接口文档必须解释大量内部步骤，调用者仍不知道能依赖哪些保证。
4. 并发、缓存、事务或持久化语义只存在于实现者脑中。
5. 改代码时发现旧注释失真，不知道应改代码、契约还是设计说明。

### 语言信号

- “这个接口注释应该写什么？”
- “先写代码还是先写文档？”
- “怎么用注释检验抽象？”
- “为什么这个类怎么都解释不清？”
- “调用者到底能依赖哪些保证？”

### 与相邻方法 的区分

- 与 `design-deep-modules` 的区别：本方法 是抽象压力测试和契约表达工具；深模块方法 还负责用例覆盖、原语归约和逃逸。
- 与 `make-code-obvious-to-readers` 的区别：这里聚焦接口设计前的语义；后者覆盖命名、一致性、控制流和实现阅读。
- 与 `audit-information-leakage` 的区别：文档权威可以缓解不可避免的跨模块知识；若代码仍重复解释同一决定，需泄露审计。

## E — 可执行步骤

1. **确定读者和抽象层**
   - 写明谁会调用、他们要完成什么、哪些实现知识不应要求他们知道。
   - **完成标准**：读者角色与模块责任各有一句明确描述。

2. **先写模块总体契约**
   - 回答：模块代表什么、拥有何种状态/知识、提供哪些保证、明确不负责什么。
   - 若是架构边界，再写明高层策略、低层细节和依赖方向；不要把框架名当业务抽象。
   - **完成标准**：5–10 句内能形成完整使用视图，不列实现步骤。

3. **写主要公开方法的契约**
   - 对每个方法说明：
     - 行为与结果；
     - 参数和返回值的语义，而非类型复述；
     - 前置/后置条件与不变量；
     - 副作用、幂等性、并发、持久化和顺序保证；
     - 正常边界与错误。
   - **完成标准**：调用者无需读实现即可判断一次调用是否合法、成功意味着什么。

4. **做“简短且完整”压力测试**
   - 若注释冗长，检查是否混入多个职责、暴露内部表示或要求配对调用。
   - 若注释很短却遗漏关键保证，让读者提出反例补齐。
   - **完成标准**：说明长度与功能相称，既不复述实现，也没有依赖“大家都知道”。
   - **判停条件**：必须描述主要算法或内部对象组装才能安全使用时，先重设抽象，不进入编码。

5. **声明关键状态和不变量**
   - 为成员、状态枚举、锁和生命周期写含义；把跨模块决策放在唯一权威说明中并就近链接。
   - **完成标准**：每个重要状态都能解释允许的转换和维护责任。

6. **再实现，并让新发现反推契约**
   - 每新增参数、异常、配置或公开方法，都先问它是否属于调用者视图。
   - 若实现暴露契约未表达的重要语义，修改契约或重构设计，不能只藏在方法体注释里。
   - **完成标准**：实现符合契约，公共表面没有“实现到一半顺手加”的元素。

7. **用契约驱动评审与测试**
   - 让评审者不看实现演算常见、边界和失败场景，再检查测试是否验证承诺而非内部步骤。
   - 让模块可见性、依赖规则和类型约束尽可能执行书面边界。
   - **完成标准**：读者解释一致；契约变化会触发相应测试和审查。

8. **维护单一权威**
   - 代码变更时先判断是行为变了还是实现变了；行为变更同步接口契约，实现变更通常不改接口说明。
   - 删除重复、过时或离代码太远的说明。
   - **完成标准**：每项设计知识只有一个权威位置，相关位置可链接到它。

## B — 边界

### 不要在以下情况使用此 方法

- 注释只是把 `i++` 改写成“i 加一”，会增加噪声。
- 接口问题能通过准确命名、类型或拆分直接消除，应先改代码而非补解释。
- 安全关键契约还需要形式规范、schema、类型或验证工具，普通注释不能替代。

### 作者在书中警告的失败模式

- 注释复述代码，而不说明调用者真正需要的非显然信息。
- 先完成实现再补文档，使注释被当前结构绑架。
- 接口注释泄露内部算法，导致实现变化时文档频繁失真。
- 同一设计决定复制到多处注释，最终互相矛盾。
- 用长注释为浅模块和含糊职责辩护。

### 作者的盲点 / 时代局限

- 现代类型、契约测试、schema 和静态分析可把部分自然语言约束机器化，应优先选择可执行表达。
- 文档维护需要团队纪律；公开 API、跨组织协议还需版本和兼容政策。
- 书中偏向类/方法注释，事件驱动和分布式系统还应记录时序、交付与一致性模型。

### 容易混淆的邻近方法论

- 注释优先不是“文档驱动瀑布”：契约应随实现反馈迭代。
- “代码自解释”适用于实现能表达的部分；设计理由、跨调用语义和隐含约束仍需文档。
