# 从必要契约反推全局简化

用于用户希望减少整体实现负担，或局部整理无法消除反复出现的转换、协调与双轨实现时。
“全局”指沿相关工作流理解整体代价，不要求扫描整个仓库或一次重写系统。
本参考负责发现简化候选；定性、取舍与实施沿用架构审计和方案比较与演化。

## 暂时放下现有机制

先问：若今天只需满足已知契约，会怎样实现这条工作流？
把必须保留的结果、约束与当前实现手段分开，避免把已有模块和数据结构都当成需求。

- **必要契约**：结果、不变量、公开承诺、实际消费者依赖，以及适用的权限、持久化、失败和性能要求。
- **现有机制**：中间模型、转换、缓存、事件、调度、适配器、配置、扩展点及其生命周期。
- **待核实约束**：缺少来源或消费者证据的历史假设，标明未知，不直接删掉，也不默认永久保留。

搜索时可以假设替换现有机制；接受方案前必须核实它承载的契约。
不为保持内部形状保留代码，也不以“只是内部实现”为由忽略外部依赖。

## 沿工作流寻找可一起消失的机制

选与目标相关的真实工作流，从输入到结果及相关失败、取消、恢复和清理追踪：
数据经过哪些表示和转换，状态由谁拥有，哪些组件只负责让其他组件保持一致。
阅读调用方、运行配置、持久化与外部边界；目录结构和局部引用搜索不能证明全貌。

优先尝试以下问题，不要求逐项执行或形成清单：

- 能否让同一份权威表示贯穿更多步骤，连带删除中间模型、映射、校验副本和同步逻辑？
- 能否通过调整状态归属，使缓存失效、重复记账、状态镜像或补偿协调不再需要？
- 能否将总是一起完成的责任收回同一边界，删除调用者的顺序、配对和生命周期胶水？
- 能否用一个完整原语覆盖真实用例，退出平行入口、旧实现及其各自维护的规则？
- 能否收窄没有实际消费者且不属公开承诺的自由度，删除只为支持这些选择存在的分支和扩展机制？
- 能否改变上游输入或边界，使下游一整类特殊情况不再产生，而不只是集中处理它们？

从具体负担反推其上游原因；不要停在合并函数、提取公共代码或删掉薄封装。
相似实现可能表达不同语义；合并后需要更多模式、条件和例外时，未必更简单。
使用多个审查者时，不仅按文件分工：保留跨端到端路径的视角，检查局部建议组合后是否仍需原有协调。

## 把搜索与接受分开

允许提出尚未证明值得实施的结构假设，不必先认定当前设计有架构缺陷。
候选说明“改变什么决定，哪些机制因此消失，哪些契约需要验证”，避免只写“统一”或“抽象”。
对于有价值的方向，与现状或局部修正比较；不为满足候选数量制造方案。
搜索范围不以最小 diff 为目标；实施仍按可验证、可回退的完整切片推进。

例如：内部 DTO 只为转交相同数据而存在，可探索直接传递领域值，连带删除映射和重复校验。
若它实际隔离外部版本、权限字段或持久化格式，则这些责任仍须有明确归属。
把 DTO 改名、将转换藏进框架，或把责任推给每个调用方，都不等于消除了复杂性。

## 用净复杂性决定是否采用

比较同一工作流改动前后的总负担，包括核心实现、调用方、测试、配置、部署与迁移。
检查少了哪些独立概念、状态、同步关系和失败路径，又新增了哪些分支、隐含约定或依赖。
代码净减少可以作为结果证据，但不设行数配额；代码搬家、压缩写法或降低可读性不算简化。
测试与文档的删除单列，不用于充当生产实现的缩减；保留必要行为覆盖，不永久冻结内部形状。
新增少量代码若能消除长期协调，也可能更简单；新增依赖的维护与运行成本同样计入。

区分“删掉收益低的特化”和“保留优化、简化承载它的表示与生命周期”，不要只探索前者。
保留有证据的性能机制与安全边界，或用相称验证证明替代方案仍满足要求。
删除缓存、复制、批处理或零拷贝路径前核实实际作用；不能用“更直接”推断性能不退化。
检查仓库外消费者、持久化数据、新旧版本共存和运维入口；未找到引用不等于没有契约。
验证应能反驳候选的关键假设，而不只是证明新代码能运行；未知影响保留为条件或阻断项。

接受候选后，按完整工作流切片迁移，明确旧机制和临时双轨何时真正退出。
设计咨询不自动转为重写；没有可信净收益时保留现状，不强制新增流程或交付文档。
