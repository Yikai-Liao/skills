# 软件设计哲学共享术语词典

本词典供 11 个方法共用。主书术语以 John Ousterhout 的含义为准；“辅助术语”来自
《架构整洁之道》；“本包合成术语”是蒸馏流程为了可执行性引入的名字；“系统 pattern 术语”由 `System Design 101` 的候选经主书尺度重述，不冒充任一来源原话。

## 本页导航

1. 复杂性与诊断
2. 模块、接口与知识边界
3. 有限接口、默认路径与专用需求

6. 系统 pattern 术语

## 一、复杂性与诊断

### 复杂性

- **含义**：任何让软件系统难以理解和修改的因素；还要按开发者接触该部分的频率加权。
- **不是**：系统大、功能多、算法难或代码行数多本身。
- **使用**：所有设计规则冲突时，回到真实任务的整体理解和修改成本裁决。
- **对应方法**：[`diagnose-software-complexity`](./diagnose-software-complexity.md)

### 复杂性的三种症状

- **变更放大**：概念上的一次变化需要修改很多位置。
- **认知负荷**：安全完成任务前必须同时掌握大量信息。
- **未知的未知**：开发者不知道还要查看或修改什么，甚至不知道风险存在。
- **注意**：它们是表现，不是根因；根因通常是依赖性与模糊性。

### 依赖性

- **含义**：一段代码无法被孤立理解或修改，必须连带考虑其他代码或知识。
- **范围**：不只包括导入和调用，还包括协议两端、共享格式、状态顺序和隐含约定。
- **目标**：不是消灭所有依赖，而是减少依赖，并让剩余依赖简单、稳定、明显。

### 模糊性

- **含义**：完成任务所需的重要信息不明显。
- **来源**：错误抽象、含糊名称、不一致、隐藏控制流、缺失契约或不明显依赖。
- **不是**：单纯“注释太少”；多写注释可能仍掩盖错误设计。

## 二、模块、接口与知识边界

### 模块

- **含义**：任何同时具有接口与实现的代码单元。
- **范围**：函数、类、包、子系统、进程和网络服务都可按模块原则审查。
- **注意**：深模块不等于“大类”，模块尺度必须在任务中明确。

### 接口与实现

- **接口**：调用者正确使用模块必须知道的全部内容，包括行为、约束、副作用、错误和顺序保证。
- **实现**：接口如何实现的内部代码和知识。
- **关键区别**：私有字段若调用者必须理解才能正确使用，其知识已经事实性进入接口。

### 抽象

- **含义**：保留目标使用者真正需要的信息，并省略对其不重要的细节。
- **错误抽象**：隐藏了重要信息，或把大量不重要细节带入调用者视图。
- **对应方法**：[`design-abstractions-comment-first`](./design-abstractions-comment-first.md)

### 深模块

- **含义**：完整接口成本较低，却提供强功能并隐藏大量设计知识的模块。
- **不是**：代码多、方法少、层级深或类体积大。
- **验收**：常见与高影响用例有直接路径；未覆盖需求有明确归位；调用者不复制内部知识。
- **对应方法**：[`design-deep-modules`](./design-deep-modules.md)

### 浅模块

- **含义**：学习和使用接口的成本，与模块提供的功能和信息隐藏收益相近。
- **信号**：只包一两行明显代码、接口注释近似复述实现、透传同样参数而不增加抽象。
- **注意**：并非所有小类都浅；判断对象是接口收益比，不是行数。

### 信息隐藏

- **含义**：把一项设计知识及其相关决定封装在单一模块内部，使其不进入普通调用者接口。
- **不是**：只加 `private`，或为每个内部字段提供 Getter/Setter。
- **部分隐藏**：少数高级用户通过独立入口接触必要控制，普通用户仍无需知道。

### 信息泄露

- **含义**：同一设计决定反映在多个模块中，使一次变化要求多处保持一致。
- **公开泄露**：接口直接暴露内部格式、状态或表示。
- **后门泄露**：多个实现独立解析或重建同一知识，即使 API 中看不见。
- **传递性泄露**：一个模块因依赖对象暴露细节，被迫继续依赖更下层实现。
- **对应方法**：[`audit-information-leakage`](./audit-information-leakage.md)

## 三、有限接口、默认路径与专用需求

### 有点通用

- **含义**：模块功能以当前真实需求为边界，但接口不绑定当前单一按钮或业务动作，而以少量原语覆盖一类用途。
- **不是**：为未知未来建万能框架，也不是用很多开关把所有专用动作塞进一个方法。
- **例子**：范围删除比“退格、前删、删除选区”三个核心方法更有点通用。

### 专用代码上移或下移

- **上移**：业务动作、界面流程或分组规则留在掌握整体语义的上层，由核心原语组合。
- **下移**：设备、供应商或操作类型差异进入共同接口后的具体实现。
- **目的**：让共享核心保持通用，同时不否认真实专用需求。

### 常见情况

- **含义**：按开发者实际使用频率判断的常见调用方式。
- **设计要求**：应有最短、最明显且有安全默认的路径。
- **区别**：它不是性能章节中由测量确认的“关键路径”。

### 默认值

- **含义**：为多数调用者自动选择合理行为，使他们通常无需知道选择本身存在。
- **边界**：不能替调用者猜测模块无法获知的安全、持久化、合规或业务策略。
- **治理**：少数覆盖入口应与常见构造和示例分开。

### 配置参数

- **含义**：调用者显式控制模块行为的接口元素。
- **成本**：每个参数都会把策略判断、组合语义和测试负担交给调用者。
- **准入条件**：只有调用者确实拥有模块无法推断的重要信息，或能作出更好决定时才公开。

### 下沉复杂性

- **含义**：由最了解问题的模块承担与其职责密切相关的复杂性，从而一次性简化多个调用者。
- **不是**：把所有功能塞进大类，或无条件替用户作决定。
- **判据**：下沉后系统总复杂性下降，接口更简单，且没有隐藏重要信息。

### 受控逃逸（本包合成术语）

- **含义**：有限核心无法覆盖某项真实需求时，把它明确分流到：
  1. 核心原语；
  2. 上层组合；
  3. 专用实现或适配层；
  4. 独立高级入口。
- **主体不变量**：逃逸可以增加专用动词，但不能随意重造身份、生命周期、权限、状态一致性、错误与可观测体系；结果应能重新汇入公共治理。
- **审计维度**：逃逸频率、逃逸深度、局部性、重新汇入能力和生态分叉成本。
- **治理要求**：与常见路径隔离、只暴露必要信息、优先类型化、可观测；相同逃逸反复出现时晋升为核心，长期不用时淘汰。
- **来源说明**：主书提供默认值、专用代码上/下移、重要信息必须暴露等依据；用户补充的 Linux 文件系统设计材料提供主体不变量和逃逸审计细则。两者都没有使用本包的“受控逃逸”一词。

### 独立测试 / Agent 调试面（本包合成术语）

- **含义**：与生产业务 API 分离、允许获准测试或 Agent 无需修改业务代码即可构造状态、注入故障、检查和清理的高权限控制面。
- **创建条件**：设计深模块时必须主动询问；只有设计者明确要求后才创建，不能因“可能方便”自行加入。
- **接口要求**：稳定 CLI/API、明确 schema、幂等语义、短期限环境限能力令牌、审计和自动回收。
- **安全边界**：独立部署或不可绕过的环境门禁保证生产不可达；不得退化成无类型 `eval`、内部对象裸暴露或公共核心入口。

## 四、错误、性能与重要性

### 通过定义来规避错误

- **含义**：调整操作语义，使原来的边界情况成为有明确结果的正常行为。
- **例子**：把“删除存在变量”改为“确保变量不存在”。
- **不是**：捕获后丢弃错误；调用者必须知道的重要失败仍要暴露。
- **对应方法**：[`reduce-exception-surface`](./reduce-exception-surface.md)

### 关键路径

- **含义**：先由测量定位的、真正决定整体性能的少数执行路径。
- **设计动作**：写出常见情况的理想最少代码，把稀有情况通过一次检查分流到慢路径。
- **不是**：凭直觉挑出的“看起来常用”代码。
- **对应方法**：[`design-measured-critical-paths`](./design-measured-critical-paths.md)

### 重要信息

- **含义**：相对于目标使用者、任务和外部约束，必须明显且不能被安全推导的信息。
- **杠杆点**：一个决定能解决多个问题，或知道它后其他信息容易推导的位置。
- **设计要求**：最小化重要事项数量，把它们集中并强调；其余细节隐藏或自动处理。
- **对应方法**：[`design-around-what-matters`](./design-around-what-matters.md)

## 五、辅助材料术语

### 行为者 / 变化轴

- **来源**：《架构整洁之道》第 7、13、17 章。
- **含义**：提出同类变化要求的一组利益相关者，以及代码因此发生变化的原因和速率。
- **用途**：作为拆分证据；不同变化轴倾向隔离，相同原因且同时变化倾向组合。
- **限制**：不能把它机械化为“一个行为者一个类/服务”，仍要计算接口和知识成本。

### 依赖关系规则

- **来源**：《架构整洁之道》第 11、19、22 章。
- **含义**：源码依赖应由易变的低层机制指向更稳定的高层策略，控制流可通过接口与多态反向。
- **用途**：保护知识所有者不被具体数据库、Web、硬件或框架污染。
- **限制**：层次不能自动决定什么重要；主书的真实任务与调用者知识仍是最终判据。

### 策略与细节

- **来源**：《架构整洁之道》第 15、19–22、30–32 章。
- **策略**：业务规则、用例和较稳定的系统决定。
- **细节**：数据库、Web、框架、设备与装配机制。
- **限制**：“细节”表示依赖位置和可替换地位，不代表持久化、安全、性能或运维后果不重要。

### 边界强度

- **来源**：《架构整洁之道》第 16、18、24 章。
- **层级**：同进程源码边界、独立部署单元、本地进程、网络服务。
- **成本**：越强的物理隔离通常增加通信、失败、版本与运维成本。
- **用途**：边界是否存在与边界是否物理分离是两个独立决定。

### 不完全边界

- **来源**：《架构整洁之道》第 24、25 章。
- **含义**：通过单向接口、Facade 或统一部署等方式保留部分接缝，而暂不承担完整独立组件成本。
- **用途**：在“现在完整拆分”和“完全不准备”之间提供可逆候选。
- **限制**：只为有证据且未来补边界昂贵的变化轴使用，避免预测性过度设计。

### 组合根 / Main 组件

- **来源**：《架构整洁之道》第 26、32 章。
- **含义**：创建具体对象、装配依赖、加载配置和外部资源，再把控制交给核心策略的最外围入口。
- **用途**：把不可避免的具体依赖集中在一处，避免框架注解和供应商类扩散到业务模块。

### HAL / OSAL

- **来源**：《架构整洁之道》第 29 章。
- **HAL**：硬件抽象层；按上层产品需要提供接口，而不是镜像寄存器和 GPIO。
- **OSAL**：操作系统抽象层；隔离 RTOS 或平台原语，使高价值逻辑可脱离目标环境测试。
- **用途**：作为深模块、专用实现下移和信息泄露修复的具体案例。

### 真实重复与表面重复

- **来源**：《架构整洁之道》第 16 章。
- **真实重复**：各副本必须因同一决定一起变化，倾向集中。
- **表面重复**：当前代码相似，但服务不同角色、未来独立演化，强行合并反而制造耦合。
- **用途**：补充主书的信息泄露审计，防止把 DRY 机械化。

## 六、系统 pattern 术语

### 架构模式、组件与产品

- **架构模式**：在一组条件下反复出现的责任、关系、数据流或协调结构，并包含成立条件与权衡。
- **组件/产品**：模式的一种实现候选，例如具体网关、缓存或消息产品。
- **边界**：模式名和产品名都不是架构发现；只有改变系统构造或跨边界保证时才是架构决定。
- **对应入口**：[系统设计模式选择器](./select-system-design-patterns.md)

### 负载模型与质量预算

- **负载模型**：使用者、流量分布、峰值/突发、数据增长、并发、对象大小和资源需求的可复现描述。
- **质量预算**：把高性能、高可用、实时等口号改写为分位延迟、吞吐、错误预算、新鲜度、RTO/RPO 和资源/成本上限。
- **限制**：平均 QPS、行业默认数字或公司案例不能代替当前系统的代表性负载。

### 无状态服务

- **含义**：一次请求不依赖某个实例先前保存的会话状态，因此可由其他实例接手；系统本身仍可在外部存储拥有状态。
- **不是**：系统没有状态、有状态组件天然错误，或所有状态都必须放数据库。
- **契约后果**：保留本地状态时，需要明确黏性、分片、迁移、恢复和副本。

### 数据所有权

- **含义**：一个边界对某项数据的权威写入规则、业务不变量和演化决策负责；其他边界通过契约或事件使用并可维护投影。
- **不是**：每个服务必须有一个独立物理数据库。
- **失败信号**：多个边界绕过权威直接写，或状态、缓存、事件各自成为真相源。

### 编排与协同

- **编排**：中央协调者拥有工作流状态与下一步决策。
- **协同**：参与者依据事件和协议分散推进。
- **裁决**：核心是工作流知识和恢复责任归谁，以及集中容量/分散规则成本；它们不等同于同步/异步。

### CQRS、Event Sourcing 与 CDC

- **CQRS**：命令/写模型与查询/读模型分离，不要求两个数据库。
- **Event Sourcing**：不可变业务事件序列是权威历史，状态由其派生。
- **CDC**：当前状态库仍是权威，系统捕获其变化向下游同步。
- **误用**：Kafka topic、审计日志或 CDC 流不自动成为 Event Sourcing。

### 一致性的多重语义

- **ACID Consistency**：事务保持业务/数据库不变量。
- **CAP Consistency**：分布式操作观察到单一、最新顺序的状态保证。
- **最终一致性**：更新停止后副本最终收敛；不等于固定时间。
- **Read-your-writes**：调用者能看到自己已完成的写入。
- **要求**：按具体操作写契约，不用 CP/AP 标签单独选库。

### 交付语义与处理效果

- **At-most-once / At-least-once**：描述明确边界内的投递尝试及丢失/重复可能。
- **Exactly-once**：必须声明保证范围；broker 语义不自动覆盖数据库和外部副作用。
- **处理效果**：最终副作用是否只发生一次，需要幂等、去重、原子持久化、状态查询或对账共同保证。

### 幂等性与幂等键

- **含义**：重复提交同一逻辑操作，不产生第一次以外的额外外部效果。
- **完整契约**：稳定操作身份、请求内容绑定、键作用域、结果重放、保留期和原子记录边界。
- **不是**：生成一个 UUID 就自动获得 exactly-once。

### 重试风暴

- **含义**：依赖变慢或失败时，客户端和多层组件的同步/叠加重试继续增加负载，形成正反馈。
- **约束**：只重试暂态且可安全重放的操作；指定唯一主要所有者、总 deadline、上限、退避和 jitter。

### 故障域、冗余与故障转移

- **故障域**：可能共同失败的一组资源、控制面或人为流程。
- **冗余**：提供独立替代能力；只有故障足够独立时才提高可用性。
- **故障转移**：探测、仲裁、切换、fencing 和数据恢复的完整过程。
- **误用**：增加节点或负载均衡器不会自动消除单点。

### RTO 与 RPO

- **RTO**：灾难后可接受的最长恢复时间。
- **RPO**：按时间表达的最大可接受数据损失。
- **边界**：二者是业务目标，Backup/Restore、Warm Standby 或 Hot Multi-site 等拓扑名称不是保证；必须通过恢复演练测量。

### 监控、可观测性与信号

- **监控**：检查已知条件和阈值。
- **可观测性**：能从系统输出推断内部状态并诊断未知问题。
- **信号**：日志/事件、trace 和 metrics 各回答不同问题；安装三套工具不自动得到可观测性。

### 缓存 miss 放大

- **含义**：同时过期、冷启动、热键失效、不存在键穿透或缓存整体不可用，使相关 miss 将负载集中回源。
- **共同问题**：缓存的正常收益依赖一条未受控的退化路径。
- **验证**：冷启动、全失效、hot key 和源站限流演练，而不是只测稳定命中率。

## 来源冲突
