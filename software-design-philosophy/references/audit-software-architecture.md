# 架构审计

固定范围，从公开入口、调用方、状态权威、组合及运行配置追踪实际关系；目录图不能代替它们。按真实任务取样，说明未检查范围。

## 什么算架构问题

架构规定单元、知识与不变量归属、协作契约及生命周期责任；单元内可独立替换且不改变这些约定的机制是实现细节。私有布局成为公共零拷贝契约后也可能属于架构，严重的局部错误则未必是。

确认架构问题须有三项：**具体结构对象、导致一类任务受损的因果机制、能切断因果链的结构调整**。证据可来自调用代码、历史、运行或明确标注的变更推演；行数、环或 import 数量不够。完整修复仅改一个值、条件或配置时通常是局部问题。

先分类再评严重度；高危局部问题仍应提示。同一事实如另有结构因果链，分别说明。缺测试、基准、指令文件或一次模型误改不能单独证明架构缺陷。

## 直接发现问题

广义审计沿所选工作流检查下列相关边界，不必先猜问题名或读完专题。每项检查都允许得到确认问题、候选/缺证据、值得保留或不适用，而非强制找错。

| 观察对象 | 检查与反证 |
|---|---|
| 变化与知识 | 一项高频或高后果修改需要谁同步解释哪些规则？契约是否可达？多份独立解释与同源生成不同；相似代码也可有独立语义 |
| 模块深度与组合 | 完整调用是否仍需重复配对、循环、转换、状态顺序或恢复？共同变化的责任是否分散、独立责任是否绑死？薄边界可能有真实隔离收益，源码模块不必拆服务 |
| 接口与契约 | 创建到结果、失败、清理是否完整？调用者是否依赖隐含单位、所有权、副作用、顺序或持久化？高级入口是否复用身份/权限/生命周期并能重新汇入？常见逃逸可能是原语缺口，必要决策不能隐藏 |
| 错误与恢复 | 恢复信息归谁？是否重复 catch、包装或重试，把未知当失败或成功？聚合错误不能丢掉调用者决策所需的语义；次数配置错误不必是架构问题 |
| 生命周期 | 启动、受理、关闭、清理、扩容副作用和恢复是否责任冲突？多角色同进程不自动有错，须证明发布、权限或故障责任有冲突 |
| 演化 | 临时旁路是否成为永久权威？难逆建议是否有结构不同的可行替代？未决定方案的风险不自动是当前缺陷 |
| 性能 | 数据布局、转换、复制、跨边界调用和资源竞争如何影响性能目标？已有证据支持哪些成本或瓶颈，哪些仍需测量？可以建议基线、优化方向及结构调整，但不把性能标签或缺基线当成实际性能结论 |
| 异步与事件（存在时） | 受理能否可靠进入调度，终态、取消与恢复由谁裁决？事件 schema、顺序、重放和副作用由谁治理？202、队列和发布订阅不保证完成、解耦或恰好一次业务效果 |
| 多份状态（存在时） | 谁可写、谁是权威？新鲜度、写后读、失效、重建及分区不变量由谁维护？读多不自动加缓存，数据大不自动分片，满足约束的单一权威可保留 |
| 故障与交付（存在时） | deadline、重试、队列上限和背压是否一致？可选依赖能否阻断核心能力？副本是否共享故障域？新旧版本、切换和数据恢复归谁？节点数不证明可用性，应用回滚不等于数据回滚 |

对所抽样关键模块给出深度判断与依据，即使健康也不只说“没有问题”。判断需要实际调用负担，不能仅凭方法数；证据不足保留为候选。

## 建议与报告

每项发现交代位置/边界、任务证据、结构因果链、影响、最小调整及验证。按频率、后果和证据强度排序，沿用项目等级，不编精确加权分数。

报告保留范围、主要发现、值得保留、关键证据缺口与改进顺序，不强制逐行出表。范围外高风险简短提示，不声称做过安全、性能或运维专项。已有约束可以否决“更整洁”的建议，例如有证据的共置与批量视图不能无据换成网络或强制复制。

需要设计具体改进时，再按入口路由读取相应专题；审计判据负责发现，不替代专题契约。
