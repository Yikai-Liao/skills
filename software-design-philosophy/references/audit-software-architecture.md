# 架构审计

用于评估当前仓库或子系统的结构。先固定评价范围，从公开入口、调用方、状态所有者、组合位置及运行/部署配置还原实际关系；目录图不能代替它们。按真实任务取样，说明尚未检查的范围。

## 架构与实现的边界

**架构决定**规定选定范围内有哪些单元、谁拥有哪些知识与不变量、如何协作，以及跨边界契约和生命周期/质量责任如何分配。**实现细节**是在既定单元内可独立替换、无需其他参与方改变上述约定的机制。底层布局一旦成为公共零拷贝契约也可能是架构；严重的局部错误仍可能只是实现问题。

将发现称为“已确认架构问题”需要同时说明：

1. **结构对象**：具体边界、知识权威、依赖、接口或责任分配。
2. **系统性机制**：它如何让一类真实任务联动修改、反复重建知识、漏改或承担运行/协调失败。调用代码、历史、运行证据或具体变更推演可以支撑；仅有静态形状不够。
3. **结构改进**：改变哪项权威、契约或责任能切断因果链。若完整修复只需改一个值、条件或配置，通常属于局部问题。

先判断类别，再评严重度。高危局部问题可比架构问题更紧急，应明确提示；同一事实有独立的结构因果链时，分别陈述。不要把“缺少测试/基准”本身升格为架构问题。

## 直接用于发现的判据

广义审计用下列判据检查所选工作流及重要边界，不需要先猜出问题名。它们提供发现所需的问题与反证；专题文件只在需要进一步设计或验证时读取。按系统实际形态选择相关对象，不要求逐文件检查或为不相关领域生成报告。

| 观察对象 | 直接检查什么 | 反证或继续调查的条件 |
|---|---|---|
| 真实变更与核心概念 | 重放一项高频或高后果变更：哪些位置必须改、维护者必须知道什么、哪些依赖容易遗漏？系统最重要的规则由谁决定？ | 改动多不等于泄露；分别拥有不同语义的变化可能合理。没有历史时标为推演。 |
| 公共模块深度 | 沿一条常见或高影响完整工作流，比较接口负担与隐藏能力：调用者是否仍需配对操作、重复循环/转换、维护内部顺序或读实现？ | 不能以方法少证明深，也不能以薄适配器证明浅。没有调用方证据时保留为候选。 |
| 知识归属与依赖 | 同一格式、状态机、规则是否有多个独立解释者？谁能修改权威？一次规则变化会向何处传播？ | 共享 schema 生成的表示、稳定协议和语义独立的相似代码不是自动缺陷。 |
| 组合与拆分 | 总需一起理解或变化的责任是否被拆开？独立变化的责任是否被绑定？透传边界提供了什么隔离？ | 计入共同发布、权限、通信和故障成本；源码模块不天然对应网络服务。 |
| 接口覆盖与逃逸 | 常见路径能否从创建走到结果、失败和清理？高级入口由谁需要，是否复用公共身份、权限和生命周期，能否重新汇入？ | 调用者必要的决策不应隐藏；反复依赖同一逃逸可能是核心原语缺口。 |
| 契约与读者理解 | 成功、状态、单位、所有权、副作用、顺序和失败是否能从接口明确得知？真实修改者会从哪个入口开始？ | 名称难懂可能是局部问题；只有跨边界隐藏约定或责任错误才是架构发现。 |
| 错误与恢复 | 哪层拥有恢复所需信息？是否重复 catch/包装/重试，或将未知结果当作失败/成功？ | 对外错误可以聚合，必要诊断和调用者决策不能丢；重试次数错误本身可能只是配置问题。 |
| 生命周期与隔离 | 谁负责启动、受理、关闭、清理、扩容副作用和恢复？一次外部依赖失败会阻断哪些核心能力？ | 同进程多角色不自动有错；先证明发布、权限、启动或故障责任确实冲突。 |
| 演化与候选 | 临时旁路是否成为永久权威？重大难逆建议是否比较过改变状态归属或边界的可行替代？ | 不为每个小修复凑方案；尚未决定的高代价方案属于风险，不一定是当前缺陷。 |
| 性能契约 | 哪些批量、布局、静态分派或共置决定有目标与测量支持？建议会否增加复制、往返或破坏时限？ | “高性能”定位不能批准裸内部对象图；没有当前基线时限定结论，不擅自展开性能工程。 |
| 异步与事件（存在时） | 受理是否可靠进入调度？任务如何查终态、取消和恢复？事件的 schema、顺序、重放与副作用由谁治理？ | 202、消息队列或发布订阅不自动提供完成、解耦或恰好一次业务效果。 |
| 多份状态（存在时） | 谁是权威、谁可写？缓存/副本的新鲜度、写后读、失效和重建由谁保证？分区是否破坏局部性或不变量？ | 读多不自动需要缓存，数据大不自动需要分片；当前满足约束的单一权威可保留。 |
| 部分失败与交付（存在时） | deadline、重试、队列上限与背压是否跨边界一致？副本是否共用故障域？新旧版本、切换与数据恢复由谁负责？ | 节点数量不等于可用性，应用回滚不等于数据回滚；缺 dashboard 本身不是架构问题。 |

为相关检查区分**确认问题、候选/证据缺口、值得保留、不适用**。这里的区别用于控制结论强度，不是要求输出十三张表或每行一个问题。广义审计应给出所抽样关键模块的深度判断及依据，即使结论是健康，也不能只说“没有问题”。

## 从发现到建议

用一条可追踪记录组织每项发现：`位置/边界 → 任务证据 → 结构因果链 → 影响 → 最小结构调整 → 验证`。优先级考虑任务频率、失败影响和证据强度，沿用项目等级，不伪造精确加权分数或另建一套强制评级。

- 知识/边界问题进一步设计时读 [模块与知识边界](design-module-boundaries.md)。
- 工作流/接口缺口读 [深模块与接口](design-deep-modules.md)；错误责任独立成题时读 [错误处理边界](reduce-exception-surface.md)。
- 跨进程、异步和复制状态的发现需要具体结构方案时读 [系统边界与失败契约](design-system-boundaries.md)。
- 难逆方案与迁移读 [方案比较与演化](evolve-design-strategically.md)。性能决定确需测量裁决时读 [性能约束下的设计](design-measured-critical-paths.md)。

报告保留范围、主要发现、值得保留的结构、关键证据缺口和改进顺序即可。范围外高风险另作简短提示；不声称完成了未执行的安全、性能或运维专项。已有约束也可能否决“更整洁”的建议：例如共置与批量视图已支撑关键性能时，不应无证据地换成网络调用或强制复制。
