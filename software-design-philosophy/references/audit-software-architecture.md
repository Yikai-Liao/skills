# 架构审计

固定范围，沿真实调用、修改或恢复路径追踪入口、使用者、状态与运行配置。结合实际定义和用法核对实体、基数、权威与时态，说明未检查范围。

## 什么算架构问题

架构规定单元、知识与不变量归属、协作契约及生命周期责任；单元内可独立替换且不改变这些约定的机制是实现细节。私有布局成为公共零拷贝契约后也可能属于架构，严重的局部错误则未必是。

确认架构问题须有三项：**具体结构对象、导致一类任务受损的因果机制、能切断因果链的结构调整**。证据可来自调用代码、历史、运行或明确标注的变更推演；行数、环或 import 数量不够。完整修复仅改一个值、条件或配置时通常是局部问题。

先分类再评严重度，高危局部问题仍提示；同一事实另有结构因果链时分别说明。验证缺口与架构因果链分别评价。

## 度量审查

优先复用项目已有报告，按当前问题做相称测量，核对源码版本和统计口径。覆盖率缺失或测量失败记为未知；行、分支和指令覆盖率分别解释，需要比较时使用同一口径。

`CRAP = CC² × (1 − c)³ + CC`，其中 `CC` 是圈复杂度，`c` 是 0 到 1 的覆盖率比例。用它定位复杂且覆盖薄弱的函数、安排审查重点，沿用项目有效关注线。覆盖率为 100% 时仍有 `CRAP = CC`；超线后按真实维护任务判断结构与验证收益，允许有依据地保留完整算法。

覆盖率高还须核对关键边界、失败和状态转换的断言，必要时采用[定向变异检查](evolve-design-strategically.md#验证行为)。度量信号支持定位，架构结论仍须有结构对象、受损任务与因果链。

## 直接发现问题

沿所选任务检查相关边界，结论可为问题、候选/缺证据、值得保留或不适用。

| 观察对象 | 检查与反证 |
|---|---|
| 变化与知识 | 一项高频或高后果修改需要谁同步解释哪些规则？契约是否可达？结构相似度达到项目关注线时，核对是否在独立解释同一规则及共享后的协调成本；多份独立解释与同源生成不同，相似代码也可有独立语义 |
| 模块与接口 | 创建到结果、失败和清理是否有归属？输入在哪里成为有效表示，其约束如何保持？调用者还需哪些配对、转换、顺序与恢复？共同责任是否分散、独立责任是否绑死？单位、所有权、权限和提交语义不能隐去；高级入口能否回到公共资源治理，常见逃逸是否反映原语缺口 |
| 错误与恢复 | 恢复信息归谁？是否重复 catch、包装或重试，把未知当失败或成功？聚合错误不能丢掉调用者决策所需的语义；次数配置错误不必是架构问题 |
| 生命周期 | 启动、受理、关闭、清理、扩容副作用和恢复是否责任冲突？多角色同进程不自动有错，须证明发布、权限或故障责任有冲突 |
| 演化 | 临时旁路是否成为永久权威？难逆建议是否有结构不同的可行替代？未决定方案的风险不自动是当前缺陷 |
| 性能 | 布局、转换、复制、跨边界调用和资源竞争怎样影响目标？中间态、scratch 与失效载荷何时同时驻留？区分可推导工作量与待测瓶颈，可以建议基线和结构调整，不从性能标签或缺基线推出性能结论 |
| 异步与事件（存在时） | 受理能否可靠进入调度，终态、取消与恢复由谁裁决？事件 schema、顺序、重放和副作用由谁治理？202、队列和发布订阅不保证完成、解耦或恰好一次业务效果 |
| 共享或多份状态（存在时） | 哪些状态确需共享可变，独立状态能否分离？谁可写、谁是权威？新鲜度、写后读、失效、重建及分区不变量由谁维护？读多不自动加缓存，数据大不自动分片，满足约束的单一权威可保留 |
| 故障与交付（存在时） | deadline、重试、队列上限和背压是否一致？可选依赖能否阻断核心能力？副本是否共享故障域？新旧版本、切换和数据恢复归谁？节点数不证明可用性，应用回滚不等于数据回滚 |

## 建议与报告

发现交代边界、任务证据、因果链、影响、相称调整与验证；按频率、后果和证据强度排序，沿用项目等级。关键健康模块说明实际调用负担和隔离收益，证据不足保留为候选。

报告保留范围、主要发现、值得保留、证据缺口与改进顺序。建议满足已有共置、批量、兼容等约束，范围外高风险简短提示。

设计具体改进时读取对应专题，核对其契约与代价。
