## 1. 定位

当用户要求评估当前仓库的架构设计，并报告“当前问题、风险、推荐改进”时使用本工作流。

本页负责固定审计范围、筛选架构问题、组织证据和报告；它不新增一套架构理论，也不作为额外的原子方法。真实任务造成的变更放大、认知负荷和未知依赖是共同评价尺度；再按候选问题的证据联合能回答它的方法，例如复杂性诊断、信息泄露、组合或拆分、重要性设计、深模块、性能设计或战略式演化。方法之间没有主/辅层级，使用某个方法也不授权把报告扩张成该方法对应的另一项专项任务。

核心纪律是：

> 先判断问题属于什么类别，再判断它有多严重。

一个局部安全缺陷可以是上线阻断项，但仅凭“严重”不能证明它是架构问题。反过来，某条高频变更路径的依赖方向失控可能没有即时事故，却仍是高优先级架构问题。

## 2. 来源依据与推导边界

### 《软件设计的哲学（第二版）》提供的主尺度

- **第 2 章**：复杂性体现为变更放大、认知负荷和未知的未知；总体复杂性还要按开发者接触时间加权。架构审计因此不能按代码行数、层数或缺陷严重度直接排名。
- **第 5 章**：模块应隐藏设计知识；同一决定反映在多个模块中会产生信息泄露。架构问题需要指向知识归属和跨边界依赖，而不是只指出一个错误值。
- **第 9 章**：合并或拆分要看能否降低整个系统的复杂性、减少依赖并形成更深接口，不能按文件大小、目录标题或固定分层教条裁决。
- **第 20 章**：日常设计要自然高效，但增加复杂性的优化需要目标和前后测量；真正热点应围绕理想关键路径组织，把特殊情况移到慢路径。`Buffer` 通过外部块避免复制，也明确暴露了所有权约束。
- **第 21 章**：重要事项应影响结构，不重要事项应尽量隐藏；把太多事情都宣布为“最重要”本身会增加认知负荷。审计必须克制主表范围。

### 《架构整洁之道》补充的检查维度

- **第 1、15、16 章**：架构质量体现在系统长期满足用例、运行、开发和部署需要所需的人力；单体、服务或进程数量本身不是结论。
- **第 17、22 章**：边界用源码依赖方向保护策略，跨边界数据不应把数据库或框架表示带入内层。依赖方向和边界数据可作为结构证据。
- **第 25 章**：边界既有收益也有成本；应观察真实摩擦并比较建立边界与忽略边界的成本，不为假想未来自动增加组件或服务。

### 《架构设计的本质》补充的纵向设计链与横向系统关系

- 来源以性质、受众、利益、目标、需求、抽象、设计和方向描述纵向链条；本技能将前四项操作化为风险、主体、价值和目标评价基线，再把需求转成业务、概念和系统模型。架构不能脱离这些上游判据自行追求技术形式。
- 架构是对系统实体及其关系的抽象描述，用稳定构造指导后续建设。本技能在分析时让架构衔接“上游目标与模型”和“下游具体建设”，但不把它固定为单一阶段：业务、产品、技术和实施阶段都可能产生架构决定，验证也会反向修正它。
- 横向上同时观察实体、功能、关系、边界、外部环境和预期效果；纵向链回答目标如何变成构造，横向分析回答当前有哪些稳定对象及关系。架构图与技术选型只是表达或落地手段，不等于架构本身。

### 本工作流的推导规则

这些来源都没有规定“架构报告必须把安全 P0 单列”这样的报告格式。本页将上述尺度转成可执行的分类门禁：架构主表只容纳有结构对象、复杂性机制和结构性改进方向的发现。安全、配置、运维、测试等问题仍可升级，但放入相邻风险轨道。

这是一条审计纪律，不是否认设计与架构的连续性，也不表示安全或运行后果“不重要”。同一证据可以同时支撑一个安全发现和一个架构发现，但必须分别写出因果链，不能用一个标签替代另一个。

### 架构设计与实现细节的操作性定义

三份材料提供不同但可拼合的边界：

- 用户提供的《架构设计的本质》同时给出纵向设计链和横向系统关系：先从性质、受众、利益和目标建立判据，再把需求建模；各阶段都可通过抽象系统实体及其关系形成架构，并由建设与验证反馈校正。
- 《架构整洁之道》第 1 章指出高层结构与低层设计是连续体，没有天然物理分界；第 15 章把架构描述为组件划分、排列与通信形成的系统形状。
- 《软件设计的哲学》第 2、5、21 章提供裁决尺度：看真实任务的复杂性、知识由谁拥有，以及什么重要到足以影响系统结构。

因此，本技能不按“业务/技术”“高层/低层”“类/组件”或文件目录划线，而在选定系统范围后做操作性分类。

#### 在系统设计链条中的位置

| 层次 | 回答的问题 | 产物 | 与架构的关系 |
|---|---|---|---|
| 性质、受众、利益、目标 | 风险是什么、谁受影响、价值与定位是什么 | 评价基线 | 架构的上游判据，不是架构结论 |
| 需求与建模 | 系统必须支持哪些完整用例、实体、功能和约束 | 业务/概念/系统模型 | 架构的输入；不能直接把每个用例变成组件 |
| 抽象与架构 | 哪些实体和责任构成系统，它们的稳定关系、边界、契约与质量责任如何安排 | 系统构造规则 | 规定“哪些部分存在、如何协作、谁拥有决定” |
| 建设与实现 | 每个既定单元内部用什么机制完成责任 | 可运行实现 | 受架构约束，但会通过实现反馈校正架构 |
| 验证 | 系统是否满足价值、目标、用例和约束 | 任务演练、测试、测量 | 验证或推翻架构，不以测试反向生成架构 |

这不是阶段归属表或瀑布流程。业务、产品、技术和实施阶段都可能产生架构决定，实现与验证也可以迫使上游模型和架构重做；区别在于每一项决定当前回答的是“系统怎样构成”，还是“某个已定单元怎样完成工作”。

#### 明确定义

- **架构设计**：承接上游价值、目标、模型和真实约束，对选定范围内的系统实体、责任及其关系进行抽象；决定单元划分、知识与不变量的权威、外部边界、跨边界契约和依赖方向，以及运行、部署、生命周期和关键质量约束如何分配。它规定系统的构造规则，并约束一族后续实现。
- **系统实体**：选定范围内参与系统行为的稳定对象，包括参与者、模块、进程、数据、设备和外部系统。它不是 DDD Entity、代码类或数据库表的同义词；只有对系统行为和关系具有稳定意义时才进入架构模型。
- **实现细节**：在架构已经给定的某个单元、责任与契约内部，选择具体算法、私有表示、控制流、库调用、局部配置或错误处理来完成工作。只要该选择能独立替换，而不改变其他单元必须遵守的契约、知识、依赖、生命周期、部署协作或质量责任，它就是相对于该边界的实现细节。
- **架构问题**：某个架构决定或缺失的架构决定，通过错误的边界、关系、知识归属、接口或责任分配，系统性增加一类真实任务的理解、修改、运行或协调成本。它不是“架构代码里的任何缺陷”，也不是“影响很大的任何问题”。
- **实现问题**：错误主要位于一个既定责任内部，完整修复不要求重设系统构造规则。它可以极其严重，也可以阻断上线，但严重度不改变类别。

#### 可执行边界

在审计范围 `S` 内，一项决定满足以下全部条件时，归为**架构决定**：

1. **结构对象**：它决定 `S` 的实体/责任划分、稳定关系、外部边界、跨边界契约，或关键质量与生命周期责任的分配；
2. **下游约束**：它约束多个可独立变化的参与方，决定选定范围内多个内部部分的组织方式，约束一个单元与外部调用者/运行环境之间的一族实现，或承载无法局部替换的系统级不变量/质量保证；
3. **协调替换**：改变它必须让多个参与方协调修改，或会改变系统级用例、质量保证、部署/运行方式与长期演化成本。

一项决定满足以下全部条件时，归为**实现细节**：

1. 它位于 `S` 中一个已确定的责任和契约内部；
2. 其他单元和调用者不需要知道该决定；
3. 它可被局部替换和验证，不改变跨边界契约、知识权威、依赖方向、生命周期、部署协作或系统级质量分配。

若两组条件都不能充分证明，标记为“架构候选/边界未定”，通过真实变更、替换演练或运行证据补齐，不强行二分。

#### 相对性与升降级

- 架构范围必须先声明。同一个存储布局在应用级审计中可能是库内细节，在该库自身审计中却可能决定公共数据模型和调用者契约。
- 延迟、吞吐、可用性、安全或兼容目标本身是上游约束；决定哪些单元、边界和运行角色分别承担这些保证，才是架构设计。
- 技术选型、数据库、框架、协议、算法、数据结构都不是固定类别。选择本身只有在决定系统构造或跨边界保证时才是架构；被深模块隐藏且可局部替换后，就降为实现细节。
- 不是所有 public API 都是架构。只有它约束独立参与方、一族实现或长期兼容承诺，并具有跨边界替换半径时，才进入架构分类。
- 私有细节一旦泄露到多个调用者、成为兼容承诺或要求跨模块同步，就升级为架构候选；真正的问题是泄露后的知识与关系，不是该技术听起来“底层”。
- 架构决定被封装为稳定边界后，其内部机制可以继续演化为细节；这正是深模块降低复杂性的方式。
- 性能逃逸遵循同一规则：私有布局或所有权策略通常是细节；若已测关键路径要求调用者控制它，它就成为需要明确契约和责任的架构接口，而不是自动被禁止的泄露。

#### 快速裁决四问

1. **系统构造**：这项决定改变“哪些部分存在、如何关联、谁拥有决定”，还是只改变一个既定部分内部怎么做？
2. **替换半径**：替换时，是否必须重组范围内多个部分，改变其他参与方的契约/知识/生命周期/部署协作，或改变无法局部兑现的系统级保证？
3. **任务跨度**：它是否影响一类完整变更、理解、部署或运行任务，或者影响低频但系统级高后果、难逆的任务，而不只是一次孤立局部故障？
4. **完整修复**：修复必须重设边界/关系/权威/接口/责任，还是局部改算法、条件、配置或调用？

前三问指向系统构造且第四问要求结构变化时，进入架构准入；否则归实现或相邻专项。四问只负责分类，真正定为架构问题仍须通过第 4 节三道门。

## 3. 把真实约束和压力变成评价基线

架构判据必须相对于真实任务。先按用户原话记录本次结果、交付范围和授权动作，再从用户说明、README、公开 API、基准、发布记录、部署文件、调用示例、提交历史和运行行为整理其余输入。若根因或权重尚不清楚，再读取 `diagnose-software-complexity.md` 执行完整诊断；若候选已明确，只使用共同评价尺度，不把诊断强制成固定前置流程：

| 输入 | 性质：背景/约束/证据 | 来源 | 受影响的使用者/任务 | 频率与失败后果 | 对架构判断的作用 |
|---|---|---|---|---|---|

约束或压力可以来自功能变更、理解成本、运行性能、安全后果、资源上限、兼容承诺、部署方式或外部协议，但必须有真实来源。performance-first、安全优先或维持单体通常是背景/约束。每个架构发现都要回指用户目标与这张表；无法回指的原则只能作为待验证假设。

这不是给仓库贴“业务系统/基础库”的固定标签。例如：

- 对普通 CRUD 后台，数据库对象穿透到业务规则通常需要重点检查；
- 对以零拷贝和跨语言批处理为核心价值的原生库，所有权、生命周期、连续内存、批量边界和跨语言往返成本可能就是公共契约中的重要信息；
- 对嵌入式系统，硬件能力需要在适配边界隔离，但实时性和资源上限不能被当作可隐藏的普通细节；
- 对公开 SDK，兼容性和长尾扩展可能让一个窄高级入口优于强行封死能力。

不能因某种结构不符合常见 Web 分层就定罪，也不能因仓库追求性能就放弃封装。应判断真实压力落在哪里、哪些信息能由模块自己处理、哪些决定确实只有调用者掌握。

若性能是明确背景或硬约束，用 `design-measured-critical-paths.md` 和 `design-deep-modules.md` 的相关判据检查架构发现与建议是否误伤关键路径、是否把合理逃逸误判为泄露。除非用户要求性能优化/架构性能调优，或某项架构裁决确实依赖性能测量，否则不要展开热点清单、benchmark 体系和优化路线图。

### 设计细则覆盖合同

面向整个仓库或子系统的架构审计，不能等候选问题已经被发现后才选择判据。那会形成循环：没有深模块判据就看不见浅接口，没有信息泄露判据就看不见知识归属错误。先用下表对高权重任务和边界做覆盖筛查，再对命中项读取完整 reference 深挖。

这里的“覆盖”是观察义务，不是固定执行顺序、统一封装标准或“每项都必须找出问题”。每项必须得到四种结果之一：**已确认问题、候选/证据缺口、有证据支持的健康设计、不适用并说明原因**。不能用“未发现”代替检查证据。

| 设计细则 | 审计时必须观察什么 | 何时读取完整方法 |
|---|---|---|
| 真实任务中的复杂性 | 代表性任务是否出现变更放大、认知负荷、未知依赖；成本落在谁身上并有多高权重 | 根因或排序不清时读取 `diagnose-software-complexity.md` |
| 重要性与系统中心 | 仓库使命、主体、价值、核心用例和质量约束是否真正影响结构；重要决定是否有明确所有者 | 中心概念不清、配置/参数膨胀或底层穿透时读取 `design-around-what-matters.md` |
| **模块深度与接口负担** | 高权重边界的接口负担是否显著小于其隐藏的能力与知识；完整工作流、默认路径、调用者胶水和逃逸是否合理 | **每次此类仓库/子系统广义审计都完整读取 `design-deep-modules.md`，并显式报告结论** |
| 知识归属与信息泄露 | 格式、状态机、规则、不变量或调用顺序是否被多个位置共同解释 | 一项知识有多个解释者或变更点时读取 `audit-information-leakage.md` |
| 单元划分与依赖关系 | 边界是否围绕共享知识和变化轴；拆分增加的接口/导航/发布成本与组合增加的耦合成本如何 | 出现透传层、循环、边界争议或共同变化时读取 `decide-combine-or-split.md` |
| 契约与失败责任 | 跨边界语义、状态、副作用、不变量、错误和恢复责任是否能由调用者正确理解，是否迫使各层重复处理 | 契约难以简短完整表达时读取 `design-abstractions-comment-first.md`；错误面扩散时读取 `reduce-exception-surface.md` |
| 结构可发现性 | 新读者能否从入口、名称、可见性和依赖方向找到能力、权威位置与正确修改点 | 多次误解、跳转或猜错时读取 `make-code-obvious-to-readers.md` |
| 运行与生命周期责任 | 启动、关闭、部署、扩缩容、故障隔离和运行副作用由谁拥有，是否被不必要地绑定 | 在本工作流内检查；只有真实运行压力成立才形成问题 |
| 改进的演化与候选质量 | 建议是否指向目标结构、能否以最小完整切口落地、是否比较过结构上不同的候选 | 受交付约束时读取 `evolve-design-strategically.md`；重大或难逆改进只有一个方案时读取 `design-it-twice.md` |
| 性能、兼容与其他硬约束 | 约束是否修正接口、边界和逃逸判断；建议是否会破坏已证实的关键路径或兼容承诺 | 架构裁决依赖测量，或用户明确要求性能设计时读取 `design-measured-critical-paths.md` |

这些细则从属于架构评价，但它们发现的每个现象不一定都是架构问题。例如难懂名称、某个异常分支或一个浅适配器通常仍是实现层发现；只有现象通过第 4 节的结构对象、系统性机制和结构改进三道门，才进入架构主表。

### 广义架构审计中的模块深度强制检查

“模块”按知识与责任边界识别，不等于每个类、文件或函数。优先检查公共 API、跨模块契约、高频工作流入口、高扇入能力、插件/扩展边界，以及承担生命周期或关键质量保证的单元；仓库过大时说明取样范围，不假装全量覆盖。

对每个被抽样边界至少记录：

| 边界及其知识/责任 | 接口负担 | 隐藏的能力与复杂性 | 完整工作流与调用者胶水 | 逃逸及重新汇入 | 结论与证据强度 |
|---|---|---|---|---|---|

- **接口负担**包括调用者必须学习的方法、概念、参数、状态、顺序、返回/错误语义和重复胶水，不按公开方法数量机械评分。
- **隐藏能力**包括模块统一承担的知识、不变量、自动决策、生命周期和复杂机制；少量接口只有在确实消除了调用者负担时才“深”。
- **工作流覆盖**按真实频率和失败影响加权。常见或高影响任务若必须重复拼装、成对调用、转换、探测实现或阅读内部代码，是浅接口候选。
- **逃逸**要检查谁掌握必要决策、是否类型化、是否守住主体不变量、能否重新汇入，以及高频后是否被核心收编；有证据的性能逃逸不得因暴露所有权或布局语义而自动定罪。

结论必须明确：

1. 若接口把模块内部知识和常见工作流成本转嫁给多个调用者，并且修复需要重设边界、权威或跨边界契约，则按三门准入列为架构问题；
2. 若只有静态接口形状、没有工作流或调用方证据，列为候选与最小验证动作；
3. 若有限入口覆盖了高权重工作流、隐藏了关键知识且逃逸受控，列入值得保留的架构；
4. 若对象只是刻意保持简单的适配器、值类型、纯函数或内部辅助层，浅本身不是问题；除非它构成无收益的跨边界负担，否则不要为了“做深”而合并职责。

## 4. 架构问题准入

每个候选发现必须依次通过三个门。缺少任一项时，不得作为已确认架构问题进入主表。

### 门 A：存在明确的结构对象

至少涉及下列一种对象：

1. 系统、模块或进程边界；
2. 源码依赖方向或跨边界数据契约；
3. 设计知识、不变量或决策权的归属；
4. 对外接口的覆盖、深度、默认值或受控逃逸；
5. 启动、关闭、扩缩容、部署或运行副作用的责任划分；
6. 为满足核心用例、开发、运行或部署而形成的系统结构。

单个值、局部缺陷或验证遗漏本身没有通过这一门。

### 门 B：有可复验的系统性机制

至少给出一条从结构到成本或失败的因果链：

- 一项真实修改需要联动多个权威位置；
- 完成常见任务必须跨越不必要的边界并掌握内部知识；
- 依赖隐藏，导致调用方或维护者经常漏改；
- 低层表示反向约束高层用例，变更沿错误方向传播；
- 生命周期责任绑定导致部署、扩缩容、启动或故障隔离互相牵连；
- 有证据的核心用例无法由现有边界稳定支持。

证据强度分为：

- **已观察**：提交历史、事故、调用方代码、运行行为或团队任务直接证明；
- **可复演**：静态依赖与一次具体变更演练共同证明；
- **待验证**：只有原则或形状信号。只能进入“候选与证据缺口”，不能定为主表事实。

### 门 C：改进会改变结构机制

建议应至少改变边界、依赖、知识归属、接口、组合位置或生命周期责任之一，并说明减少哪种复杂性。

如果完整修复只是替换局部值、调整单项配置、修正条件、增加一条验证或升级依赖，通常是相应专项修复，不是架构改进。若同一位置还存在结构问题，应拆成两个发现。

### 准入记录

对每个候选先写一行内部记录：

| 候选 | 门 A：结构对象 | 门 B：系统机制与证据强度 | 门 C：结构改进 | 归类 |
|---|---|---|---|---|
| 单个高风险配置值错误 | 无 | 可直接造成严重后果，但不是结构传播机制 | 修正配置与发布门禁 | 相邻专项 |
| 同一入口策略由每个适配器重复声明 | 策略归属和边界 | 新入口依赖隐藏规则；可用新增入口复演 | 集中默认策略、显式例外 | 架构 + 相邻风险，分写 |

只有归类完成后才能赋予优先级。

## 5. 问题类别与双轨优先级

### 类别先于严重度

候选至少在以下类别中选择主类别：

- **架构**：边界、依赖、知识、接口、组合或生命周期责任；
- **安全/隐私**：身份、权限、秘密、数据暴露、攻击路径；
- **配置/发布**：默认值、环境装配、迁移和发布门禁；
- **运行/可靠性**：容量、恢复、可用性、观测和操作故障；
- **测试/质量**：行为未被验收、测试隔离或工具链缺口；
- **实现正确性**：局部逻辑、异常处理或数据错误；
- **性能**：已有目标和测量支持的运行热点。

允许一个事实拆成不同类别的两个发现；不允许为显得“更架构”而把类别合并。

### 架构轨道

架构主表使用 `A0/A1/A2`，只在已经通过准入的发现之间排序：

- **A0**：结构本身正在广泛阻断核心用例、安全交付、启动/恢复或高频变更，而且没有可行的局部隔离。很少使用。
- **A1**：高频或高影响路径存在已观察/可复演的变更放大、知识泄露、错误依赖方向或责任耦合。
- **A2**：局部或正在形成的结构摩擦，适合随下一次相关变更增量治理；若证据仍弱，应降为候选而不是强行定级。

架构优先级可参考：

`任务频率 × 变更/理解成本 × 失败影响 × 证据可信度`

不要伪造精确分数，也不要因为安全严重度是 P0 就复制成 A0。

### 相邻风险轨道

非架构发现使用项目已有的 `P0/P1/P2` 或等价严重度：

- P0 可以阻断上线；
- P1 需要近期治理；
- P2 可进入计划。

相邻问题可能比全部架构问题更紧急，应明确提醒并给出责任人/处理动作；只是不能把它们写进架构主表。

## 6. 可执行审计步骤

1. **固定用户目标、范围与评价基线**
   - 写明仓库/子系统、时间范围、部署形态、用户要求和本次只读/可修改边界。
   - 原样记录用户目标，再区分背景/倾向、硬约束和证据；完成评价基线，不预设所有仓库都应使用同一种分层或封装。
   - 背景只修正架构判断。若用户没要求性能、安全、测试或实现专项分析，不把它们扩成报告主体。
   - 明确审计的是“实现出来的架构”，不是一般安全、代码质量或测试全量审计。
   - 记录无法访问的运行数据、历史或团队知识。

2. **重放三到五项代表性任务**
   - 至少覆盖一个高频功能变更、一个跨边界修改，以及适用时的启动/部署/故障任务。
   - 对每项记录修改点、必须知道的知识、潜在漏改和边界穿越。
   - 没有历史时，用具体变更演练代替，并标为“可复演”而非“已发生”。

3. **建立候选清单，不急于定级**
   - 来源可以是依赖图、目录、import、接口、配置、生命周期 hook、变更历史、测试和运行行为。
   - 循环构造、跨层引用、基础设施类型穿透或多进程只是信号，需要继续追问结构机制。
   - 完成“设计细则覆盖合同”和模块深度取样，同时记录值得保留的深模块、单一知识源、清晰组合根和稳定边界，避免只罗列缺陷。

4. **逐项执行三门准入**
   - 未通过的高风险问题移到相邻风险表；
   - 证据不足但结构上可疑的内容移到候选与证据缺口；
   - 同一证据有两个因果链时拆分，不混写。

5. **按覆盖结果联合完整方法**
   - 模块深度已是必查项；其余维度按覆盖表中的信号读取复杂性、重要性、信息泄露、组合/拆分、契约、异常面、读者验证、战略演化、候选比较或关键路径方法。
   - 一个方法可以发现问题、约束定罪、设计改进或验证候选；不设置主/辅、数量上限或固定先后。
   - 读取方法不等于复制其完整输出模板，也不授权扩张用户目标；只产生本次架构判断需要的证据和产物。

6. **分轨定级并提出最小结构切口**
   - 先排架构 `A0/A1/A2`，再独立排相邻 `P0/P1/P2`；
   - 建议要命名新的权威、依赖方向、接口、组合位置或生命周期责任；
   - 不默认重写、拆微服务、增加层或建立昂贵边界。

7. **设计验证**
   - 对建议重放原任务，比较修改点、所需知识和漏改风险；
   - 用模块可见性、依赖规则、契约测试、启动 smoke test 或运行演练验证相应边界；
   - 测试用于证明边界，不把“缺少测试”倒推成架构问题。

## 7. 报告契约

默认输出以下结构：

```markdown
# 架构评估报告

## 架构结论
只总结已经通过准入的结构结论；另用一句话提醒最高相邻风险。

## 范围、任务与证据
仓库范围、用户目标、背景/约束/证据表、代表性任务、证据强度、限制。

## 架构设计细则覆盖
逐项给出取样对象、结果、证据强度和命中的完整方法；不适用项说明原因。

## 模块深度与接口负担
按高权重边界给出接口负担、隐藏能力、工作流胶水、逃逸和明确结论；即使没有确认问题也不得省略。

## 值得保留的架构
写清有效边界/权威及其降低的任务成本。

## 架构问题
| ID | 架构优先级 | 结构证据 | 复杂性机制 | 风险 | 推荐改进 | 验证 |

## 架构候选与证据缺口
列出只有静态信号、尚不能定罪的项目及最小验证动作。

## 范围外但需升级的问题
| 类别 | 全局严重度 | 证据 | 风险 | 推荐动作/责任域 |

## 改进顺序
架构演化轨道与即时风险轨道分别排序，说明依赖关系。
```

每个架构发现必须让读者看出：

1. 哪里是结构问题；
2. 它怎样影响真实任务；
3. 为什么建议能切断这条因果链；
4. 用什么证据可以验证或推翻结论。

“违反整洁架构”“耦合严重”“建议解耦”“补测试”都不是完整发现。

## 8. 典型证据如何分类

### 严重局部故障与结构问题

先问直接修复是否只改变一个值、条件、权限、依赖版本或验证项。若是，先进入对应专项轨道。只有还能写出另一条独立因果链，证明边界、策略归属或生命周期责任使同类失败系统性复发时，才另建架构发现；两条因果链分别给证据和严重度。

### 静态拓扑与真实任务

依赖环、跨层引用、聚集度、目录形状和 import 计数只是取样线索。选择一项真实变化，记录它为什么要穿越这些位置、哪些知识必须同步、遗漏能否由结构发现。只有形状信号时列候选；证明变更放大、未知依赖或错误传播方向后才进入主表。

### 入口策略与默认行为

某个入口配置错误首先属于相应功能或安全问题。若每个入口都必须重复声明同一默认策略，新增入口需要记住隐藏规则，才形成“策略没有唯一权威”的架构因果链。建议要重设默认值和例外归属，而不只是修补已知入口。

### 生命周期与部署边界

多个责任位于同一进程、模块或启动阶段不是自动缺陷。只有真实的启动失败、幂等、独立扩缩容、故障隔离、发布节奏或关闭顺序要求被绑定时，才审计责任划分。建议拆分前必须比较新增协议、部署和运维成本。

### 验证缺口

缺少测试、基准或静态规则通常是验证/质量问题。它们可以成为某项已成立架构建议的验收手段，却不能反向生成架构结论。先写需要保护的边界行为，再选择相称的验证机制。

## 9. 性能背景如何影响架构判断

当用户要求架构审计并说明仓库 performance-first 时，性能首先是一项背景/约束，不是自动增加的交付目标。

它对架构审计有三种作用：

1. **修正定罪**：零拷贝视图、引用生命周期、批量接口、编译期结构、跨语言边界或多表示等设计，可能是为了满足已证实的关键路径。不能因它们暴露低层语义或不符合普通业务封装习惯就直接列为架构问题。
2. **约束建议**：建议增加边界、统一表示、引入动态分派、隐藏所有权或改变调用粒度时，必须说明不会增加不可接受的复制、分配、间接跳转和跨语言往返；必要时把 benchmark 作为验收条件。
3. **限定证据强度**：没有性能基线时，不能断言现有逃逸“必须保留”，也不能断言更整洁的候选“性能足够”。将其标为架构建议的验证缺口，不顺势写一份完整性能治理路线。

性能背景本身不会让下列事项通过架构准入：

- 缺少 benchmark suite；
- 某个循环可能较慢；
- 某次转换可能是 O(n)；
- 可以增加 SIMD、缓存、并行或 fast path；
- README 有“快百倍”的声明。

这些可以是性能证据、验证动作或相邻风险。只有它们进一步形成边界、知识归属、接口或依赖的系统性机制，并影响真实修改/理解任务时，才成为架构发现。

如果用户随后明确增加性能设计、性能优化或架构性能裁决，再完整使用 `design-measured-critical-paths.md`，并按问题需要联合其他方法。任务变化来自用户目标，不来自仓库标签、背景描述或审计过程中发现的新线索。

## 10. 失败模式与边界

禁止：

- 先按 P0/P1/P2 排序，再把排在前面的都叫架构问题；
- 把蒸馏方法当成互不相关的可选专题，只在已经看见问题后才读取，导致深模块、知识归属或契约细则根本没有参与候选发现；
- 用“没有发现深模块问题”代替接口负担、隐藏能力、工作流覆盖和逃逸证据；
- 因一个适配器、值类型或纯函数看起来浅，就把它升级为架构问题或强行扩充职责；
- 把安全审计、代码质量审计或测试审计的全部发现倾倒进架构主表；
- 仅凭循环依赖、跨层引用、基础设施类型、目录层级、进程数量或缺少测试定罪；
- 把业务后台常见的分层和封装原则原样套到性能库、系统组件、嵌入式仓库或公共 SDK；
- 因用户提供 performance-first 背景，就把架构报告扩写成 benchmark、热点和 fast path 优化手册；
- 反过来以“高性能”为由批准没有基线、热点、收益复测或不变量契约的裸底层穿透；
- 把“数据库/Web 是细节”误写为安全、数据和运维后果不重要；
- 没有部署/扩缩容证据就建议拆微服务；
- 用层数、端口数或模式数量代替真实任务成本；
- 给每个问题都增加新边界，忽略边界本身的接口和运维成本；
- 把建议写成“解耦、整洁化、补测试”而没有新的责任和验证方式。

以下请求需要其他专项审计而非扩大本工作流：

- 全量漏洞与威胁模型；
- 生产事故止血；
- 数据库查询/事务性能；
- 测试套件充分性；
- 一般代码规范或依赖升级。

若这些问题在架构审计中被发现，保留最小证据并升级到相邻风险表，不假装已经完成专项审计。
