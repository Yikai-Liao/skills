## 使用范围

当问题涉及存储选择、读取热点、复制、分区、缓存、状态/事件权威、并发写、唯一标识或跨系统正确性时使用。先读 [模式选择器](select-system-design-patterns.md)。

不要从数据库类别或产品开始。先建立：

| 维度 | 必须回答 |
|---|---|
| 业务不变量 | 哪些关系任何时刻都不能被破坏 |
| 权威 | 当前状态、事件历史或外部机构中谁说了算 |
| 数据形状 | 规模、键分布、对象大小、关联和增长 |
| 访问模式 | 读写比例、查询形状、范围/点查、峰值和局部性 |
| 时间语义 | read-after-write、最大陈旧度、事件时间和保留 |
| 并发 | 写者数量、冲突率、顺序和重做成本 |
| 失败 | 丢失、重复、部分提交、恢复、备份和对账 |
| 操作能力 | 团队能否部署、迁移、观察、备份和恢复该结构 |

## D01 从简单权威存储开始

普通关系型单库、清晰 schema 和本地事务常是低复杂度基线，但不是教条。只有工作负载或能力边界已经稳定地超出它时，才引入专用存储、复制、缓存或分片。

可能的演化动作包括查询/索引调整、归档、纵向扩容、连接池、预计算、读副本、垂直拆分和水平分片。它们不是固定阶梯；每一步都必须对应当前最主要压力并复测。

数据库选型至少比较事务不变量、主要查询、写入模式、数据规模、schema 演化、尾延迟、备份恢复、运维能力和迁移成本。CAP 标签或“SQL/NoSQL”不能单独裁决。

## D02 索引、预计算与物化视图

### 索引

适合稳定的过滤、排序和连接路径。新增索引会增加写放大、存储和维护；必须用查询计划和代表性数据证明收益。一个缺失索引通常是实现/性能问题，除非索引策略或查询模型已经成为多个模块共同依赖的架构契约。

### 预计算/物化视图

适合读路径重复执行昂贵计算、允许明确的新鲜度窗口，或需要为特定查询形成深读接口。

必须定义：

- 权威输入和刷新触发；
- 全量/增量刷新、失败和落后检测；
- 最大陈旧度与 read-after-write；
- 重建时间、回填和版本迁移；
- 物化结果能否作为临时可丢缓存，还是关键持久状态。

没有真实重复计算或读取压力时，预计算只会制造第二份状态。

## D03 缓存准入

缓存只有同时满足下列条件才进入候选：

1. 已证实重复读取、昂贵计算、外部配额、离线可用性或单位成本等压力；若主张性能收益，必须有目标、基线和热点；
2. 键与工作集有足够局部性，预期复用/命中率可验证；
3. 权威数据明确；
4. 业务接受可说明的陈旧窗口，或能实现需要的失效语义；
5. 缓存 miss、冷启动或整体故障时，源站有受控退化路径；
6. 收益足以支付双份状态、失效、容量和运维成本。

“读多写少”只是候选信号，不足以通过准入。若目标是离线使用，缓存事实上承担本地副本和同步责任，还必须定义冲突、恢复和数据生命周期，不能借“缓存”弱化契约。

## D04 缓存读写模式

| 模式 | 适用条件 | 主要代价/失效 |
|---|---|---|
| Cache-Aside | 应用能识别热点并容忍 miss 后回源 | 应用拥有填充/失效；并发 miss、陈旧窗口 |
| Read-Through | 希望缓存层统一加载权威源 | 缓存适配器变复杂，加载失败语义需明确 |
| Write-Through | 写后缓存必须同步可见 | 写延迟和双写失败处理 |
| Write-Behind/Back | 写吞吐优先且允许持久化窗口 | 缓存成为暂时权威，存在丢失、乱序与恢复责任 |
| Write-Around | 写入不应污染热点工作集 | 首次读 miss，写后读需要契约 |
| Refresh-Ahead | 热点稳定且刷新成本可预测 | 无效刷新、时间同步和新鲜度错误 |

策略名称不是完整设计。每种都要写 source of truth、原子边界、TTL、失效所有者、最大陈旧度和缓存不可用时的行为。

## D05 缓存失效放大

相关 miss 会把缓存问题放大到权威源：

- 大量键同时过期或冷启动；
- 热键过期引发 stampede；
- 不存在键反复穿透；
- 单个 hot key/大 key 集中网络或 CPU；
- 缓存整体不可用，全部流量回源。

可选手段包括 TTL 抖动、single-flight、负缓存/存在性过滤、预热、请求合并、回源限流和分级降载；都需验证副作用。热点“永不过期”不是通用规则，它可能制造永久陈旧和内存治理问题。

验证命中率、p95/p99、陈旧分布、失效速率、内存成本、源站减载，以及缓存全失效/冷启动负载。无可测收益时撤销缓存。

## D06 读副本与新鲜度感知路由

### 准入

主库读资源已经成为瓶颈，且至少部分工作流允许陈旧读取。

### 结构动作

- 普通陈旧容忍读走副本；
- 写后读、高影响读或严格新鲜读走主库；
- 能获取复制位点时，可等待/验证副本追平；
- 路由策略应由知道业务新鲜度的接口表达，而不是按 SQL 动词粗分。

### 契约

定义最大复制延迟、read-after-write、会话单调读、主库回退和副本故障。复制延迟是调用者可见语义，不能藏在“读写分离”实现名后。

### 验证与退出

测 lag 分布、写后立即读、故障切换和主库回退负载。若大多数读都要求最新值，或回退让主库仍越界，副本不是有效解法。

## D07 高可用复制与数据副本

复制可以服务于读取、故障恢复或地理分布，这三者的契约不同。先写：

- 正常状态谁可写、谁可读；
- 同步还是异步确认，提交点覆盖哪些副本；
- 故障探测、选主、fencing 和脑裂处理；
- 重复输出、冲突合并和恢复后的数据校验；
- RPO/RTO 与副本所在故障域。

两个副本只有在故障足够独立、切换可靠且共享依赖不会同时失败时才提高端到端可用性。节点数量不能直接换算可用性。

## D08 分片准入

只有单节点数据量、IOPS、写吞吐、连接、维护窗口或法规隔离已经越界，并且索引、模型调整、归档、升配、副本或缓存等更简单候选不足时才分片。

分片把一个数据问题变成：

- 路由与元数据权威；
- 跨片查询、排序、连接和事务；
- 热点、扩缩、迁移和再平衡；
- 备份、恢复、故障定位和 schema 变更；
- 调用方是否需要知道分片键。

没有当前基线和代表性键分布时，不做分片架构结论。

## D09 分片键与路由算法

先选能表达主要访问局部性、业务所有权和均匀性的键，再选算法：

| 方案 | 主要收益 | 主要风险 |
|---|---|---|
| Range | 范围扫描和相邻数据局部性 | 单调增长、热点范围、迁移不均 |
| Hash | 分布通常较均匀 | 范围查询和业务局部性被打散 |
| Consistent Hash | 节点变化时减少迁移范围 | 虚拟节点、热点键、副本和故障域仍需设计 |
| Directory / Virtual Bucket | 路由灵活、便于迁移和隔离热点 | 元数据权威、额外 hop 和控制面可用性 |
| Geography/Tenant | 合规、所有权或常见查询局部 | 大租户/热点区域不均、跨域操作 |

用真实键分布和查询轨迹模拟 skew、scatter-gather、跨片事务和加减节点。找不到稳定键或跨片操作占主导时，暂停分片或重设数据边界。

路由知识应有唯一权威。多个应用各自解释拓扑会泄露知识；独立中间件可以集中路由，但新增延迟、HA 和控制面成本。用一次拓扑变化演练比较应用内路由与中间件。

## D10 一致性的不同语义

- **ACID Consistency**：事务完成后业务/数据库不变量仍成立；
- **CAP Consistency**：分布式操作观察到单一、最新顺序的状态保证；
- **最终一致性**：更新停止后，各副本最终收敛；它不是固定时间，也不自动提供 read-your-writes；
- **Read-your-writes**：调用者能看到自己已完成的写；
- **单调读/因果一致性**：防止会话看到状态倒退或因果顺序颠倒。

先按具体操作定义需要的保证。CAP 只帮助讨论网络分区时的选择，不能替代正常态延迟、查询、事务、运维和迁移分析。

采用最终一致性前写最大收敛时间、用户可见中间状态、乱序/重复、补偿和人工恢复。无法定义补偿或业务不接受窗口时，不要用“eventual”掩盖未完成的设计。

## D11 当前状态、Event Sourcing 与 CDC

| 结构 | 权威 | 适用压力 | 主要代价 |
|---|---|---|---|
| 当前状态存储 | 最新状态 | 只关心当前值和普通事务 | 历史需另行审计 |
| Event Sourcing | 不可变业务事件序列 | 审计、确定性重放、历史状态和多投影是核心需求 | schema、顺序、重放、副作用和存储增长 |
| CDC | 原状态库仍是权威，捕获其变化 | 遗留库向搜索、缓存、分析或下游渐进同步 | 捕获延迟、删除/事务语义、重复和下游投影 |

CQRS 只表示命令/写模型与查询/读模型分离；它不要求两个数据库，也不蕴含 Event Sourcing。Kafka topic、审计日志或 CDC 流也不会自动成为 event store。

验证从零重建、历史 schema、重复/乱序、回填和新旧消费者。无法回答哪个存储说了算、没有真实重放需求或形成双写双真相时，退回更简单状态模型。

## D12 CQRS、后台同步与最终一致性责任

先决定“谁负责收敛”：

- 事件消费者按事实更新各自投影；
- 后台同步任务定期比较并修正；
- Saga 以业务步骤和补偿推进；
- CQRS 投影从命令侧状态派生。

选择依据是新鲜度、变更频率、补偿可行性和规则所有权。若读写模型相同、一个本地事务足够，CQRS/异步同步只增加双模型。若无人监控 lag 和失败，系统没有“最终”的保证。

## D13 乐观与悲观并发控制

| 选择 | 适用条件 | 失败方式 |
|---|---|---|
| 乐观版本检查 | 冲突少，重做便宜，可向调用者表达冲突 | 热点下重试风暴、用户输入丢失 |
| 悲观锁 | 冲突频繁且重做昂贵，锁可短持有 | 等待、死锁、长事务和资源占用 |
| 单写者/队列化 | 一个稳定所有者可串行维护不变量 | 所有者容量与可用性 |
| 分区所有权 | 冲突可按键/租户局部化 | 迁移、热点和跨区协调 |

先测冲突率、锁等待、重做成本和尾延迟。若并发控制完全封装在一个既定存储边界内且不改变调用者语义，它通常是实现细节；若调用者必须提供版本、处理冲突或遵守租约，它已成为架构契约。

分布式锁不是默认协调器。它可能掩盖错误的数据所有权；租约过期后仍需 fencing 防止旧持有者写入。

## D14 唯一 ID 作为保证向量

ID 进入公共 API、分区键、排序或跨系统关联时，先写：

- 唯一范围和寿命；
- 是否按时间大致有序；
- 位宽、字符集和可索引性；
- 是否可离线/多区域生成；
- 时钟回拨、节点重启和隐私泄露；
- 延迟、吞吐和依赖可用性。

UUID、数据库自增、号段、Snowflake 类方案或集中分配器只是候选。若 ID 只是模块内部 opaque 值且可局部替换，就不要把生成算法架构化。

## D15 对账（Reconciliation）

资金、结算、库存或其他跨外部权威的高后果副作用，即使在线路径设计了幂等，也可能需要独立控制环：

1. 从各权威读取记录并标准化；
2. 以稳定业务标识匹配；
3. 检查笔数、总额和业务不变量；
4. 区分迟到/跨日等暂时差异与永久差异；
5. 自动重试、补偿或升级人工处置；
6. 保留修复审计。

“任何系统都必须对账”不成立。只有多权威、高价值且在线失败不能完全排除时才采用。对账数据若与被检系统共享同一错误来源，也不是独立安全网。

## 存储抽象：Block、File 与 Object

- **Block**让调用者控制布局和随机访问，适合数据库/虚拟机等确需低层控制的系统；调用者承担更多所有权与恢复知识；
- **File**提供命名、层次、共享和顺序字节抽象；
- **Object**以对象/键和元数据换取大规模、耐久和较低成本，通常不适合细粒度原地随机更新。

用实际对象大小、访问形状、共享并发、延迟和恢复验证。不要仅以“性能”暴露更低层接口；若调用者确实必须控制布局，则通过窄而类型化的高级入口表达。

## 审计表

| 数据边界 | 权威与不变量 | 访问/负载证据 | 新鲜度/并发/失败契约 | 当前模式 | 问题/健康/候选/不适用 |
|---|---|---|---|---|---|

### 常见结构问题机制

- 多个模块都能写同一不变量，或分别解释缓存、复制、分片和事件规则；
- 调用者必须知道拓扑、复制 lag、分片位置或事务实现才能完成常见工作流；
- 缓存/投影/事件流与权威状态形成双重真相源；
- 本可局部事务完成的流程被边界强迫进入 Saga、补偿和最终一致性；
- 分片键与业务访问不匹配，结构性制造热点和跨片协调；
- 数据迁移、重建或恢复没有唯一生命周期所有者。

单个慢查询、索引、锁等待或缓存 bug 通常是实现/性能问题。只有责任、契约和知识传播的结构机制成立时才进入架构主表。
