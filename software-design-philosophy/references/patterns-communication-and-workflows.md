## 使用范围

当系统需要在模块、进程、服务、客户端或外部机构之间传递命令、结果、事件或流时使用。先读 [模式选择器](select-system-design-patterns.md)。

先定义通信契约，再选择 HTTP、RPC、队列、事件总线或流平台。产品名不能替代以下语义：

| 维度 | 必须决定 |
|---|---|
| 意图 | 命令、查询、通知、事实事件还是数据流 |
| 方向 | 单向/双向，一对一/一对多，谁能发起连接 |
| 时间 | 调用者何时需要结果，deadline、新鲜度和过期规则 |
| 交付 | 可否丢失、可否重复、确认点和保证覆盖到哪一步 |
| 顺序 | 无序、分区内有序、因果顺序还是全局顺序 |
| 状态 | 谁拥有流程状态、幂等记录、偏移和补偿决定 |
| 流控 | 容量、队列上限、背压、限流、卸载与优先级 |
| 演化 | schema 权威、兼容窗口、未知字段和重放 |
| 故障 | 超时、未知结果、部分完成、恢复和人工介入 |

## C01 同步请求—响应

### 适用压力

调用者必须立即获得结果才能继续，交互短、失败语义清楚，或一致性边界与调用同步完成。

### 结构动作

调用方给出端到端 deadline，服务端在预算内返回成功、业务拒绝或明确失败。RPC、REST、GraphQL 都可实现该模式；它们的契约形态不同，但不会消除网络失败。

### 代价与失效

- 串联多个同步调用会放大尾延迟和可用性依赖；
- 超时只表示调用者停止等待，不证明远端没有提交；
- 重试未知结果可能重复产生副作用；
- 聊天式服务边界让一次工作流了解整个部署图。

### 验证

画端到端 deadline 分配、调用 fan-out 和部分失败矩阵；对有副作用操作测试超时前后断连。若调用者不需要即时结果，比较异步请求—回复；若大量细碎同步调用共享知识，先重新裁边界。

## C02 异步请求—回复（Asynchronous Request-Reply）

### 适用压力

任务显著长于客户端连接期限，突发负载需要隔离，或调用者可以先获得受理状态、之后查询/订阅结果。

### 结构动作

1. 接收命令并持久记录身份、幂等键和受理状态；
2. 返回任务标识、状态入口和取消/过期语义；
3. worker 处理并记录终态；
4. 调用方轮询、订阅或接收回调。

接口必须区分“已受理”“已执行”“结果可见”和“最终失败”，不能把 HTTP 202 当成成功语义的全部。

受理与调度之间不能形成静默丢任务窗口：要么在同一可靠边界记录“待调度”，由可重入 dispatcher 扫描；要么使用能证明原子提交/发布的机制。进度必须表达真实阶段或完成量，总量未知时明确不可确定，不能伪造百分比。`cancel_requested` 只表示收到取消意图，不等于 `cancelled`；完成与取消竞态由唯一状态机裁决。终态应不可逆，结果保留期、过期语义和访问授权属于接口。

### 代价与失效

新增任务状态机、存储、清理、重复执行、取消竞态、结果保留和授权责任。若工作必须立即原子返回，异步化只把一致性问题推给调用者。

### 验证

测试重复提交、受理后未调度、worker 在产物/终态提交前后崩溃、长期排队、取消与完成竞态、任务过期、未授权结果访问和调用方断线恢复；观察队列深度、最老任务年龄和端到端完成时间。

## C03 工作队列与竞争消费者（Queue / Competing Consumers）

### 适用压力

- 生产速率有峰值，消费者需要按自身节奏处理；
- 工作可分割并由多个消费者并行；
- 调用者允许延迟，且每个任务由一个逻辑消费者完成。

### 结构动作

队列拥有积压、投递和可见性；消费者拥有处理幂等和结果。并发消费者通常不保证全局顺序，只能在明确分区键内保序。

### 代价与失效

- 无界队列把过载变成延迟和存储事故；
- poison message 可阻塞分区或造成无限重试；
- 任务完成但确认失败会重复投递；
- 扩消费者若下游容量不变，只会移动瓶颈；
- 优先队列可能饿死低优先级任务。

### 验证

定义容量、最老消息年龄、过期、死信/隔离、重驱动和降载策略；在峰值、消费者宕机、重复与乱序下演练恢复。要求全局顺序或单事务原子性时，不用竞争消费者掩盖约束。

## C04 发布—订阅（Publish/Subscribe）

### 适用压力

一个已经发生的事实需要被多个相互独立的下游消费，发布者不应知道消费者清单，且消费者可以接受异步收敛。

### 结构动作

事件由最了解事实语义的边界拥有；订阅者各自维护处理状态。事件名称、schema、版本、顺序、重复、重放和数据生命周期是公共契约。

### 代价与失效

“空间解耦”不等于无耦合。消费者仍依赖事件语义、时间顺序和发布政策；全局工作流可能分散到多个订阅者，调试和恢复困难。将命令伪装成事件会隐藏真正的控制者。

### 验证

执行新增消费者、事件字段变化、重复、乱序、迟到、重放和消费者长期离线演练。若一条规则变化要求修改所有订阅者，检查共享知识是否应有唯一权威。

## C05 可重放日志与流（Partitioned Log / Stream）

### 适用压力

需要高吞吐顺序追加、多个消费进度、保留与重放，或同一事实流支持实时与离线处理。

### 结构动作

事件按稳定键分区；分区内维护顺序，消费者维护偏移。保留期、压缩、重放、分区扩缩和 schema 演化属于架构契约。服务层与持久层分离、分层存储只在分区迁移或长期保留成本有证据时进入。

### 代价与失效

- 全局顺序会限制伸缩；
- 错误分区键产生热点或破坏需要的局部性；
- 重放会重新触发副作用；
- 扩分区可能改变键到分区的映射和顺序假设；
- 日志不能自动成为业务真相源。

### 验证

测键分布、分区 lag、扩缩和保留成本；从零重放投影并验证外部副作用被隔离。只需要一次性任务分发时，普通队列可能更简单。

## C06 更新通道：轮询、Webhook、SSE 与 WebSocket

| 候选 | 适用条件 | 关键代价 |
|---|---|---|
| 短轮询 | 基础设施受限、更新不频繁、延迟要求宽松 | 空请求与陈旧窗口 |
| 长轮询 | 需要近实时但无法维持专用推送协议 | 长连接、超时重建 |
| Webhook | 服务间可达，接收方能暴露稳定端点 | 鉴权、重试、重复、回放和端点不可达 |
| SSE | 浏览器侧单向连续更新 | 单向、重连和事件补发 |
| WebSocket | 高频双向交互或服务端主动推送 | 连接状态、路由、背压、重连与容量治理 |

选择前写清连接发起者、单向/双向、最大新鲜度、更新频率和漏通知后的恢复。WebSocket 不是业务消息语义；Webhook 返回 2xx 也不一定等于下游业务完成。

验证连接数、空轮询比例、端到端延迟、断线重连、游标续传和重复通知。没有实时决策需求时，使用满足期限的更简单通道。

## C07 编排与协同（Orchestration / Choreography）

### 编排

流程状态与步骤规则由编排器拥有。适合需要全局可见性、统一超时、错误和补偿的长工作流。

- **收益**：规则和状态集中，新增步骤、恢复与审计较明显；
- **代价**：额外 hop、容量上限、单一控制点和领域知识过度集中；
- **失效**：编排器变成所有服务的业务上帝对象，或每个服务只是贫血执行器。

### 协同

参与者通过事件推进流程，不设唯一中央控制者。适合局部规则确实分别由自治参与者拥有、吞吐和去中心化更重要的场景。

- **收益**：参与者自治，直接发布事实；
- **代价**：全局规则、错误恢复和可观测性容易散落；
- **失效**：增加一步需要修改多个服务，没有人能解释完整状态机。

### 裁决

用一次“新增步骤”、一次“中途失败补偿”和一次“追踪具体实例”演练比较。核心不是中央还是分散，而是流程规则的真实知识所有者在哪里，以及集中容量成本是否可接受。

## C08 Saga

Saga 处理跨多个自治事务边界的长工作流。每个本地事务提交后，通过后续步骤或补偿动作推进。

### 准入

- 无法或不应使用一个本地事务；
- 中间状态可被业务看见或隔离；
- 每个已提交副作用有可定义的补偿、对账或人工恢复；
- 业务接受最终完成而非即时全局原子性。

### 失效

- 单个数据库事务被无端拆成 Saga；
- 把补偿误当回滚：外部邮件、资金、实物等副作用未必可逆；
- 未定义乱序、重复、补偿失败和人工卡住状态；
- 编排/协同只是实现选择，核心不变量无人拥有。

### 验证

对每一步在“提交前、提交后、确认前、补偿中”注入失败；验证重复命令、并发流程、长期离线和人工恢复。不能补偿且中间状态不可接受时，重设边界而不是强上 Saga。

## C09 Claim Check 与优先队列

- **Claim Check**：消息只传稳定引用，大载荷放在独立存储。适合 broker 大小/吞吐受限且载荷生命周期可治理。必须处理引用权限、TTL、原子发布、孤儿清理和载荷不可用；小消息不要为此增加一次存储 hop。
- **优先队列**：不同任务有真实 SLO 或失败后果时分级。必须定义容量预留、老化/公平和低优先级最大等待；不能用优先级掩盖总容量不足。

二者通常是局部模式。只有载荷存储、优先策略和生命周期成为多个参与方的公共契约时，才上升为架构决定。

## C10 交付语义

| 语义 | 适用条件 | 调用者必须知道 |
|---|---|---|
| At-most-once | 少量丢失可接受，重复更有害 | 失败时可能永不再投递 |
| At-least-once | 可用幂等或去重承受重复 | 同一消息可能多次到达 |
| “Exactly-once” | 只有在明确边界内能同时证明不丢和不重时使用 | 保证覆盖到 broker、处理、数据库还是最终外部副作用 |

端到端“恰好一次”不能由 broker 配置自动兑现。对于不可逆副作用，通常要把目标分解为：

1. 有界重试和持久记录提供至少一次尝试；
2. 稳定幂等键、原子检查与结果重放提供至多一次业务效果；
3. 外部系统不支持相同幂等边界时，保留状态机、查询未知结果或独立对账。

幂等契约必须写明键的业务作用域、生成者、保留期、并发原子性和重复请求返回什么。

## C11 超时、重试与结果未知

先分类错误：

- **永久失败**：输入、权限、约束或确定性业务拒绝，不重试；
- **暂态失败**：短暂网络/依赖故障，可在总 deadline 内有限退避；
- **过载**：盲目重试会放大事故，应限流、卸载、尊重 Retry-After 或熔断；
- **结果未知**：调用超时但远端可能提交，先查询状态或使用幂等重放。

重试必须同时具备总 deadline、次数上限、指数退避与 jitter，并明确放在哪一层。多层各自重试会乘法放大负载。HTTP 状态码只是线索，不能替代领域失败语义。

## C12 外部副作用的崩溃安全协议

支付、库存扣减、邮件或第三方资源创建等副作用位于本地事务之外时，broker 的事务语义不能覆盖最终效果。至少设计：

1. **先持久化意图**：在外调前记录稳定业务操作 ID、下游幂等键、请求摘要和当前状态；
2. **使用同一身份执行**：超时或恢复后只能查询或以同一键重放，不能生成新键盲重试；
3. **三态结果**：区分确定成功、确定未执行/拒绝和 `UNKNOWN`；网络超时不能直接改成普通失败；
4. **持久收敛**：对 `UNKNOWN` 查询下游状态；查询仍不能判定时进入独立对账或人工处置；
5. **原子发布结果**：本地终态与待发布结果记录在同一可靠边界提交，之后再确认输入消息；恢复可重发结果，消费者仍按幂等处理；
6. **保留期匹配**：本地重试/重放窗口不能超过下游幂等记录的有效范围；无法证明时停止自动重试。

逐点在“外调前、下游执行后响应前、响应后本地提交前、本地提交后发布/ack 前”注入崩溃。验证同一业务意图的最终效果、内部状态和外部权威能够收敛。补偿动作是新的业务副作用，不是假装数据库回滚。

## C13 Schema 与事件治理

消息格式是设计知识：

- 指定唯一 schema 权威和兼容政策；
- 区分可选字段新增、语义变化、删除和重命名；
- 验证旧读新、新闻旧、历史重放和未知字段；
- 明确事件时间、处理时间、去重标识、分区键和敏感数据生命周期；
- SDK、schema registry 和平台工具可以集中机制，但不能让平台团队独占领域语义。

“用了 Avro/Protobuf/JSON Schema”不证明兼容。格式选择可为实现细节；跨团队版本承诺、回放和语义所有权是架构。

### 常见已确认问题机制

- 事件语义、流程状态或重试政策被多个参与者重复解释；
- 异步接口让调用者承担隐藏状态机，常见工作流必须自行轮询和拼装；
- 队列无界或没有过期/背压，使局部过载扩散为全系统延迟；
- 同步 fan-out 让一个核心用例继承多个服务的尾延迟和可用性；
- 所谓 exactly-once 只覆盖 broker，却被调用者当成最终副作用保证；
- 协同流程没有唯一可解释的全局不变量，真实变更反复漏改。

这些现象仍需通过架构准入。单个重试次数、一个消息处理 bug 或一次 poison message 通常属于实现/运行问题，除非责任和策略的结构分配使它系统性复发。
