## 使用范围

当问题涉及外部依赖、部分失败、过载、冗余、故障转移、扩缩容、发布、恢复或灾备时使用。先读 [模式选择器](select-system-design-patterns.md)。

先把质量口号变成预算：

| 目标 | 可执行表达 |
|---|---|
| 延迟 | 代表性工作流的 p50/p95/p99/p999 与端到端 deadline |
| 吞吐 | 峰均负载、突发形状、完成率和资源上限 |
| 可用性 | 哪些能力、哪些窗口、错误预算和降级后仍保留什么 |
| 正确性 | 哪些不变量在失败/恢复时仍必须成立 |
| 恢复 | RTO、RPO、积压清空时间和人工介入界限 |
| 成本 | 正常、峰值、备用和恢复时的单位成本 |

行业默认的“几个 9”、通用超时或典型 RTO/RPO 只能帮助提问，不能成为当前系统目标。

## 先建故障与过载模型

至少枚举：

- 依赖慢、拒绝、结果未知、返回错误或完全不可达；
- 进程崩溃、重启、半开连接、网络分区和时钟异常；
- CPU、内存、线程、连接、队列、磁盘或下游配额饱和；
- 单节点、机架、可用区、区域、控制面和人为共同故障；
- 数据损坏、复制落后、恢复失败和版本不兼容；
- 流量突发、热点键、重试风暴和缓存/队列放大。

为每个失败写检测者、决策者、隔离边界、用户可见语义和恢复责任。没有失败模型时，不要叠加韧性模式。

## R01 Timeout

Timeout 限制等待，不会取消远端副作用，也不会证明远端失败。

- 从用户端到下游分配端到端 deadline，保留传输、排队、处理和返回预算；
- 连接、读取、写入和整体请求可以有不同预算；
- 上游剩余时间必须随调用传播，不能每一层重新获得完整超时；
- 超时后结果未知的写操作要查询状态、幂等重放或进入对账。

验证慢依赖、半开连接和临近 deadline。复制固定数值到所有调用会制造同步失败和无意义等待。

## R02 Retry、Backoff 与 Jitter

只对暂态失败或可安全重放的结果未知操作重试：

- 指定唯一主要重试所有者；
- 设置端到端 deadline、次数/时间预算；
- 指数退避并加 jitter，避免客户端同步；
- 有副作用操作先定义幂等键和结果重放；
- 过载、永久错误或预算耗尽时停止；
- 尊重服务端限流和 Retry-After。

多层重试会乘法放大请求。通过故障实验观察入站流量、尾延迟和重复副作用；重试不能改善成功率或使依赖更饱和时撤销。

## R03 Circuit Breaker

### 适用压力

依赖持续失败/变慢时，继续调用会耗尽本地资源，且系统存在安全 fallback、缓存结果、降级或快速失败路径。

### 契约

定义失败统计窗口、打开条件、冷却、半开探测、隔离粒度和 fallback 语义。熔断器保护调用者资源，不修复依赖；fallback 不能伪造关键成功。

### 失效

- 共享全局熔断器让一个租户/端点拖累全部流量；
- 本地重试触发熔断，熔断又让上游重试；
- 半开探测同步涌入；
- 没有可接受降级时，熔断只改变错误速度。

验证持续失败、慢响应、半开恢复和多个实例同时恢复。

## R04 Rate Limiting、Load Shedding 与 Backpressure

三者作用不同：

- **Rate limiting**在入口按身份、租户、资源或成本限制接受速率；
- **Load shedding**在系统已接近饱和时优先拒绝低价值工作，保护核心能力；
- **Backpressure**让生产者看到下游容量并减速/暂停；
- **有界队列**把容量和最长等待显式化，队列满必须拒绝、降级或转移。

先定义公平、优先级、突发额度、拒绝语义和客户端行为。无界缓冲不是背压，只是延迟过载。调用方忽略信号继续重试时，需要契约与入口共同治理。

验证峰值、热点租户、下游变慢、队列满和恢复清积压；只看平均 QPS 会错过突发。

## R05 Bulkhead

按租户、依赖、工作流、线程/连接池或资源类别隔离容量，使一个失败域不能耗尽全部系统。

准入取决于可识别的故障传播路径。隔舱会降低资源共享效率、增加容量规划和优先级反转；隔得过细也会制造大量池和配置。

在一个分区饱和时验证其他核心工作流仍满足目标；若故障实际共享同一数据库/控制面，表面资源池不能提供隔离。

## R06 Graceful Degradation 与 Let-it-Crash

- **优雅降级**：依赖失败或过载时保留高价值、可正确提供的能力，明确隐藏、延迟或拒绝哪些功能；
- **Let-it-crash/监督重启**：状态可重建、失败局部且 supervisor 能安全恢复时，让组件快速失败而非带病运行。

不能降级正确性、安全和不可逆副作用。重启前必须知道状态是否丢失、请求是否重复、崩溃是否会循环。每个 fallback 都要有用户可见契约和恢复验证。

## R07 故障探测与健康信号

探测器回答的知识强度不同：

- 进程是否响应心跳；
- 服务能否完成关键依赖；
- 网络路径是否双向可达；
- 节点是否适合接新流量；
- 多数派是否能安全决定成员状态。

超时只产生“怀疑”，不是节点已死的证明。检测越快通常误报越多；网络可能不对称。自动故障转移还需选主、仲裁和 fencing，不能只靠心跳。

分别设计 liveness、readiness 和业务健康，避免 readiness 因非关键依赖抖动导致全体摘除。注入拥塞、丢包、慢节点和分区，记录检测时延与误报。

## R08 冗余与高可用拓扑

| 拓扑 | 适用压力 | 主要代价/风险 |
|---|---|---|
| 单主 + 备份 | 写入所有权要简单，允许切换窗口 | 备用利用率、切换和数据落后 |
| 主写 + 读副本 | 读扩展且部分读取允许陈旧 | lag、写后读、主库仍为写单点 |
| Active-Passive | 需要较快恢复但不需双点写 | 容量预留、切流演练 |
| Active-Active/多主 | 多区域写可用或吞吐收益已证明 | 冲突、脑裂、去重、全局路由 |
| Leaderless/Quorum | 接受可调读写 quorum 和冲突修复 | 读修复、版本、热点与尾延迟 |

冗余只有在故障独立、健康判断正确、切换可执行、数据语义明确时才提高端到端可用性。共享数据库、电源、区域、DNS、身份或控制面会产生共同故障。

验证单节点、单区、控制面、网络分区和恢复后的数据完整性。没有写冲突规则时，双活不是高可用方案。

## R09 Load Balancing 与 Service Discovery

负载均衡器按健康、容量、局部性、会话和成本分发流量；服务发现维护可用端点。它们可能集中策略，也可能成为控制面和数据面关键依赖。

选择前回答：

- 请求是否无状态，还是需要会话/数据局部性；
- 采用轮询、最少连接、加权、哈希还是延迟感知；
- 健康信号是否能反映真实服务能力；
- 端点变化、连接排空和重试怎样处理；
- 多层 LB/Gateway 是否重复决策。

“加负载均衡”不能消除后端单点或共享瓶颈。验证热点、慢实例、摘除、扩缩和连接排空。

## R10 伸缩方式

### 纵向与横向

- **纵向**成本低、事务简单，但受单机和维护上限限制；
- **横向**增加容量/故障隔离，但要求状态、路由、并发和重新平衡契约。

先定位 CPU、内存、I/O、锁、网络、连接还是外部配额瓶颈。增加线程或实例可能加剧竞争。

### 无状态与有状态

无状态服务表示请求不依赖特定实例先前保存的会话状态，系统仍然拥有状态。它便于重路由和横向扩展，但会把一致性、延迟和可用性压力转移到外部存储。

有状态实例在低延迟、局部缓存、实时连接或专用计算中可以合理；必须明确分片、黏性、迁移、恢复和副本。不要把有状态本身叫反模式。

### 并发与并行

并发组织多个等待中的任务，适合 I/O 等待和响应性；并行同时执行计算，适合 CPU 热点。先 profile blocked time、CPU、队列和上下文切换；开更多线程不等于提高吞吐。

### 批处理、流处理与混合

用业务新鲜度/决策期限选择：

- batch 以较高延迟换吞吐和成本效率；
- stream 以状态、乱序、重放和运维成本换低延迟；
- 混合可由流先产出、批次校正。

若下游不会在实时结果到达时行动，或 batch 已满足窗口，不要流式化。

## R11 Serverless、长驻服务与共置

Serverless/FaaS 适合事件驱动、弹性突发、短任务和按使用付费；长驻进程适合稳定高负载、长连接、低延迟、本地状态或可预测资源。

成本必须包含状态转换、冷启动、网络/对象存储中间传输、调用次数、最低常驻容量和运维。逻辑组件可以保持模块化却共置在一个进程；共置也可在未来重新分离。

用真实调用量、数据大小、端到端延迟和单位任务成本比较。不能从“云原生”推出 serverless，也不能从一个公司案例推出单体部署。

## R12 发布拓扑

| 模式 | 适用条件 | 前置能力与风险 |
|---|---|---|
| Recreate | 允许停机、环境低风险 | 最简单；有明确回滚产物 |
| Rolling | 新旧版本可共存，容量允许逐批替换 | 混跑、schema/协议兼容、回滚窗口 |
| Canary | 需要用小流量验证安全/性能 | 分群、可观测门禁、自动停止/回滚 |
| Blue-Green | 需快速切换且可承担双环境 | 状态/schema 兼容、切流和成本 |
| Shadow | 需真实流量证据但不能影响用户 | 副作用抑制、敏感数据和结果比较 |
| A/B | 比较产品行为或体验 | 不是发布安全模式，需实验统计与分群 |

选择维度是允许停机、爆炸半径、所需证据、回滚速度、额外容量和状态兼容。没有自动成功判据时，Canary 只是把故障变慢；Shadow 若产生真实副作用必须停止。

对不可逆 schema/数据迁移，先设计 expand/contract、双读/写窗口、回填和降级；部署拓扑不能替代数据回滚。

## R13 灾备

由业务 RTO/RPO 和成本选择：

| 形态 | 成本 | 恢复特征 |
|---|---|---|
| Backup/Restore | 最低 | 恢复最慢，必须验证备份可用 |
| Pilot Light | 保留核心数据/控制能力 | 恢复时扩出应用面 |
| Warm Standby | 常驻缩小环境 | 较快扩容与切流 |
| Hot Multi-site | 最高 | 最快切换，一致性和相关故障最复杂 |

灾备范围必须包含身份、密钥、网络、DNS、依赖、数据和操作流程，不能只复制应用。定期真实恢复和切流，记录实际 RTO/RPO；拓扑名称不是保证。

## R14 可观测性作为验证面

可观测性不是安装日志、指标和 trace 三套工具，而是能回答当前设计的故障和性能问题：

- metrics 展示延迟、流量、错误、饱和、队列、lag 和预算消耗；
- trace 说明端到端路径、fan-out、重试和瓶颈；
- logs/events 记录离散决策、状态转换和失败上下文；
- 关联标识能从告警定位到具体工作流；
- 遥测不泄露秘密，也不因高基数/采样压垮系统。

从一个 SLO 告警演练到根因和恢复。缺少观测通常是验证/运行问题；只有诊断责任、跨边界上下文或遥测契约的结构分配失当时才是架构问题。

## 组合韧性模式的纪律

不要把 Timeout、Retry、Circuit Breaker、Rate Limit、Bulkhead、Queue 和 Cache 全部无条件叠加。先建立：

| 失败/过载 | 传播路径 | 决策者 | 最少机制 | 用户语义 | 验证 |
|---|---|---|---|---|---|

检查相互作用：

- timeout 是否小于上游剩余 deadline；
- retry 是否计入容量，是否被熔断器再次放大；
- queue 是否有界，背压能否传回生产者；
- cache/fallback 是否满足正确性和陈旧度；
- bulkhead 是否隔离了真实共享资源；
- 自动恢复是否与故障探测、fencing 和幂等兼容；
- 降级结束后积压和数据怎样收敛。

删除没有独立故障模型、没有可测收益或无法说明恢复责任的机制。

## 审计表

| 核心工作流 | SLO/失败后果 | 失败与过载传播 | 已有模式 | 恢复/降级/验证 | 结论 |
|---|---|---|---|---|---|

### 常见结构问题机制

- 每一层各自 timeout/retry，缺少端到端预算与唯一策略所有者；
- 无界队列、缓存 miss 或重试把局部过载放大到共享依赖；
- 副本处于同一故障域，却被当作可用性保证；
- API、worker、bootstrap 或迁移的故障/扩缩责任被无证据地绑定或拆散；
- 发布和数据 schema 无兼容/回滚契约，多个团队共同承担未知顺序；
- 可用性、RTO/RPO 或降级语义只存在口号，没有责任和演练。

单次配置错误、某个 timeout 数值、缺少 dashboard 或一次发布失败通常属于实现/运行/交付问题。只有策略、边界、生命周期和跨方契约的结构机制成立时才进入架构主表。
