## R — 原文

> 如果阅读你代码的人说它不是易理解的，那么它就不是易理解的，无论它对你来说多么清晰。
>
> — John Ousterhout，第 18 章

---

## I — 方法论骨架

易理解不是作者的主观感受，而是读者能否快速形成正确预期。
错误猜测、停顿、反复跳转和额外搜索，都是重要信息不明显的证据。
修复顺序首先是通过更好的抽象、数据类型和消除特殊情况，减少读者必须知道的内容。
其次复用项目已有的名称、布局、接口和不变量，让熟悉外观对应熟悉行为。
最后用准确名称、接口契约和必要实现说明补足仍不能隐藏的信息。
同一概念要有唯一称呼，不同概念即使相近也要显式区分。
低层一致性可由格式化、静态检查、访问控制和编译器强制，避免靠记忆。
每轮修改都要让未参与设计的人重读；若他仍猜错，就继续改设计而不是解释读者。

## A1 — 书中的应用

### 案例 1：Sprite 的 `block` 歧义

- **问题**：`block` 同时表示文件逻辑块和磁盘物理块，读者自然把两者当作同一概念。
- **方法论的使用**：作者从读者的错误预期追到含糊名称和隐藏转换，主张为两类块使用可区分名称。
- **结论**：名称必须精确到足以表达影响正确性的差异。
- **结果**：原歧义曾造成六个月数据损坏排查，说明命名不是表面风格问题。

### 案例 2：自动检查行终止符

- **问题**：跨平台行终止符不一致依赖开发者记忆，提交后产生无意义差异和工具问题。
- **方法论的使用**：作者将约定写入提交前自动检查，而不是反复口头提醒。
- **结论**：能机器执行的一致性不应由人脑维护。
- **结果**：违规在进入代码库前被阻止，读者看到的文件保持统一。

### 辅助案例 3：让架构“尖叫”业务用途

- **问题**：《架构整洁之道》第 21、34 章指出，顶层目录常只暴露 `controllers/services/repositories` 或框架名，新读者看不出系统在做什么。
- **方法论的使用**：按业务用例/组件命名公开入口，隐藏实现类，并用包或模块访问控制阻止绕过入口。
- **结论**：代码结构应先表达领域和可执行用例，再表达交付框架。
- **结果**：读者能从顶层找到“订单”“目录”等能力，编译器同时维护设计意图。

## A2 — 触发场景

### 用户会在什么情境下需要这个方法？

1. 新成员看完代码后对行为、状态或修改位置作出错误判断。
2. 同一词在不同模块含义不同，或同一概念有多个近义名称。
3. 返回通用 tuple、字典或布尔值，读者必须记住位置和隐含语义。
4. 回调、事件、线程或配置驱动控制流没有明显入口。
5. 项目同时保留两套约定，代码外观不能可靠预测行为。
6. 团队已明确领域核心与用例，但顶层结构只显示框架层，使读者仍找不到这些概念。

### 语言信号

- “这段代码为什么这么难读？”
- “我以为这个名字是另一个意思。”
- “不看实现根本不知道这个返回值是什么。”
- “新人总是改错地方。”
- “怎么让项目结构一眼看出业务？”

### 与相邻方法 的区分

- 与 `diagnose-software-complexity` 的区别：本方法 专注读者形成预期的路径；诊断方法 还处理修改放大和未知依赖。
- 与 `design-abstractions-comment-first` 的区别：后者在实现前写接口契约；本方法 覆盖实现、命名、一致性、结构和读者验证。
- 与 `design-around-what-matters` 的区别：后者决定哪些概念值得突出；本方法 决定如何让这些概念被读者正确识别。

## E — 可执行步骤

1. **定义读者任务**
   - 选择一次真实任务：解释行为、定位修改点、判断返回值、跟踪控制流或添加相邻用例。
   - 选一名未参与当前设计的目标读者。
   - 若任务是让目录表达领域，先要求团队写出已经选定的核心概念和用例；若尚不能回答“什么值得突出”，转到 `design-around-what-matters`，不在本步骤替架构选择中心。
   - **完成标准**：任务有明确正确答案和合理时间范围。

2. **进行无提示阅读**
   - 让读者边读边说出预期，记录猜错、停顿、跨文件跳转、搜索词和需要口头解释之处。
   - 作者只观察，不为代码辩护。
   - **完成标准**：形成“所需信息—当前位置—为何不明显”的清单。

3. **先通过设计减少信息**
   - 用具名类型替代 tuple/裸字典，用不变量消除状态组合，用直接调用替代不必要间接层。
   - 把共同机制藏进模块，删除读者无需承担的循环、配对调用和特殊情况。
   - **完成标准**：读者完成任务所需概念数和跳转数下降。

4. **统一概念与约定**
   - 为同一概念选择唯一名称；为不同概念使用明显不同的词。
   - 查找项目已有命名、错误、生命周期和布局约定；没有新证据时沿用。
   - 若必须迁移约定，统一替换并删除旧痕迹，不能长期双轨。
   - **完成标准**：相同外观可可靠预测相同行为。

5. **补足不能隐藏的信息**
   - 名称包含关键单位、方向、所有权或状态；参数和返回值使用明确类型。
   - 对间接控制流写明谁、何时、在哪个线程调用；对接口写明约束和副作用。
   - **完成标准**：读者不需猜测影响正确性的含义。

6. **让结构表达领域与边界**
   - 用已经验证的用例、领域或能力命名顶层入口，技术框架留在外层实现；本步骤负责表达已选中心，不负责凭目录结构发明中心。
   - 仅公开真正入口；内部类型用包/模块可见性隐藏，防止读者走进错误路径。
   - **完成标准**：新读者从目录和公开接口能指出系统的主要能力与扩展位置。

7. **自动执行低层一致性**
   - 使用格式化、lint、类型检查、架构测试和编译器可见性阻止可机械检测的偏差。
   - **完成标准**：约定违反会在本地或持续集成中失败。

8. **重新盲读**
   - 让原读者或另一位读者重复同一任务，不提供额外说明。
   - **完成标准**：能快速给出正确解释和修改位置，且没有新增高成本误导。
   - **判停条件**：若只能通过加长注释让人理解，返回步骤 3 检查抽象；若领域本身复杂，则保留必要复杂性并提供结构化说明。

## B — 边界

### 不要在以下情况使用此 方法

- 只是更换个人偏好的命名或格式，读者任务没有改善证据。
- 团队尚不知道哪些概念、政策或能力真正重要：先使用 `design-around-what-matters` 选择中心，再回来表达。
- 专业领域概念本身复杂且精确，不能为了“通俗”改成含义更弱的词。
- 安全或形式正确性要求显式复杂契约，易读性不能压过可验证性。

### 作者在书中警告的失败模式

- 宽泛名称、同名异义和长度过短导致关键信息消失。
- 通用 Pair/tuple、类型不一致和事件驱动流程迫使读者记住隐含规则。
- 有“更好的想法”就引入第二套约定，使熟悉外观不再预测行为。
- 作者以自己熟悉代码为证据，忽略评审者的真实困惑。
- 只加注释解释复杂代码，而不先减少复杂性。

### 作者的盲点 / 时代局限

- 多语言团队、生成代码和大型 monorepo 的读者群差异更大，需要角色化阅读任务。
- 动态追踪、IDE 导航和类型工具能改善可发现性，但也可能掩盖源码结构问题。
- “架构尖叫业务”来自辅助材料，适合作为结构检查，不应强迫所有技术库伪装成业务应用。

### 容易混淆的邻近方法论

- 易理解不是短代码；更多显式类型或说明可能降低认知负荷。
- 一致性不是拒绝改进；只有新证据足够且能完成统一迁移时才改变约定。
