## R — 原文

> 在设计模块时，应专注于执行每个任务所需的知识，而不是任务的执行顺序。
>
> — John Ousterhout，第 5 章

## I — 方法论骨架

深模块不是“大类”，而是以较低的学习和调用成本提供较强功能、隐藏较多设计知识。
它从已经存在的真实任务出发，先找完成这些任务共同依赖的知识和决定，再据此划边界。
核心接口优先统一长期稳定的不变量，例如对象身份、生命周期、权限、错误、等待、状态一致性与可观测性，而不强求所有对象拥有相同行为。
接口不应逐一复制当前按钮、页面或业务动作，而应把它们归约成少量能自然覆盖一类用途的原语。
“有限”不靠主观确信保证；要把常见、重要和长尾的完整工作流逐项映射到候选接口，并观察调用者胶水。
覆盖率必须按真实频率和影响加权：常见路径应直接、明显、有合理默认值，安全关键路径即使低频也不能遗漏。
有限接口不能覆盖所有事情；缺口应按知识归属分别进入核心、上层组合、专用实现/适配层或高级入口。
只有调用者掌握模块无法推断的重要信息时，才允许显式逃逸；这也包括已测得关键路径中必须由调用者控制的所有权、生命周期、数据布局、批量边界或硬件能力。逃逸可以增加专用动词或类型化性能能力，但不能随意重造身份、生命周期、权限、错误与可观测体系。
逃逸要按频率、深度、局部性、重新汇入能力和生态分叉成本治理；一旦成为常见路径，就应重新归约进核心。
设计时必须主动询问是否需要独立测试/Agent 调试面；只有设计者明确要求后，才通过稳定 CLI/API 和限权令牌实现，并与生产公共入口严格隔离。
信息泄露、配置表膨胀、万能模块和隐藏重要信息，都是停止扩展并重新划界的信号。
最终产物不是一张 API 清单，而是一条由用例、知识、原语、覆盖证据和逃逸治理组成的闭环。

## A1 — 书中的应用

### 案例 1：Unix 与 Java 文件 I/O 的深浅对照

- **问题**：文件 I/O 要处理打开、读写、随机访问、权限、缓冲和序列化；调用者不应了解每个实现细节。
- **方法论的使用**：Unix 用文件描述符统一资源引用、生命周期、权限和等待，用 `read/write` 覆盖常见数据面，再以 `lseek`、socket 专用操作等类型化能力补充差异。用户补充材料进一步指出：专用操作仍应复用主体资源模型；`ioctl` 一类无类型出口是逃逸失控的反例。Java 的流装饰器则让调用者组装多个对象并主动记住缓冲。
- **结论**：好的有限接口不强求覆盖全部动词，而是覆盖稳定共同协议和多数完整工作流；逃逸只扩展领域语义，不能轻易推翻主体不变量。
- **结果**：Unix 基础接口在实现长期变化中保持稳定，并能把重复的特殊需求提升为 `poll/epoll` 等公共能力；Java 方案带来更多对象、异常样板和漏配缓冲的风险。

### 案例 2：文本编辑器把专用动作归约为范围式原语

- **问题**：退格、删除键、删除选区、复制等界面动作容易演化成一串专用方法。
- **方法论的使用**：作者把动作还原为对文本位置和范围的操作，用通用范围式接口覆盖多种编辑行为；当前界面的差异留在上层组合。
- **结论**：原语应围绕被操作的基本对象和语义，而不是围绕某个按钮命名。
- **结果**：方法数量减少，接口更通用，同时没有为了未知未来制造万能框架。

### 案例 3：从设备驱动到按上层需求塑形的 HAL

- **问题**：主书中的设备驱动要隐藏具体设备命令；《架构整洁之道》第 29 章又展示上层业务被 GPIO、闪存字节、处理器和 RTOS 污染。
- **方法论的使用**：具体设备在统一接口后实现；HAL 不照抄寄存器，而按上层需要提供 `Indicate_LowBattery`、保存/读取名称值等语义。
- **结论**：专用实现属于共同接口之后，接口由调用者真正需要的能力塑形；硬件细节不应反向决定核心 API。
- **结果**：业务逻辑可脱离目标硬件测试，硬件或操作系统变化被限制在 HAL/OSAL 实现中。

## A2 — 触发场景

### 用户会在什么情境下需要这个方法？

1. 正在设计新的类、服务、SDK、协议或公共 API，不知道接口该多专用还是多通用。
2. 一个模块的方法随业务动作增长，出现 `deleteBackward`、`deleteForward`、`deleteSelection` 一类平行接口。
3. 接口看起来很小，但调用者到处写循环、转换、状态拼装、成对调用或重复异常处理。
4. 为覆盖少数高级客户，公共构造器和配置对象不断增加开关。
5. 团队争论某个需求应进入核心、留在业务层、做成实现插件，还是开放底层能力。
6. 普通用户需要简单默认值，同时专家用户确实掌握模块无法知道的策略、安全或持久化信息。
7. 正在完成模块方案，但设计者尚未说明是否需要无需改代码的独立测试/Agent 调试面。
8. 性能是产品契约，测量表明通用路径无法满足目标，需要设计零拷贝、批量、view/span 或硬件专用能力。

### 语言信号

- “怎么设计一个真正的深模块？”
- “这几个有限接口怎么证明能覆盖大部分需求？”
- “没覆盖的特殊需求应该怎么逃逸？”
- “接口越来越多，能不能归约成几个原语？”
- “这个高级配置该放核心 API、适配层还是业务层？”
- “为什么调用方用了这个库还要写这么多胶水？”
- “是否需要给测试或 Agent 单独留一个可鉴权的调试入口？”

### 与相邻方法 的区分

- 与 `audit-information-leakage` 的区别：本方法 从用例构造完整接口与逃逸体系；后者专门追踪一项知识为何散落并重组边界。
- 与 `decide-combine-or-split` 的区别：本方法 设计一个模块应提供什么；后者裁决已有职责、类或方法是否应合并/拆开。
- 与 `design-around-what-matters` 的区别：后者寻找少数高杠杆信息；本方法 把它们落实为原语、覆盖矩阵和逃逸治理。
- 与 `design-it-twice` 的区别：设计两次是本流程中比较候选接口的工具，但不负责需求覆盖和长尾归位。

## E — 可执行步骤

### 先准备四张表

执行过程中持续维护：

1. **用例表**：调用者、任务、频率、失败影响、调用者独有信息。
2. **知识表**：规则、格式、状态、不变量、算法和变化原因，以及当前由谁知道。
3. **覆盖表**：每个用例如何通过核心原语完成，额外胶水是什么，未覆盖时走哪条逃逸路线。
4. **逃逸账本**：逃逸原因、使用权重、逃逸深度、污染范围、能否重新汇入、权限与收编/淘汰条件。

### 步骤 1：建立真实用例基线

- 收集已经存在或已承诺的任务，不以想象中的“以后也许有人需要”扩大范围；Agent 降低了改代码成本，却没有降低预测未知需求的难度。
- 将用例分为：
  - 高频常见路径；
  - 低频但高影响或安全关键路径；
  - 确实存在的长尾路径。
- 以完整工作流而非单个方法验证，例如 `创建 → 执行 → 等待 → 失败 → 恢复 → 删除`，防止接口只覆盖一半就迫使调用者逃逸。
- 为每个用例记录调用者比模块多知道什么，例如租户策略、事务边界、持久化要求或设备能力。
- **完成标准**：每个用例有具体输入、期望结果、频率/影响和知识所有者；所有高频及高影响用例均在表内，并至少有一条端到端主工作流。
- **判停条件**：若没有真实调用者或行为证据，只能先做可替换原型，不得宣称接口“覆盖大部分需求”。

### 步骤 2：按知识而非执行顺序划职责

- 列出完成这些任务所需的设计知识：协议格式、状态机、索引规则、重试策略、资源约束等。
- 另列不随具体类型轻易变化的系统不变量：身份、生命周期、权限、状态一致性、错误模型、等待/取消和可观测性；优先让主体接口统一它们。
- 把同一知识的解析、校验、存储和转换尽量集中到一个权威模块。
- 为模块写一句职责声明：`它拥有哪些知识，为调用者消除什么负担`。
- 执行顺序相邻但知识不同的职责可以拆开；时间上分开的步骤若共同解释同一规则，可能应组合。
- 长参数链可用窄而稳定的上下文对象终止透传，但上下文只能承载共同环境，不能成为任意数据袋。
- **完成标准**：每项核心知识有唯一权威位置；职责声明不依赖当前页面、按钮或工作流名称。
- **判停条件**：若模块需要知道多个独立业务域的规则才能成立，可能正在形成万能模块，先重划边界。

### 步骤 3：从专用动作归约有限原语

- 去掉方法名中的界面动作和一次性业务名，寻找共同操作的对象、范围、状态转换和不变量。
- 尝试用一个通用操作覆盖多个专用操作，例如用范围删除覆盖退格、前删和删除选区。
- 原语必须“有点通用”：完整支持当前需求，但不预测未知未来；少几个方法不能以参数爆炸为代价。优先选择简洁、优雅、低代码量和低复杂度且保留受控逃逸的方案。
- 至少草拟两个差异明显的接口，只写方法签名、行为契约、默认值和错误语义，无需先实现。
- **完成标准**：每个核心原语服务多个真实用例，或虽只服务一个用例但承载不可再分的重要能力；没有与单一按钮同义的核心方法。
- **判停条件**：若一个“通用”方法需要模式字符串、十几个布尔开关或调用者理解内部状态，它只是把专用性藏进参数，返回步骤 2。

### 步骤 4：设计常见路径和接口契约

- 为高频用例提供最短、最明显的入口和可工作的默认值。
- 将模块能够通过观测或自身知识可靠决定的事项自动化，不把它们伪装成“灵活性”交给每个调用者。
- 在实现前写接口注释，明确抽象、输入语义、结果、副作用、并发/持久化保证和错误。
- 将罕见覆盖入口与普通构造和调用路径分开，使普通用户不必先学习它。
- **完成标准**：首次使用者只读接口契约即可完成常见任务，不必读实现、查示例组合或先选择高级策略。

### 步骤 5：用加权覆盖矩阵验证有限接口

对每个真实用例逐步演算，并填写：

| 用例 | 频率/影响 | 核心原语路径 | 调用者额外胶水 | 是否需逃逸 | 结论 |
|---|---|---|---|---|---|
| 示例：顺序读取 | 高频 | `open → read → close` | 无 | 否 | 核心覆盖 |
| 示例：随机读取 | 中频 | `open → seek → read` | 无 | 否 | 核心覆盖 |
| 示例：专用编码 | 低频 | 核心读取后转换 | 一处清晰组合 | 否 | 留在上层 |

- 胶水包括重复循环、拆分/合并、类型转换、状态传递、成对调用、实现探测和重复异常处理。
- “覆盖大部分”按真实使用权重判断，而不是按用例条数判断。若有遥测，计算无需逃逸的请求/调用占比；没有遥测时，至少要求所有高频用例和所有高影响用例有明确路径。
- 少量、单点、容易读懂的上层组合可以接受；相同胶水在多个调用者出现就是核心能力缺口。
- 让不了解实现的评审者只看接口和矩阵演算至少一个常见、一个长尾用例。
- **完成标准**：
  - 高频路径不依赖逃逸口；
  - 高影响路径的语义明确且不会被默认值掩盖；
  - 没有多处重复胶水或必须阅读实现才能完成的步骤；
  - 接口注释能简短而完整地解释行为。
- **判停条件**：若多数调用者需要相同组合、配对方法或内部表示，有限接口覆盖失败；回到步骤 2 或 3，而不是继续补文档。

### 步骤 6：给每个未覆盖需求选择唯一归位

按顺序裁决，不能直接跳到“加配置”：

| 归位 | 适用条件 | 处理方式 | 禁止信号 |
|---|---|---|---|
| **核心原语** | 多数用户需要；属于模块拥有的知识；能消除多处胶水 | 扩展或重新归约核心接口，并提供合理默认 | 为单个客户复制一个专用方法 |
| **上层组合** | 用现有原语可清楚表达；规则属于某个业务动作或工作流 | 在最了解业务语义的上层封装组合 | 同样组合在多处复制 |
| **专用实现/适配层** | 差异来自设备、供应商、传输或不可改的外部接口 | 放到共同接口后的实现；适配层只翻译边界 | 让公共接口镜像供应商全部选项 |
| **显式高级入口** | 调用者掌握模块无法推断且结果重要的信息，或某类对象确有专用动词 | 使用独立高级方法、类型化能力/策略或显式配置；仍复用主体身份、生命周期、权限、错误和可观测规则 | 开放原始内部表示、万能键值袋或另造平行资源体系 |
| **性能逃逸** | 代表性测量证明核心路径需由调用者控制所有权、生命周期、布局、批量边界或设备能力 | 提供窄的 `span/view`、批量 API、能力对象或专用 adapter；写清失效、线程与回退语义 | 没有基线就开放裸指针/内部容器；fast path 绕过共同不变量 |

- 若需求不满足任何一栏，先确认它是否真实、是否属于另一个模块，或是否应拒绝支持。
- **完成标准**：每个缺口只有一个知识所有者和一条路径，归位理由可由用例与知识表验证。

### 步骤 7：把逃逸设计成受控通道

- **隔离**：高级入口不出现在常见构造器和入门示例中，普通调用者无需知道它。
- **收窄**：暴露调用者真正掌握的策略信息，而不是内部队列、缓存、线程或存储表示。
- **类型化**：优先使用具名策略、能力接口或专用适配器，避免字符串键和无限扩张的 `options`。
- **性能证据**：性能逃逸必须对应目标、代表性负载、基线和热点，或已有可复现的数量级差异；仓库宣称“高性能”只能触发检查，不能单独批准复杂入口。
- **零拷贝责任**：若暴露 view/reference/span，必须把所有权、生命周期、失效条件、可变性、线程安全和复制回退写进契约；这些由调用者必须知道的事实不是应被隐藏的信息。
- **守住不变量**：允许新增领域动词，不允许扩展者另造对象身份、生命周期、权限、状态一致性、错误模型和可观测体系。
- **重新汇入**：专用方式创建或操作的结果应尽快回到公共句柄、事件、审计和资源治理中；逃逸若一路污染所有上层，就是平行系统。
- **有默认**：默认值必须对多数调用者安全；高风险控制要求显式选择，不能静默猜测。
- **可观测**：记录何时使用逃逸、由谁选择、命中何种结果，便于判断它是否已成常见需求。
- **设置调试面确认点**：主动询问设计者“是否需要独立测试/Agent 调试面，以及允许哪些环境和动作”；未获明确要求时不创建超级权限入口，也不从“可能方便”自行推断需求。
- **按要求设计高权限调试平面**：设计者明确要求后，提供无需改业务代码即可调用的稳定 CLI/API，以短期、限环境、限能力的鉴权令牌访问获准的状态构造、故障注入、检查与清理能力；命令要有 schema、幂等语义、审计和自动回收。该控制面必须独立部署或由不可绕过的环境门禁保证生产不可达，不能变成无类型 `eval` 或公共核心入口。
- **让成本具有方向性**：使用官方扩展点应自动获得生命周期、权限、监控、重试、版本与审计；绕开主体规则则必须显著更难并接受单独审查。
- **可晋升/可淘汰**：同类逃逸反复出现、完整工作流经常无法留在主体模型，或使用权重显著上升时，提炼共同结构并纳入核心；长期无人使用则删除。
- **完成标准**：逃逸只暴露必要决策，不复制模块知识，不迫使普通用户理解它；逃逸账本能证明其频率低、深度浅、局部、可重新汇入，并有权限、审计和回归测试。

### 步骤 8：红队审查并决定是否回炉

逐项检查五类失控信号：

1. **信息泄露**：调用者重复解析同一格式、维护同一状态机或了解内部数据结构。
2. **配置膨胀**：每个新用例都增加布尔开关、模式枚举或供应商选项，组合语义无法说明。
3. **万能模块**：模块吸收彼此无关的业务知识，只因“想把接口做深”而不断扩大职责。
4. **隐藏重要信息**：持久化、安全、财务、并发或策略选择被默认值吞掉，但调用者才拥有正确判断所需的信息。
5. **平行生态**：高级入口重新定义对象、生命周期、权限、错误或观测，离开核心后无法重新汇入。

- 另查：高级入口是否进入常见示例；适配层是否长成第二套核心；调用者是否必须读实现；接口注释是否长到只能复述内部流程；高权限调试面是否可由普通生产身份访问。
- 用包/模块可见性只公开真正入口，让越界依赖在编译或持续集成阶段失败，而不是只靠架构图。
- **完成标准**：每个信号要么不存在，要么有明确回炉步骤和所有者。
- **判停条件**：出现信息泄露、常见路径依赖逃逸、不可解释的配置组合、被隐藏的高影响决策、不可重新汇入的平行体系或生产可达的调试超级权限时，不得发布当前接口；返回步骤 2、3、6 或 7。

## B — 边界

### 不要在以下情况使用此 方法

- 只是把更多职责塞进同一个类以减少公开方法：模块深度是功能收益相对接口成本，不是体积。
- 调用者必须依法规、安全、财务或持久化要求作出显式决定：这些信息不能以默认值偷偷隐藏。
- 插件生态、跨组织公共 API 或多供应商平台以可扩展性为核心价值：有限核心仍有用，但扩展契约、兼容性和权限边界必须单独设计。
- 当前问题只是两个已知组件是否合并：优先使用 `decide-combine-or-split`；确定目标边界后再用本方法 设计接口。

### 作者在书中警告的失败模式

- 浅模块：接口成本几乎等于它提供的功能，调用者没有得到明显简化。
- 类太小综合症和透传层：每层只转交同样信息，没有形成新的抽象。
- 为每个当前动作增加专用方法，最终得到通用/专用混杂的接口。
- 过度配置：模块本可自动决定，却把选择甩给所有用户。
- 下沉复杂性过头：模块隐藏了它无法正确推断、而调用者确实关心的信息。
- 上下文对象滥用：它能终止稳定环境信息的逐层透传，但若变成无类型数据袋，会制造新的隐蔽依赖。

### 作者的盲点 / 时代局限

- 书中的深模块证据多来自操作系统、存储和单团队项目；公开 API 的兼容期、跨组织治理和数据迁移会限制重新划界。
- 深接口可能把诊断、容量和故障复杂性集中到实现者；必须补充可观测性、故障注入和运维逃逸，书中讨论较少。
- 现代类型系统、所有权、效果系统和生成式接口可能用机器契约承担一部分原本靠注释隐藏的复杂性。
- “覆盖大部分”没有通用百分比。必须使用本系统的频率、影响和风险证据，不能把书中案例变成固定阈值。

### 容易混淆的邻近方法论

- 深模块不等于大模块：若职责不共享知识，合并只会产生万能模块。
- 有限接口不等于封死扩展：它要求把未覆盖需求显式分类并治理。
- 受控逃逸不等于暴露底层对象：真正的逃逸只交出调用者独有的必要决策，并继续服从主体不变量。
- 深封装也不等于强制复制或逐元素调用：在性能型仓库中，批量原语、结构化导出和有生命周期契约的 view 可能正是正确的深接口。
- “组合优于实现继承”、上下文对象和默认 Getter/Setter 审查都作为边界手段并入相关方法，不作为独立方法论。
