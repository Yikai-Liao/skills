## 阅读方法

- **主来源**：《软件设计的哲学（第二版）》John Ousterhout。
- **辅助来源**：《架构整洁之道》Robert C. Martin。
- **系统边界补充**：《架构设计的本质》。
- **Pattern 与案例补充**：`System Design 101`；只提供条件性结构候选和反例，不覆盖主来源尺度。
- **裁决原则**：按用户指定，主来源优先。辅助来源中有冲突的主张只有经用户裁决后才改写 方法；未裁决内容只作条件性补充或反例。
- **状态含义**：
  - `可调和`：两书关注层次不同，可以同时保留，但必须写清适用条件。
  - `待裁决`：会改变执行建议，不能无痕合并。
  - `已裁决`：用户已经给出取舍，方法按该答案执行。

## C01 — TDD 是设计动力，还是只应作为重构安全网？

- **主书观点**：第 19 章认为 TDD 容易把开发者带向“让下一个测试通过”的战术式增量，可能造成按功能碎片堆积；测试的主要设计价值是为重构提供安全网，不能替代设计思考。
- **辅助书观点**：第 1 章引用一个为期六天的小实验，报告采用 TDD 的轮次约快 10%；第 28 章把测试视作系统组件；后序建议每次测试后进行设计审查。
- **冲突核心**：是否应把 TDD 本身作为推荐的设计流程。
- **裁决前默认**：保留测试先复现缺陷、契约测试和重构安全网；不把“测试先行”写成设计正确性的来源，也不采纳 10% 为通用生产率结论。
- **原建议状态**：`待裁决`。若用户希望更积极吸收辅助书，可在 `evolve-design-strategically` 中增加“可选 TDD 循环，但每轮必须独立做抽象审查”。

答：TDD不作为推荐的设计流程，在Agent驱动的开发中表现并不好，测试驱动很容易进入局部陷阱，架构设计碎片化，后续变更困难，因为AI总是倾向于过度测试。

- **裁决状态**：`已裁决`。TDD 不作为推荐设计流程；测试只作为行为基线、缺陷复现、契约验证和重构安全网。Agent 开发必须先写目标抽象与知识归属，并按风险设置测试预算，避免逐个测试驱动局部补丁。

## C02 — 核心接口应“有点通用”，还是按用例高度专用？

- **主书观点**：第 6 章主张把退格、前删、删除选区等专用动作归约为范围式通用原语；专用方法扩散会形成浅接口。
- **辅助书观点**：第 20、23 章强调用例端口，并给出 `getLastNamesOfUsersWhoLoggedInAfter` 这类高度专用的数据库网关方法。
- **冲突核心**：跨边界接口应该表达通用领域能力，还是直接表达单个用例所需查询。
- **裁决前默认**：核心领域/数据模块遵循主书，提供围绕共同知识的有限原语；若某端口由单一用例拥有，则允许在上层定义窄而专用的端口，由适配器把它翻译到核心能力，但不得把专用方法反向塞入共享核心。
- **原建议状态**：`待裁决`。这项选择会直接影响 `design-deep-modules` 的逃逸归位规则。

答：参考Linux 文件系统接口设计上的实践：阅读 ChatGPT - Linux 文件系统设计.md

- **裁决状态**：`已裁决`。以用户提供的 Linux 文件系统设计讨论补充主书：
  1. 核心统一身份、生命周期、权限、错误、等待、状态一致性与可观测性等稳定不变量，不要求所有对象统一全部动词。
  2. 用完整工作流检验主体接口；常见工作流不能做到一半就依赖逃逸。
  3. 类别/专用操作必须继续服从主体不变量，并能重新汇入公共治理；不得借逃逸另造平行资源体系。
  4. 按逃逸频率、深度、局部性、重新汇入能力和生态分叉成本审计；重复逃逸要提升为核心能力。

## C03 — 面向当前需求，还是尽量最大化未来可选项？

- **主书观点**：第 6、11 章要求面向当前真实需求设计“有点通用”的接口，反对为未知未来构造万能机制；通过“设计两次”比较眼前候选。
- **辅助书观点**：第 15–17 章反复要求尽可能长时间保留尽可能多的选项；第 24、25 章甚至允许为可能出现的边界做部分预留，同时承认这与 YAGNI 存在张力。
- **冲突核心**：为尚未发生的变化投入多少抽象成本。
- **裁决前默认**：只为有证据的变化轴、昂贵且不可逆的决定保留选项；通过依赖方向、窄接口或不完全边界延迟具体选择，但不实现未被当前用例需要的通用功能。
- **原建议状态**：`可调和`，但若用户希望严格 YAGNI，可进一步删掉所有“预测性部分边界”建议。

答：面向未来最大的原因是，减少变更难度，但是AGENT驱动时，变更成本在下降，这就让确定未来需求这个事情的难度凸显出来。我们可以在设计时明确反对一些典型的错误架构设计。但是在开发时，简洁优雅低代码量低复杂度的设计才是更优的。当然，你得有逃逸机制。

- **裁决状态**：`已裁决`。只为有证据且昂贵难逆的变化轴保留窄接缝；当前实现优先简洁、优雅、低代码量和低复杂度，并提供受控逃逸，不为推测的未来实现完整框架。

## C04 — 功能/用例分解，还是警惕小模块与按流程拆分？

- **主书观点**：第 5、7、9 章反对按执行时间顺序拆模块、类太小综合症、透传层和按行数拆方法；模块边界应围绕共享知识，接口收益必须大于接口成本。
- **辅助书观点**：第 4 章把功能性分解称为最佳实践之一；第 7、16、33 章按行为者和用例拆类、组件与垂直切片。
- **冲突核心**：一个用例或函数是否天然应该成为独立模块/组件。
- **裁决前默认**：行为者和用例只作为变化证据，不自动生成边界。仅当拆分能隔离不同知识/变化原因、形成可测试契约，且新增接口成本可接受时才拆。
- **原建议状态**：`可调和`。
- **裁决状态**：`可调和`，按当前默认直接执行；行为者/用例是变化证据，不自动生成模块边界。

## C05 — 架构/策略天然更重要，还是重要性必须按具体任务判断？

- **主书观点**：第 2、4、8、21 章按真实任务、接触频率和调用者知识判断什么重要；持久化时机等“底层细节”如果调用者必须知道，就不能隐藏。
- **辅助书观点**：第 2、15、17、30、31 章把架构价值置于行为价值之上，并把数据库、Web、I/O、框架统称为不重要的实现细节。
- **冲突核心**：能否预先用“策略/细节”层级决定重要性和隐藏方向。
- **裁决前默认**：“细节”只决定源码依赖应朝向稳定策略，不等于其后果不重要。数据模型、持久化保证、安全策略、延迟预算和运维控制若影响调用者决策，必须显式进入契约或高级入口。
- **原建议状态**：`待裁决`。当前 方法 会采用主书的任务/知识判据，并把辅助书的层级仅用作依赖组织工具。

答：主书是对的。如果依赖底层细节，就不能隐藏，但是为什么会依赖底层细节需要考量，有可能是通用接口设计不合理，导致必须依赖底层细节，也可能是依赖无法避免。前者应该回退到架构设计的调整。有可能是依赖底层细节才能实现更好的性能优化，但是除非是热点函数，或者一个甚至多个数量级上的性能优化，否则不应该依赖底层细节。并且，在软件从0到第一版的开发中，应重点关注流程正确性，尤其是主路径（主要对外的抽象接口）的正确性，不需要关注性能进一步优化问题，如非必须，不依赖底层细节。

- **裁决状态**：`已裁决`。重要性按真实任务和知识判断。出现底层依赖时先检查是否因通用接口失当；若是则回退架构设计。性能穿透只在测量证明为热点，或有一个乃至多个数量级且对目标必要的收益时考虑。从零到第一版优先主流程与主要对外抽象正确。

补充裁决：用户目标与背景约束必须分开。性能背景用于防止把有证据的零拷贝、批量、静态分派或多表示逃逸误判为结构缺陷，也用于否决会破坏关键路径的候选；它不会自行增加性能分析交付。只有用户目标确实包含性能设计或裁决时，才完整执行性能契约、基线、热点、理想路径和 A/B 复测。确需调用者控制所有权、生命周期、数据布局、批量边界或硬件能力时，可设计窄而类型化的性能逃逸；不得为“封装”强迫关键路径复制，也不得以“高性能”为由暴露整个内部对象图。

## C06 — 依赖指标能否指导重构？

- **主书观点**：复杂性最终由真实开发任务中的变更放大、认知负荷和未知的未知判断；局部形式指标不能替代整体复杂性。
- **辅助书观点**：第 14 章提供 `Fan-in`、`Fan-out`、不稳定性 `I`、抽象度 `A` 和主序列距离 `D`，用于发现异常组件；同时明确指标不等于真理。
- **冲突核心**：指标是重构结论还是调查入口。
- **裁决前默认**：只把环、异常入/出向依赖和 `A/I/D` 当作候选信号；必须回到真实任务证明其造成高权重复杂性后才能重构。
- **原建议状态**：`可调和`。

答：局部指标不能代替整体复杂性，不能只分析局部

- **裁决状态**：`可调和，已确认`。依赖指标只作调查入口，任何重构结论都必须回到跨模块真实任务与总体复杂性。

## C07 — 使用继承扩展，还是优先组合并避免实现泄露？

- **主书观点**：第 19 章认为实现继承会让父类内部细节泄露给子类，优先使用组合；模式只有自然契合时才采用。
- **辅助书观点**：第 11、22、27、33 章频繁使用抽象类、派生类、模板方法、策略模式和工厂来反转依赖并实现插件。
- **冲突核心**：插件扩展点是否应以含实现的基类/模板方法为默认机制。
- **裁决前默认**：保留接口实现、多态端口和组合根；若基类只定义稳定契约可以使用，若子类依赖父类状态、调用顺序或可覆盖实现，则改用组合。
- **原建议状态**：`待裁决`。默认采用主书的“组合优先”，辅助书案例改写为接口/策略端口，不推广实现继承。

答：我明确排斥从多个基类的继承设计，即使在python中也不推荐使用。而在go和rust中，我们只能使用组合，在c++中我们可以使用concept约束。

- **裁决状态**：`已裁决`。明确拒绝多基类实现继承；Python、Go、Rust 优先组合与接口/trait，C++ 用 concept 表达能力约束。单继承也只有在稳定契约、不暴露父类状态和调用顺序时才可考虑。

## C08 — 是否应为测试提供超级权限 API？

- **主书观点**：主书强调有限接口、减少特殊入口和避免信息泄露，没有提出测试专用超级接口。
- **辅助书观点**：第 28 章建议用测试 API 绕过安全限制、昂贵数据库并强制建立状态，同时要求将其置于独立部署组件，不能进入生产。
- **冲突核心**：测试便利性是否值得新增一套高权限逃逸面。
- **裁决前默认**：只有当接口在构建和部署上可证明不会进入生产、权限边界可自动验证、且不暴露核心内部表示时，才允许作为受控逃逸；否则使用公开契约、测试替身或状态构造器。
- **原建议状态**：`可调和`，但属于高风险例外。

答：我认为测试超级权限接口是需要的，尤其是对于Agent的自主调试来讲。这个超级接口还必须考虑agent自主使用的便利性（例如，可以直接通过cli/api + 鉴权token 等机制方便的调用），不需要改动代码才能完成调试。

补充裁决：独立调试面仅在设计者明确要求时创建；未提出时，Agent 必须主动询问，不能自行加入。

- **裁决状态**：`已裁决`。深模块设计必须设置一次显式确认点：主动询问是否需要独立测试/Agent 调试面。设计者明确要求后，才提供无需改业务代码的稳定 CLI/API、限环境限能力令牌、schema、幂等、审计和自动回收；并通过独立部署或不可绕过的门禁保证生产不可达。

## C09 — 架构设计与实现细节的边界在哪里？

- **用户材料观点**：《架构设计的本质》以性质、受众、利益、目标、需求、抽象、设计和方向描述纵向设计链，同时从实体、功能、关系、边界和外部环境做横向系统分析。架构是对系统实体及其关系的抽象描述，用于指导后续各方面设计；架构也会在业务、产品、技术和实施阶段以不同形态出现。
- **辅助书观点**：《架构整洁之道》第 1 章认为高层结构和低层设计是连续体，没有天然分界；第 15 章把架构落实为组件划分、排列和通信方式。
- **主书尺度**：《软件设计的哲学》不按技术层级定义重要性，而按真实任务复杂性、知识归属和结构中心裁决；所谓底层信息如果是调用者必须决定的关键知识，就不能仅以“细节”隐藏。
- **表面张力**：若只强调连续体，架构审计可能把所有实现问题吞入架构；若按固定技术层级划线，又会漏掉已经成为公共契约或系统约束的低层决定。
- **执行口径**：先声明评价范围，再看决定回答的是“系统由什么构成、各部分如何关联、谁拥有决定”，还是“既定单元内部如何完成工作”。改变实体/责任划分、稳定关系、外部边界、跨边界契约或关键质量/生命周期责任分配的是架构决定；能在一个既定单元内独立替换且不改变上述事项的是实现细节。架构可出现在各阶段，也可存在于一个组件内部，只要它塑造该范围内多个部分或承载无法局部替换的系统级保证。
- **升降级规则**：私有机制泄露为多方必须共同理解的兼容或性能契约时，升级为架构候选；架构决定被稳定深接口封装后，其具体机制可以降为实现细节。技术名词、代码层级、修改规模和严重度都不能代替该判断。
- **裁决状态**：`可调和，已纳入`。本技能以“纵向系统设计链条 + 相对范围 + 替换/传播半径 + 真实任务机制”给出明确操作边界，同时承认设计在物理上是连续体。

## C10 — 设计方法是否应该变成一套系统 pattern 流程？

- **主书观点**：第 1、19、20、21 章要求按具体问题裁决原则，警惕模式过度使用，以真实热点和重要性组织设计。模式只有自然匹配并降低净复杂度时才采用。
- **Pattern 材料倾向**：`System Design 101` 提供大量架构蓝图、组件清单、模式目录和“常见问题—解决方案”图解，适合快速发现候选，但容易被读成固定系统设计流程。
- **冲突核心**：具体 pattern 是帮助 agent 看见更多可行结构，还是替代用户目标、需求建模和现有 11 个方法。
- **执行口径**：11 个蒸馏方法仍回答怎样发现、裁决和验证；pattern 只回答在某类已证实压力下可以比较哪些结构动作。广义架构审计完整加载 pattern 家族以避免召回盲区，但不按固定顺序执行，不要求采用或输出任何模式。
- **准入合同**：每个 pattern 必须写真实工作流、压力、契约/不变量、知识所有者、结构动作、新增成本与失效、更简单候选、验证和退出。缺少模式不是问题，组件存在也不是健康证据。
- **裁决状态**：`可调和，已纳入`。主书尺度优先；Pattern 材料成为具体候选库，不成为方法论或用户意图分类器。

## C11 — “服务越小越好”，还是以深模块和自治收益决定粒度？

- **主书观点**：第 4、9 章警惕小模块综合症和拆分成本；模块/服务只有接口收益大于管理、距离和重复成本，并隐藏足够知识时才值得独立。
- **Pattern 材料倾向**：部分微服务文章建议每个服务只做一件事、保持很小、无状态并拥有独立数据库；另一些案例又显示数百服务超出人的管理能力，低延迟和大中间数据可能要求共置。
- **冲突核心**：能否从单一职责、组织图或代码量直接生成服务边界。
- **执行口径**：先形成按知识和变化轴划分的逻辑模块；只有独立发布、扩缩、故障/信任隔离或团队所有权的收益足以支付网络、序列化、数据一致性和运维成本时，才升级为进程/服务边界。服务粒度仍接受深模块检查；一起变化、一起发布且调用聊天化的服务应考虑重组或共置。
- **数据口径**：自治边界应拥有其写入规则和不变量，但“不允许绕过权威”不等于“每个服务必须有一个独立物理数据库”。本地事务和状态局部性可以否决无条件分库。
- **裁决状态**：`已由主书优先级和既有边界裁决覆盖`。不新增用户决策点。

## C12 — 能否把简化的系统 pattern 主张直接写成规则？

`System Design 101` 的视觉化定位会省略成立条件。本技能明确拒绝直接吸收：

- 读多就缓存、慢查询或数据大就分片；
- 高可用就增加节点、双活或多主；
- 异步/事件驱动天然松耦合，消息中间件天然不丢；
- exactly-once broker 语义等于最终业务副作用只发生一次；
- 所有读都走副本，热点键永不过期；
- 所有 4xx 不重试、所有 5xx 可重试；
- 单体和有状态组件天然违背云原生；
- CAP、SQL/NoSQL、REST/GraphQL 等类别能单独决定选型；
- 公司案例数字、典型 timeout 或 RTO/RPO 可以直接移植。

这些内容只能改写成有进入条件、失败机制、可观察信号和退出标准的候选。完整来源限制见 [System Design 101 来源边界](source-system-design-101.md)。

- **裁决状态**：`已裁决`。主书“真实任务 + 净复杂度 + 性能测量”优先，简化主张只作反例或提问入口。

## 最终执行摘要

1. 11 个方法的标题、触发和核心步骤以主书为准。
2. 吸收辅助书的具体案例：FitNesse、HAL/OSAL、P/W 公司、组件聚合张力、边界成本阶梯、编译器封装。
3. 吸收辅助书的细则：行为者/变化轴、依赖方向、简单边界数据、部分边界、组合根、访问控制。
4. 不吸收为默认规则：TDD 驱动设计、为未知未来最大化抽象、用例专用接口进入共享核心、多基类实现继承、数据库/Web/运维后果“不重要”。
5. 深模块按稳定不变量、完整工作流、加权覆盖和受控逃逸构造；逃逸不得重造平行体系，重复逃逸必须收编。
6. 独立测试/Agent 调试面必须主动询问、显式授权后创建；一旦创建，必须方便自动调用且与生产业务面严格隔离。
7. 架构与实现按评价范围和系统构造影响划分：架构决定实体、关系、边界、契约与关键责任分配；可在既定单元内独立替换的机制是实现细节。
8. `System Design 101` 只补充受压力准入的 pattern 候选、失效场景与案例问题；不增加第十二个方法，不生成固定流程。
9. 广义架构审计完整加载四个 pattern 家族以消除发现盲区，但缺少组件/模式永不自动成为问题；任何推荐都必须包含成本、验证和退出。
