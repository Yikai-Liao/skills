## 定位

本页把具体系统设计模式变成可比较的结构候选。它不是第十二个设计方法，也不是“标准架构组件清单”。

- **方法**回答怎样发现、裁决和验证设计问题，例如深模块、信息泄露、设计两次。
- **模式**是在一组条件下反复出现的结构动作，例如读副本、竞争消费者、API Gateway、Saga。
- **组件或产品**是某个模式的一种实现，例如具体数据库、消息系统或网关产品。
- **架构发现**是已经证明某个边界、关系、知识归属、契约或生命周期责任造成系统性成本。
- **实现细节**是在既定边界内可独立替换的机制。一个模式只有改变系统构造或跨边界保证时才是架构决定。

因此，“仓库没有缓存”“系统还是单体”“没有消息队列”都不是发现；“用了 Kafka”“采用微服务”“部署在 Kubernetes”也不是设计理由。

## 读取合同

### 普通设计任务

1. 先读本页，把用户目标、完整工作流、真实压力和关键不变量写清。
2. 按压力路由读取一个或多个模式家族；模式可以联合，不要求选唯一主模式。
3. 同时读取负责裁决的现有方法，例如设计两次、深模块、组合或拆分、关键路径测量。
4. 只展开证据命中的候选，不输出未被问题需要的系统设计手册。

性能方法可以只作为模式准入门：例如当前 SLO 已满足、没有热点/容量/成本证据时，直接否决“为性能加缓存”，不必展开 profile、benchmark 建设或优化流程。只有用户目标包含性能设计，或候选收益确实需要测量裁决时，才执行完整性能产物。

### 面向仓库或子系统的广义架构审计

在建立候选清单前，除了完整读取 11 个方法，还必须完整读取本页和下列四个模式家族：

- [结构与边界模式](patterns-structure-and-boundaries.md)
- [通信与工作流模式](patterns-communication-and-workflows.md)
- [数据与一致性模式](patterns-data-and-consistency.md)
- [韧性、伸缩与交付模式](patterns-resilience-scale-and-delivery.md)

完整加载只负责消除发现盲区，不要求采用、替换或逐项输出这些模式。每个家族最后必须得到以下结果之一：

- **已确认问题**：真实压力已经存在，当前结构或缺失的结构通过架构准入；
- **候选/证据缺口**：只有静态形状、未来预测或未测量的压力；
- **有证据支持的健康设计**：当前结构与压力匹配，值得保留；
- **不适用**：该家族对应的压力在本次范围内不存在，并说明依据。

[System Design 101 来源与吸收边界](source-system-design-101.md)只用于追溯材料、案例和来源限制，不是每次执行必读文件。

## 模式准入：先有压力，再谈结构

任何模式进入候选比较前，都要通过六问：

1. **真实工作流**：哪个使用者在完成什么端到端任务？频率、峰值和失败后果是什么？
2. **已证实压力**：当前结构在哪个指标、变更、所有权或失败场景上越界？事实、假设和预测分别是什么？
3. **关键契约**：正确性、不变量、新鲜度、顺序、丢失/重复预算、延迟、可用性、RTO/RPO 或兼容保证是什么？
4. **最小候选**：能否先在现有边界内优化、集中知识、加深接口或调整配置？为什么必须增加新的边界、状态或运行角色？
5. **净复杂度**：模式隐藏了哪些调用者知识，又新增了哪些协议、状态、故障、部署和运维责任？
6. **验证与退出**：什么证据会保留、否决或撤回该模式？何时收编逃逸、重新组合或退回更简单结构？

任何一问没有答案，模式只能列为待验证候选，不能写成推荐结论。

### 模式决定卡

对每个保留候选填写：

| 字段 | 必填内容 |
|---|---|
| 用户目标与完整工作流 | 不用“高并发”“大数据”等空标签代替 |
| 压力与证据强度 | 已观察、可复演或待验证 |
| 必须守住的契约/不变量 | 包括失败时调用者可见的语义 |
| 结构动作与知识所有者 | 新增、移动、合并或拆分什么；谁说了算 |
| 被隐藏的复杂性 | 哪些调用者胶水、拓扑或策略不再传播 |
| 新增成本与失效方式 | 协议、状态、延迟、重复、顺序、部署、运维 |
| 更简单候选 | 包括保持现状，使用同一基线比较 |
| 验证、回滚与重评触发器 | 可复现测量、演练和退出条件 |

只写“引入缓存提高性能”“采用事件驱动解耦”“拆成微服务方便扩展”不算完成。

## 压力路由

| 需要裁决的压力或关系 | 读取的模式家族 | 同时联合的方法 |
|---|---|---|
| 源码模块、进程、服务、仓库、团队或 API 聚合边界 | [结构与边界](patterns-structure-and-boundaries.md) | 组合或拆分、信息泄露、深模块、战略式演化 |
| 同步/异步、单播/广播、长任务、更新推送、长工作流和消息语义 | [通信与工作流](patterns-communication-and-workflows.md) | 深模块、异常处理、注释优先、信息泄露 |
| 存储选择、热点读取、读扩展、分区、状态/事件权威、并发和一致性 | [数据与一致性](patterns-data-and-consistency.md) | 重要性、设计两次、信息泄露、关键路径测量 |
| 依赖失败、过载、冗余、故障转移、扩缩容、发布和灾备 | [韧性、伸缩与交付](patterns-resilience-scale-and-delivery.md) | 异常处理、战略式演化、注释优先、关键路径测量 |

同一问题可以跨家族。例如异步支付流程通常同时涉及消息交付、幂等记录、补偿/对账和故障恢复；不能因表格分栏把它切成互不相干的四份设计。

## 从模式名回到设计问题

当用户或仓库已经给出模式名时，先把它翻译成待验证问题：

| 听到的模式名 | 先追问 |
|---|---|
| 微服务 | 哪项独立部署、扩缩、故障隔离或团队所有权收益足以支付网络和运维成本？ |
| API Gateway / BFF / Federation | 聚合规则和客户端差异由谁拥有？中央边界是否成为额外 hop 或变更瓶颈？ |
| 消息队列 | 调用者是否允许延迟完成？排序、重复、积压、过期和失败由谁负责？ |
| 发布/订阅 | 谁拥有事件 schema 与语义？消费者重放、乱序和版本兼容怎样处理？ |
| Saga | 是否真的跨越多个自治事务边界？每一步能否补偿，谁拥有全局流程状态？ |
| 缓存 | 热点是否已测得？权威数据在哪，允许多旧，缓存失效时源站会怎样？ |
| 读副本 | 哪些读取允许陈旧？写后读与复制延迟怎样成为显式契约？ |
| 分片 | 哪个单节点资源已经触顶？分片键能否兼顾局部性、均匀性和重分片？ |
| CQRS / Event Sourcing / CDC | 当前状态还是历史事件是权威？读写模型差异、回放或下游同步是否真实存在？ |
| 重试 / 熔断 | 是暂态失败还是过载/永久错误？总 deadline、幂等和恢复责任是什么？ |
| 双活 / 多副本 | 故障是否独立？谁可写、怎样切换、重复和冲突怎样解决？ |
| Canary / Blue-Green / Shadow | 需要什么生产证据、允许多大爆炸半径、版本是否兼容、怎样自动回滚？ |

## 组合模式而不制造“模式汤”

模式联合必须共享同一条任务与契约链：

1. 先画完整工作流和状态权威；
2. 为每个跨边界步骤写同步/异步、超时、重复、顺序和失败语义；
3. 只在一个新模式解决上一层明确压力时加入；
4. 检查多个模式是否重复拥有同一策略或制造双重真相源；
5. 重放正常、峰值、部分失败、恢复和演化任务；
6. 删除无法回指压力或无法单独验证收益的组件。

典型错误是把 Gateway、服务发现、队列、缓存、分片、CQRS、Event Sourcing、熔断和 Kubernetes 一次性画进“生产级架构”。组件越多，只说明需要解释的状态和故障越多。

## 架构审计中的模式覆盖

广义审计至少建立：

| 家族 | 当前压力/契约 | 已有结构 | 健康/问题/候选/不适用 | 架构相关性 | 最小验证 |
|---|---|---|---|---|---|
| 结构与边界 |  |  |  |  |  |
| 通信与工作流 |  |  |  |  |  |
| 数据与一致性 |  |  |  |  |  |
| 韧性、伸缩与交付 |  |  |  |  |  |

模式覆盖只生成候选。进入架构问题主表还必须证明：

- 它改变边界、关系、知识归属、跨边界契约或生命周期责任；
- 结构通过真实任务系统性地产生理解、修改、运行或协调成本；
- 推荐改进能切断这条结构因果链。

某个重试次数不合理、一个索引缺失或单次缓存失效可以非常严重，但若局部修复不改变系统构造，它仍是实现、性能或运行问题。相反，所有调用者都必须自行理解复制延迟、路由规则或幂等存储时，这些“底层机制”已经升级为架构契约。

## 全局拒绝规则

- 不从系统规模、行业、语言或仓库标签直接推出模式。
- 不从“读多写少”直接推出缓存；还需热点、瓶颈、陈旧度和退化证据。
- 不从“数据很多”直接推出分片；还需单节点上限、访问局部性和重分片路径。
- 不从“要高可用”直接推出双活；还需故障域、写入所有权、切换和冲突语义。
- 不从“服务很多”直接推出 Gateway、Service Mesh 或事件驱动。
- 不把异步、无状态、云原生、松耦合、最终一致性或 exactly-once 当作天然更高级。
- 不把公司架构案例当作当前仓库的规模证明或通用最佳实践。
- 不把模式缺失当问题，也不把模式存在当健康证据。
- 不为了使用模式而改变用户交付目标；架构审计仍交付架构，性能背景仍只修正架构判断。

## 完成检查

- 每个模式是否回指一项真实压力和完整工作流？
- 是否先定义契约、不变量和失败预算，再选组件？
- 是否比较保持现状和至少一个结构不同的更简单候选？
- 是否说明模式隐藏了什么、又向谁新增了哪些知识与责任？
- 是否区分逻辑模块、进程、服务、仓库和部署边界？
- 是否把性能收益建立在目标、基线和代表性负载上？
- 是否定义失效、恢复、回滚和重新评估条件？
- 若是架构审计，是否完成四个模式家族覆盖但没有凑模式、凑问题或扩张专项？
