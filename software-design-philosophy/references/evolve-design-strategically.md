## R — 原文

> 战略式编程需要一种投资的思维方式。你必须花费时间来改进系统的设计，而不是采取最快的方式完成当前项目。
>
> — John Ousterhout，第 3 章

---

## I — 方法论骨架

能工作的当前版本不是唯一目标；每次改动也在决定未来修改的成本。
战略式设计不是先把全系统设计完，而是在实现反馈中持续校正抽象。
面对新需求，先描述它在正确设计中应属于哪里，再看现有结构与这个状态的差距。
选择能交付当前价值、同时向正确边界移动的最小完整切片。
测试的设计价值是保护行为，让结构性调整可以安全发生；测试不能替代抽象判断，尤其不能让 Agent 按“下一个失败测试”把架构切成局部碎片。
若期限不允许一次完成，应留下可独立验证的演进台阶，而不是永久旁路。
每个小捷径都要被认真对待，因为复杂性通常由许多“就这一次”累积。
验收标准不是改动行数最少，而是功能正确且系统没有比修改前更难理解和演化。

## A1 — 书中的应用

### 案例 1：Facebook 与 Google、VMware 的工程文化

- **问题**：快速发布的组织压力让工程师反复选择眼前最快的实现。
- **方法论的使用**：作者比较战术式文化与持续投资代码质量的文化，追踪短期速度如何积累成长期结构成本。
- **结论**：战略式编程要成为每次工作的日常预算，而不是等到技术债爆发后集中偿还。
- **结果**：Facebook 后来将口号调整为“在坚实的基础架构上快速行动”；作者也提醒，公司的成败不能只归因于这一变量。

### 案例 2：Tcl 从解释器演化为字节码编译器

- **问题**：解释器性能不足，需要替换核心执行机制，但又不能破坏既有语言行为。
- **方法论的使用**：团队利用覆盖既有语义的测试套件作为安全网，允许内部结构进行大幅重构。
- **结论**：测试应保护外部行为，从而释放设计空间，而不是把当前实现结构永久固化。
- **结果**：实现从解释执行迁移到字节码编译，同时保持兼容性；书中未给出通用的量化收益。

### 辅助案例 3：FitNesse 延迟数据库决定

- **问题**：《架构整洁之道》第 17 章中的 FitNesse 尚未证明需要关系型数据库，却必须持续开发 wiki 核心能力。
- **方法论的使用**：团队先定义 `WikiPage` 所需行为，用内存实现推进用例，之后演化为文件实现；数据库选择被保留为外围决定。
- **结论**：战略演化可以先建立正确接缝，再用真实需求决定实现，不必冻结完整架构或提前建设万能存储层。
- **结果**：系统约 18 个月无需数据库；客户后来只用一天补出 MySQL 实现，但最终也没有持续使用。

## A2 — 触发场景

### 用户会在什么情境下需要这个方法？

1. 给遗留系统加入跨模块概念，最小方案是在各处追加参数或条件分支。
2. 缺陷可用一行补丁遮住，但根因来自错误边界、重复状态或含糊语义。
3. 团队说“先上线以后重构”，却没有可验证的后续台阶。
4. 新需求要求重构，但担心破坏大量既有行为。
5. 产品必须分期交付，需要同时设计每一期的可用状态和最终结构。

### 语言信号

- “先打个最小补丁，设计以后再说。”
- “怎么加这个功能才不会继续堆技术债？”
- “能不能一边交付，一边把这块结构理顺？”
- “这次改动怎样看起来像一开始就支持？”
- “测试够不够支撑这次重构？”

### 与相邻方法 的区分

- 与 `diagnose-software-complexity` 的区别：本方法 已有具体变更，负责规划结构改善；后者用于定位复杂性根因和优先级。
- 与 `design-it-twice` 的区别：本方法 管理多步演化和交付约束；后者聚焦某个重要设计点的候选比较。
- 与 `design-abstractions-comment-first` 的区别：注释优先可作为本流程的设计工具，但不是完整的演化策略。

## E — 可执行步骤

1. **定义行为约束和目标结构**
   - 列出必须保持的外部行为、兼容性、数据和安全约束。
   - 用一句话说明：如果系统从第一天就知道这个需求，职责、状态和接口会放在哪里。
   - **完成标准**：目标描述不依赖“先在旧位置加个特殊分支”。

2. **建立可重构的安全网**
   - 先写目标抽象、知识归属和迁移方向，再选择能保护这次结构调整的行为测试；不把 TDD 循环当作设计来源。
   - 检查现有测试是否覆盖即将移动的行为，而不是只覆盖实现细节。
   - 对缺陷先增加能稳定复现根因的测试；对新能力补充契约或验收测试。
   - Agent 驱动时设置测试预算：优先主路径、高影响失败和边界契约，避免为局部实现分支堆积过度测试。
   - **完成标准**：测试在旧代码上能证明基线或复现缺陷，并可在重构期间持续运行；每项测试都能说明它保护的行为或迁移风险。
   - **判停条件**：关键行为无法被观察或回滚时，先改善可测性与恢复方案，不进行大范围结构迁移。

3. **比较战术补丁与战略候选**
   - 对每个候选列出当前交付成本、引入的依赖/特殊情况、后续迁移成本和失败半径。
   - 至少包含一个向目标边界移动的方案，不允许所有候选都只是补丁变体。
   - **完成标准**：选择依据是总复杂性和约束，而非单纯改动行数。

4. **切出最小的结构性增量**
   - 先建立正确的抽象接缝，再迁移一个端到端用例；保证每一步可构建、可测试、可回滚。
   - 完整边界太贵时，可比较源码接缝、单向接口或 Facade 等不完全边界；不得把“以后也许会拆”直接升级成服务。
   - 若完整重构超出期限，把剩余工作写成有触发条件、所有者和删除标准的迁移项。
   - **完成标准**：当前需求可以通过新边界完成，旧旁路没有继续扩散。

5. **实施时清除顺手暴露的小复杂性**
   - 修正误导名称、重复规则、无必要分支和失真的注释，但控制在当前变更的因果范围内。
   - **完成标准**：改动后没有新增不明显依赖；相关区域至少不比原来更难理解。

6. **验收演化结果**
   - 运行行为测试，比较新旧依赖图和调用路径，检查临时适配是否有明确退出路径。
   - **完成标准**：功能交付、行为保持、结构向目标状态收敛，且后续一步比修改前更容易。
   - **判停条件**：若“临时方案”没有可执行的移除条件，应视为永久设计重新评审。

## B — 边界

### 不要在以下情况使用此 方法

- 生产事故正在扩大：先采取最小可逆止血和恢复，稳定后再用本方法 处理根因。
- 真正的一次性探索脚本且不会进入共享路径：战略投资可能高于生命周期收益。
- 需求和技术风险尚未通过最小实验验证：先做隔离原型，避免把猜测固化成正式抽象。

### 作者在书中警告的失败模式

- 在实现前冻结完整设计，使后来证据只能通过旁路进入。
- 每次只求最小补丁，承诺“以后重构”却没有迁移机制。
- 按功能碎片做增量，每一片都留下专用接口，而不是增量构建抽象。
- 把测试当作设计方法本身，写出可测但仍然浅薄、耦合的结构。
- Agent 围绕逐个失败测试反复局部补丁，并为实现细节过度加测，最终让架构碎片化且难以变更。

### 作者的盲点 / 时代局限

- 书中案例较容易由一个团队整体修改；公开 API、跨组织服务和数据迁移可能要求更长的双轨期。
- “持续投入 10%–20%”是作者经验，不是经验证的统一配额；应按风险和生命周期决定。
- 合规或安全系统有时必须保留显式审查关卡，即使这降低局部演进速度。

### 容易混淆的邻近方法论

- 战略式演化不是大前期设计：它允许实现反馈改变目标结构。
- 测试套件和“先复现缺陷”已合并为本方法 的安全网步骤，不是独立的软件设计方法。
