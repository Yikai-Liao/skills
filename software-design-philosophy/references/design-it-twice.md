## I — 方法论骨架

重要设计的第一个想法通常只是最容易想到的，不代表设计空间中的最佳位置。
在编码前强制提出第二个差异明显的方案，能以很低成本暴露隐藏假设。
候选只需勾勒关键接口、状态和控制流，不需要完整实现。
比较应从上层调用者开始，再看通用性、实现复杂性、性能和演化成本。
第二个方案不能只是给第一个方案改名或换一个模式；它必须改变一个核心取舍。
比较结果可以选原方案，也可以组合优点形成第三个方案。
如果所有候选都要求大量胶水、专用分支或复杂参数，应继续找方案，而不是在坏方案中任选。
Agent 降低了日后改代码的成本，却没有降低预测未知需求的难度，因此当前应偏向简洁、低代码量、低复杂度且有受控逃逸的候选。
方法的价值不仅是当前决定，还包括明确哪些证据会使未来重新决策。

## A1 — 书中的应用

### 案例 1：文本接口的三种候选

- **问题**：文本编辑器需要选择按行、按字符还是按范围组织 API。
- **方法论的使用**：作者同时勾勒几种接口，用删除、复制、选区等真实动作比较调用者胶水、方法数量和通用性。
- **结论**：范围式接口以更少原语自然覆盖更多当前操作。
- **结果**：比较产生的不是折中式方法堆叠，而是更深、更通用的抽象。

### 案例 2：文本存储实现的多种候选

- **问题**：同一编辑器内部可使用链表、固定大小字符块或间隙缓冲区。
- **方法论的使用**：在接口设计之外，分别比较内部结构对插入、删除、定位和内存移动的影响。
- **结论**：接口候选和实现候选应分开比较，避免让当前数据结构绑架公共语义。
- **结果**：即使不完整实现每个方案，关键权衡也能在早期显现。

### 辅助案例 3：完整边界、部分边界与暂不设边界

- **问题**：《架构整洁之道》第 24、25 章指出，完整架构边界成本高，但完全不准备又可能让后续拆分昂贵。
- **方法论的使用**：把独立部署的完整边界、源码级单向边界、Facade 和暂不设置边界列为不同候选，比较当前成本与未来分离难度。
- **结论**：边界不是“有或无”的二选一，物理强度可以单独设计。
- **结果**：团队可以先保留低成本源码接缝，等真实变化压力超过成本时再升级。

## A2 — 触发场景

### 用户会在什么情境下需要这个方法？

1. 新 API、第一个模块边界或数据模型准备进入实现，但尚无备选。
2. 团队在单体、独立组件、进程或服务之间做高成本选择。
3. 一个方案调用简单但实现复杂，另一个实现简单却把负担交给调用者。
4. 两个候选都不理想，需要发现第三种组合方案。
5. 设计评审只听到“我们一直这样做”或“这个模式最流行”。

### 语言信号

- “还有没有另一种设计？”
- “offset、cursor 还是迭代器？”
- “要不要现在就拆成服务？”
- “这个方案能工作，但我不确定是不是最好。”
- “帮我系统比较这几个接口。”

### 与相邻方法 的区分

- 与 `diagnose-software-complexity` 的区别：诊断方法 定义问题、症状和优先级；本方法 生成和比较解决方案。
- 与 `decide-combine-or-split` 的区别：后者专门裁决组合/拆分；本方法 可用于任何重要设计决策。
- 与 `design-measured-critical-paths` 的区别：性能候选若需要真实收益判断，必须由测量方法 验证，不能只靠纸面评分。

## E — 可执行步骤

1. **框定一个决策**
   - 写明要决定什么、当前真实用例、不可违反的约束和决定期限。
   - 把“已观察到的变化轴”和“纯推测的未来可能”分开；后者不能单独支撑新增架构。
   - 把接口选择、实现选择和部署选择分开，避免一次比较太多维度。
   - **完成标准**：可以用一句问题和一组验收条件描述决策。

2. **写出第一方案及其核心假设**
   - 只画关键接口、数据所有权、依赖方向和一条典型控制流。
   - 列出它默认假设了什么，例如“调用者知道分页状态”“数据库不会更换”。
   - **完成标准**：不看实现也能演算常见用例。

3. **强制产生差异明显的第二方案**
   - 至少改变一个核心轴：状态归属、抽象原语、同步/异步、源码/进程边界、策略/机制分离等。
   - 即使认为第二方案较差也要完成草图；它的作用是暴露比较维度。
   - **完成标准**：第二方案不是换名、换模式或给第一方案加一个参数。
   - **判停条件**：两个方案的调用路径和知识归属几乎相同，继续生成候选。

4. **用同一证据矩阵评分**

   | 维度 | 要回答的问题 |
   |---|---|
   | 调用者易用性 | 常见任务需要几步、多少额外知识和胶水？ |
   | 接口成本 | 方法、参数、异常、顺序约束和文档有多大？ |
   | 当前需求覆盖 | 高频和高影响用例是否直接可达？ |
   | 信息隐藏 | 哪些设计知识只存在一处？ |
   | 实现复杂性 | 状态、并发、测试和故障处理成本如何？ |
   | 性能 | 是否有测量支持，关键路径是否自然高效？ |
   | 演化/可逆性 | 哪些决定不可逆，迁移与兼容成本多大？ |
   | 当前简洁性 | 为现有任务新增多少代码、概念、状态与测试负担？能否以受控逃逸替代预测性框架？ |

   - **完成标准**：每个评分都有用例、测量或明确假设，不使用“更优雅”作为单独理由。

5. **进行反例演算**
   - 每个候选至少演算一个常见用例、一个长尾用例和一次未来变化。
   - 检查是否出现重复胶水、专用方法、配置膨胀或跨边界联动。
   - **完成标准**：能指出每个方案最可能失败的情境。

6. **选择、组合或继续探索**
   - 若一个候选在高权重维度明显更好，选择它。
   - 若候选各有互补优势，形成第三方案并重新跑矩阵。
   - 若都触发根本危险信号，返回步骤 3，不在已知坏方案中投票。
   - **完成标准**：决策记录包含选择、拒绝理由、保留风险和重新评估触发器。

7. **按风险决定验证深度**
   - 低成本决定可直接实现；性能、兼容性或不可逆边界需原型、基准或迁移演练。
   - 对未知未来，默认选择当前最简洁、低代码量、低复杂度且保留窄逃逸/可替换接缝的方案，不为“也许”实现完整选项。
   - **完成标准**：验证成本与失败代价相称，纸面比较没有冒充实证。

## B — 边界

### 不要在以下情况使用此 方法

- 命名、格式等低风险可逆选择已有项目约定：遵循一致性即可。
- 生产事故正在发生：先按已知恢复路径止血，事后再比较长期方案。
- 已有剖析数据和明确热点：用 `design-measured-critical-paths` 做保留/撤销实验。

### 作者在书中警告的失败模式

- 执着于最先想到的设计，为它寻找理由而不产生真正备选。
- 候选差异太小，比较只是在确认原方案。
- 为每个候选完整编码，导致比较成本高到团队不愿执行。
- 只比较实现内部，不比较上层调用者的额外工作。

### 作者的盲点 / 时代局限

- 安全、合规和数据迁移决策可能需要威胁建模、法律审查或真实演练，接口草图不足以裁决。
- 辅助书“最大化可选项”与主书“只面向当前需求”存在张力；本包裁决为：Agent 降低变更实现成本后，更应警惕预测错误，只为有证据且昂贵难逆的变化轴保留窄接缝，当前实现优先简洁、低代码量、低复杂度和受控逃逸。
- 群体评审仍可能受组织权力影响，应明确评分证据而非只靠共识。

### 容易混淆的邻近方法论

- “设计两次”不是瀑布式大前期设计；草图应快速，并允许实现反馈改变决定。
- “保留选项”不等于提前实现所有选项；窄接缝和可逆选择通常足够。
