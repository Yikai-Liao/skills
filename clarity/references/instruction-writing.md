# 指令写作的重点边界

## 保留要求，不重定任务

改写 skill、项目指令和提示词时保留目标、条件、权限、交付及停止要求，不以简化为由重新制定流程。“必须”“可以”“禁止”及动作先后关系不降格；要求全部测试不擅改为部分测试。

将混在一起的授权、禁令和交付分清，不给简单要求套必填模板。冲突指出原句及影响，不替用户选政策。

## 内容按行为作用取舍

Skill 优先保留会改变模型默认行为的约束、易误用的边界及必要短例，不重复讲授模型通常具备的知识。判断删留要问：少了这段，哪种选择或输出容易出错？不能仅因主题重要、有可靠来源就收入，也不能因模型听过某原则就删掉针对常见偏差的约束。

先合并重复规则，再删去没有独立作用的解释和例子。不同条件、例外和权限不是重复；有意义的分组与名称应保留，不把多个职责压成术语串。例子优先说明易混边界，兼顾应改与应保留的情况，不靠堆积同义案例增强语气。

Skill 描述负责触发，共用约束放主文件，独立细节按需读取；不把分支变成必经流水线。来源整理、改版历史与自评留维护资料，执行必要的技术依据仍在使用处可得。`AGENTS.md` 不积累单次计划或失效补救指令。

## 用实际缺口修订

模型出错时，先区分规则缺失、表述含混或冲突，以及已有规则未被执行；不要每遇到一次失败就追加补丁指令。修订针对可复用的判断边界，单次事件留在测试或维护记录中。

精简后核对触发范围、条件、例外和要求强度，并用相邻的应改、应保留场景检查是否误伤。既检查语义保真，也把 skill 本身当作成品阅读：指令关系能否直接理解，是否要求读者来回拼接？篇幅减少不是效果证据；静态检查、模型试跑与实际用户反馈分别记录，不把维护验证变成使用技能的必经流程。
