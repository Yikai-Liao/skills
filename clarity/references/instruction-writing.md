# Skill、项目指令与提示词的写作

用于编写或审查 skill、`AGENTS.md` 和任务提示词；普通文档、书籍与代码任务不需要加载本文件。

## 让每类指令承担合适的职责

| 载体 | 适合放什么 | 避免什么 |
|---|---|---|
| Skill 的名称与描述 | 能力及明确触发场景，让模型能选对技能 | 长篇说明、宽泛关键词、“任何相关任务都必须使用” |
| `SKILL.md` | 共用目标、关键边界、必要的参考入口 | 把所有分支写成必经流水线 |
| 参考文件与脚本 | 特定分支需要的知识、细则或可复用操作 | 为了拆文件而拆文件，加载全部参考才能开始 |
| `AGENTS.md` | 跨任务仍成立的项目事实、约束与安全操作范围 | 一次任务的完整计划，早已失效的模型补救指令 |
| 本次提示词 | 当前目标、交付物、范围、完成与停止条件 | 重复整套技能，或只写“做好一点” |

正式指令保留执行所需的目标、条件、边界、示例和参考入口。编写来源、改版经过、作者自评及“为什么这样设计这份 skill”的说明放在项目 `doc/` 等维护路径中，不纳入 skill 的运行时参考目录。执行需要的技术依据、外部规范或授权条件仍应在使用处可得。

## 描述要短，触发要准

写清“完成什么、何时使用”，把执行细则移到正文。过长的描述增加上下文负担，也可能被运行环境截短；关键词过宽会导致误触发并与其他 skill 冲突。

不宜：处理数据库、查询、模型、持久化以及所有相关问题时使用。

更准确：创建或验证 PostgreSQL 迁移；新增、修改迁移或审查发布方案时使用。

不要追求越短越好：若删掉适用边界会使相邻任务误用，就保留该边界。不设置统一字数限额。

## 主文件负责路由，细节按需提供

多工作流技能在主文件说明各分支何时有用，再指向对应参考。单一小任务不必强拆多文件。

不宜：每次修改前阅读架构、数据库和部署的全部文档。

更准确：服务边界问题参考架构文档，schema 变化参考数据库文档，准备发布时参考部署文档。

判断一次加载是否值得：它是否提供当前决定需要、且模型不能从已有上下文可靠获得的信息？不要让一个标点修改支付整套项目导览的成本。

### PDF 任务：分支入口与实际文件要同时成立

一个 PDF 技能可以在主文件提供基础操作，将表单填写与高级处理分到专门参考。任务是提取普通 PDF 文本时，不应先支付表单字段处理的全部阅读成本。

反例指令（教学改写）：无论处理哪种 PDF，先读完表单、高级处理与全部脚本，再开始工作。

正例指令，在目录确实包含相应文件时：

> 普通文本提取使用本页的基础操作；填写 PDF 表单时读取 `forms.md`；需要高级功能时读取 `reference.md` 中对应部分。

分支条件让执行者知道何时加载，文件名让它知道到哪里取知识。所选分支中影响正确性的前置检查仍须完成；“按需”不等于跳过必要步骤。

还有一种真实的入口问题：指令写 `FORMS.md`，目录却只有 `forms.md`。在区分大小写的文件系统中，两者不是同一路径；仅有清楚的分支描述仍不足以执行。

修复应以实际目录为准，使引用名称与文件一致，并检查其他入口。若文件本身已改名或移走，还要确认内容是否仍对应任务，不能只把一个不存在的路径改成任意存在的文件。文件拆分后应同时验证触发条件、相对路径和目的内容。

## 规定结果与关键约束，不包办所有步骤

优先写清交付、必须保持的语义、领域陷阱与验证依据。只有顺序本身影响正确性、安全或可复现性时，才规定固定步骤。

不宜：任何改动都先列十步计划、生成全仓库地图、逐步汇报，然后运行所有测试。

更准确：完成本次改动，保持公开接口不变，并验证受影响的行为；涉及迁移时遵守已知的先后依赖。

减少流程负担不等于删除必要知识、权限限制或高风险检查。能用判断边界说明的事情，不另建复杂评分、状态机或审批流程。

需要其他人或 agent 执行的指令，应让目标、可执行动作、条件、权限和交付物各有归属，避免让执行者从混杂的要求中重建任务边界。

反例：

> 修改解析器内部实现并跑相关本地测试，本次修改造成失败就修到通过，公开接口变更先确认，不要发布，最后要代码和测试结果。

正例：

> - 交付：解析器修改及相关测试结果。
> - 可自行完成：修改内部实现，运行相关本地测试并修复本次改动导致的失败。
> - 需先确认：公开接口变更。
> - 不在范围内：发布。

分组显露交付与授权关系；修复范围须以实际任务为准，不能把无关测试失败自动纳入任务。简短且无歧义的单项指令无需套用这些字段。

## 授权与停止条件成对写清

不要只写“任何操作都先问”，也不要只写“自主完成一切”。说明哪些动作已获授权，哪些决定确实需要确认。

例如，**仅在环境确实如此且有权授权时**可写：

> 本地测试使用可丢弃夹具且不接触生产环境。可运行相关测试、修复本次改动造成的失败并复测，无需逐次确认；发布和生产数据修改不在授权范围内。

完成条件应对应用户真正需要的结果。若目标包括实现、运行、检查结果和修复失败，就写清这些事项；不要同时要求“首版完成后停下等待审阅”，除非那确实是需要的决策节点。

“继续完成”仍受既定范围和授权约束，不等于无限探索、顺手扩题或跳过真实阻塞。

## 给其他贡献者和模型留下可复用的指令

仓库指令也会被其他贡献者的 agent 使用。某个模型需要的反复提醒，可能让另一个模型过度谨慎或重复工作。

把稳定的项目事实与临时的模型适配分开：通用文件保留真实约束，模型特定提示只在确有需要的上下文使用。不要从“新模型更可靠”推出免除测试、确认权限或忽略安全边界。

模型、工具或项目改变后，回看旧指令：它仍针对实际失败吗？是否与其他指令冲突？是否要求读取无关材料、重复验证或过早停下？无效则删，适用面过宽则收窄，只有分支需要则移到参考。

## 最小检查

选一个典型任务、一个容易误触发的相邻任务，以及一个边界任务，检查模型能否选对入口、完成产物、遵守授权并适时停止。可以先作静态审查，再按风险试跑；不要求每次改一句描述都建立评测系统。

保留确实减少错误或提供必要知识的指令。不要仅凭文档更短或模型声称“已理解”，就认定行为已经改善。
