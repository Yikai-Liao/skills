# Skill、项目指令与提示词的写作

把已有目标、条件、权限和交付要求写清，不借改写制定新政策。

## 各载体的职责

| 载体 | 内容 |
|---|---|
| Skill 名称与描述 | 能力与触发场景，便于准确选择 |
| `SKILL.md` | 共用目标、关键边界、参考入口，不将分支写成必经流程 |
| 参考文件 | 独立主题的细节，文件名与入口说明用途 |
| `AGENTS.md` | 跨任务成立的项目事实与约束，不放单次计划或失效补救指令 |
| 本次提示词 | 当前目标、交付、范围、完成和停止条件 |

运行时保留执行需要的技术依据、规范、授权、示例与入口。来源整理、改版历史和作者自评放维护文档，不混入运行时参考。

## 描述与触发

描述写“完成什么、何时使用”，细则进正文。保留能区分相邻任务的边界，避免宽泛关键词，不设统一字数限额。

- 含混：处理数据库、查询、模型、持久化及所有相关问题。
- 明确：创建或验证 PostgreSQL 迁移；新增、修改迁移或审查发布方案时使用。

## 分清条件、动作与交付

例如，原要求将修改解析器、测试、公开接口审批与禁发要求混在一句中，可按职责展开：

> - 交付：解析器修改及相关测试结果。
> - 可自行完成：修改内部实现，运行相关本地测试并修复本次改动导致的失败。
> - 需先确认：公开接口变更。
> - 不在范围内：发布。

修复范围不扩大到无关失败；简短无歧义的单项要求不必套用字段。

“必须”“可以”“禁止”及“通过后”“之前”“仅在”保留原有强度、对象和顺序。“审阅通过后才能发布”可改为“发布前须通过审阅”，不能改成建议审阅；要求全部测试也不改成部分测试。冲突指出原句及影响，不擅自选择新政策；清楚的原文可以不改。
