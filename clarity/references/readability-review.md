# 可读性审查

## 发现准入

可读性问题应有具体依据：

1. **读者**：谁在读，合理的已有知识是什么。
2. **任务**：读者此刻要理解、找到、决定、执行或修改什么。
3. **位置**：准确引用、章节/段落、文件/符号，必要时给出多个依赖位置。
4. **额外操作或表达阻力**：需要猜哪个指代、回查哪项条件、补出哪些句间关系，或穿过哪些反复设限、无关纠偏才能取得实际判断。
5. **可避免性与后果**：表达造成什么误判、遗漏、额外搜索，或怎样推迟结论、制造训诫口吻；区分这些阻力与必要推导、领域复杂性或有意阅读体验。
6. **改进**：具体怎么改，去掉什么负担，保留什么含义。表达本来清楚时，不必给替换版本。

没有实际读者观察时，影响写成基于文本的分析，不伪称“读者测试表明”。仅有个人偏好时不进入问题清单。对空心人式解释或主张替换，须指出原主张、被添加或改写的观点，以及任务、范围或强度怎样偏移；预先澄清则核对具体语境依据。不能仅凭“没人说过”或出现几个“不能”“不等于”判错。每句为真仍可能偏题；只有组织阻力时，说明哪些排除项遮蔽了所需事实，不必将它命名为论证谬误。参见[文本写作](text-writing.md#直接陈述边界清除防御性套话)。

## 轻量输出

审查结果单独交付，不混入被审查作品；用户要求的审查报告本身应包含问题、依据和建议。例如：

> `指南 / 配置缓存 / 第 2 步` 的“启用它后重启”指向不清：前一句同时介绍本地缓存和共享缓存，部署者无法判断哪一种需要重启。这里应写出适用的缓存名称。

这些依据用于说明问题，不是必须逐项填写的报告模板。材料未明确的含义不由审查者代选；指出表达缺口即可，不附加机制调查或验证计划。

如需排序，优先处理会改变判断、掩盖风险或导致错误操作的阻塞；其次处理妨碍完成主要任务的跳转与缺失关系；最后才是局部减负。不要把风格偏好标成高严重度。

同一根因多处出现时合并并提供代表位置，避免逐句重复报告。用户要求行内批注时才使用适合格式的注释机制，保留作者原有批注。

## 应报告与不应报告

| 观察 | 裁决 |
|---|---|
| “函数有 60 行”“句子超过 30 字” | 只有度量，没有读者影响，不成立 |
| 已经拆成短句、加了标题，但每句换一个未解释的概念 | 检查读者必须自行补出的关系；排版变化不等于理解问题已解决 |
| 用临时设定的复杂系统解释一个已有简单实例的问题 | 若新增背景妨碍当前理解，优先用双方已有材料解释；不将所有新例子一律判错 |
| 用户只追问一处原因，回复却重发整份研究报告 | 指出本轮问题被哪些无关内容淹没，保留回答所需的背景和依据 |
| 专家指南直接使用该领域标准术语 | 不能因外行不熟悉就报 jargon 问题 |
| 本章有意延迟揭示人物身份 | 若符合叙事目标，保留悬念，不强制结论先行 |
| 删除操作之前没有说明会同时删除共享副本，提示藏在末尾 | 操作者在不可逆动作前缺少关键条件，成立 |
| 摘要写“方案有效”，限制部分才写仅在特定样本成立 | 决策读者可能误用适用范围，成立 |
| 报告用“为避免过度宣称，这里保留了限制”解说写作策略 | 改为直接陈述具体限制；保留对结论适用性的影响 |
| 状态汇报已知单机通过、多机未测，却只写“单机通过不能说明多机通过，仍需验证” | 应直接交代通过与未测状态；问题是所需事实被间接排除和空泛提醒遮蔽，不是出现了“不能” |
| 对“这个 PR 带来进展”回应“一个 PR 不代表全部交付” | 指出“进展”被替换为“全部交付”，后者的否定没有回应前者 |
| 汇总实验结果时，追加“作者摘要和绿色 CI 只帮助定位结果；旧结果不能为新机制背书” | 指出未经核对就降格材料，并引入旧结果替新机制背书的假想推论；应报告材料实际支持的结果与具体缺口 |
| 设计方法说明后追加“不要套用 base/head 标签，也不因缺 benchmark 就判错”，上下文没有这些做法或误解依据 | 指出新增了两项无关纠偏；保留方法和任务已有的假设要求，不把新增禁令当成必要严谨性 |
| 证据审计说明“提案不能当成已上线事实” | 有明确任务依据，可保留；无人先说错并不使它成为空心人论证 |
| 发布页混排获批与上线，说明主动区分二者 | 有具体语境依据的预先澄清，不因尚无实际误读而报告问题 |
| 接口说明“既不负责鉴权，也不负责重试” | 职责排除清楚且相关，不因连续否定要求重写 |
| “运行期间禁止拔出设备，否则会损坏数据”含否定用语 | 具体操作禁令及后果清楚，保留 |
| 把 `task` 和 `job` 统一能减少名词 | 名称按实际概念区分；语义不同则不合并 |
| 流程被多层 helper 分开 | 仅当契约不足、真实任务必须追踪额外关系时成立 |
| 函数是只读名称却会刷新令牌，调用者无法从契约获知 | 补行为契约或在权限内改名；不能为了名字删掉刷新行为 |

事实错误、软件缺陷和可理解性可以同时存在。分别注明类别：事实核查需要证据，行为缺陷需要复现或契约依据；不能用“读起来费力”替代这些证明。

### 从原话记录提取可报告的信息

一张公开的用户研究便签记录了原话：

> I don't think it is a problem, I just can't count.

便签另标有参与者编号 5。任务是决定这条材料能支持怎样的发现。

反例报告：“五名用户因界面难懂而计算失败，应简化页面。”它把编号当成样本数量，把个人表述改成已观察到的失败，又把原因归给了未提供的界面。

正面处理：

- **原始记录**：保留原话及参与者编号 5；两者应能对应原记录。
- **证据缺口**：这张便签没有给出具体任务、操作位置、行为结果或其他参与者情况。
- **当前裁决**：这是一名参与者的自述；“五名用户计算失败”和“界面导致失败”均未见对应记录。

分析与改动建议可以建立在观察之上，但不能混写成观察事实。原话不完整时保留具体缺口，不用一段看似完整的 finding 掩盖缺证。
