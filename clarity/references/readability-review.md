# 可读性审查

## 以具体阅读阻力立项

每项发现说明：谁在什么任务下，读到哪个位置，需要猜测、回查、补关系或绕过哪些无关纠偏；这会怎样妨碍判断或操作，如何修复并保留含义。必要推导、领域复杂性、叙事悬念与个人偏好本身不构成问题。

无读者观察时，写成基于文本的分析，不声称做过读者测试。主张替换须对照原观点，指出任务、范围或强度的变化；合理预澄清有具体语境即可，不以“没人说过”判错。组织问题只需说明哪些排除项遮蔽事实，不必强加谬误名称。具体场景见[文本写作](text-writing.md#直接陈述边界清除防御性套话)。

## 简明交付

例如：

> `指南 / 配置缓存 / 第 2 步` 的“启用它后重启”指向不清：前文同时介绍本地缓存和共享缓存，部署者无法判断哪一种需要重启。应写出适用的缓存名称。

这是问题、依据与建议，不是必须填写的报告模板。材料缺义时指出缺口，不代选含义或自动附加机制调查、验证计划。

优先处理错误判断、风险遗漏和危险操作，其次是妨碍任务的跳转与缺失关系，最后才是局部减负。相同根因合并并给代表位置；只在用户要求时作行内批注，保留原有批注。普通审查与作品分开，清楚的原文不必改。

## 相邻场景的裁决

| 观察 | 裁决 |
|---|---|
| 函数 60 行或句子超过 30 字 | 度量不能独立证明理解问题 |
| 短句、标题齐全，每句却换一个未解释的概念 | 指出读者仍需补出的关系 |
| 追问一处却重发报告，或另造陌生系统来解释已有简单例子 | 定位哪些内容增加无关背景，保留当前问题所需解释 |
| 专家术语或有意延迟揭示人物身份 | 按受众与叙事任务保留 |
| 删除操作会删共享副本，警告却在末尾 | 操作前缺关键条件，应报告 |
| 摘要称方案有效，适用样本却藏在后文 | 结论范围可能被误用，应就近说明 |
| 对“PR 有进展”回应“并非全部交付” | 原主张被扩大后否定 |
| 明确区分获批与上线，或说明接口不负责鉴权/重试 | 相关澄清与职责排除可保留 |
| 为少用名词而合并不同的 `task` 与 `job` | 不能抹去真实概念区别 |
| 多层 helper，但调用契约足以理解任务 | 不因跳转数量本身报告问题 |
| 只读名称的函数会刷新令牌，契约未说明 | 补契约或在权限内改名，不为名字删行为 |

事实错误、行为缺陷与可读性分别给依据；读起来费力不能代替事实核查或缺陷复现。

## 原话不等于行为证据

公开用户研究便签写道：

> I don't think it is a problem, I just can't count.

旁边的 5 是参与者编号。“五名用户因界面难懂而计算失败”误把编号当数量、自述当行为记录，又推定了原因。

报告应保留原话及编号，说明缺少具体任务、操作位置、行为结果和其他参与者材料。分析与建议可以基于观察，但不能冒充观察事实。
