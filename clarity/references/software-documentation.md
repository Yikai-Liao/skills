# 软件文档

软件文档帮助读者使用软件、确认需求、实现契约、理解架构或执行变更。本页负责 README、用户与开发指南、需求、spec、独立 API 参考、架构文档和开发计划；源码结构、行内注释、API 文档注释、docstring 与运行时报错见 [代码表达](code-readability.md)。句段与论证问题见 [文本写作](text-writing.md)，跨章组织和续写状态见 [长篇组织](long-form-writing.md)。

按给定材料起草或改写软件文档，使用本页即可。任务需要与人讨论方案、处理反馈或维护决定时，再读[设计讨论与记录](design-discussion.md)。

## 按要完成的任务组织

| 读者任务 | 需要能回答的问题 |
|---|---|
| 判断是否采用、第一次使用 | 适用什么、前提是什么、怎样完成一次任务、接下来去哪查 |
| 确认需求 | 谁遇到什么问题、目标与非目标、约束、怎样确认满足需求 |
| 按 spec 实现或调用 | 输入、输出、状态与失败语义是什么，哪些行为被保证 |
| 理解架构或评估变化 | 系统边界、职责与依赖是什么，决定为何成立、影响在哪里 |
| 执行开发计划 | 交付什么、依赖什么、如何验证、失败或中断后怎样继续 |
| 排查故障 | 观察到什么、哪些原因已证实、下一步怎样缩小范围或安全恢复 |

这些是信息职责，不是必须创建的六个文件。复用现有文档布局；小变更可以在同一文档中分节，独立查询的契约应有稳定入口。必要摘要可以重复，完整定义应有明确权威位置，不能让同一行为在 README、spec 和指南中各自演化。

区分**现状、已批准的目标、待评审提案与未知项**，按内容标明版本和适用范围。实现与 spec 的差异应在说明中可见；当前行为与批准目标各自保持准确，不用流畅文字替用户决定产品政策。

## README 与使用指南

### README 是入口，不是固定栏目清单

让读者判断项目是否适用、找到第一次使用的路径，并知道后续去哪里查。软件使用者与源码贡献者的前提不同，不能把克隆、构建、测试和发布都混进普通安装步骤。

- 最小使用路径应包含必要环境、安装或获取方式、一个代表性任务及预期结果。配置、凭据或权限若是运行前提，就放在依赖它的步骤之前。
- 项目有多种安装途径时，区分替代方案与连续步骤，不让读者以为每条命令都要执行。模板中的包名、命令、输出和联系方式必须用已核实内容替换；没有资料就指出缺口。
- 详细 API、维护开发和部署文档可以外置，入口说明目的地。若已有漏洞报告政策，提供可发现的安全报告入口，不把敏感报告统一导向公开 issue；渠道不明时不编造联系人。
- 截图或动图适合展示视觉结果和交互过程，但不能成为必要前提、命令或警告的唯一载体。徽章数量和模板栏目齐全，不证明读者能完成任务。

**真实组织案例：Ruff 与 dbt。** Ruff 的 README 将安装、lint 检查和格式化分别呈现；dbt 的 README 则为安装入门、理解项目、报告问题和贡献代码提供不同入口。

反例混排（教学改写）：把安装、`ruff check`、`ruff format` 和贡献者构建命令放在同一个“依次运行”的代码块里。只想检查代码的人可能误执行格式化，也可能被无关构建流程阻断。

正面组织是先分清任务：

| 当前任务 | 应看到的入口与边界 |
|---|---|
| 用 Ruff 检查 lint 问题 | 指向 `ruff check` 的使用方式，将写回选项与只读检查区分清楚 |
| 用 Ruff 格式化代码 | 指向 `ruff format`，明确普通格式化会写回文件，不能冒充只查看差异 |
| 开始使用 dbt | 指向适用版本的安装与入门文档 |
| 修改 dbt 本身 | 指向贡献指南，不要求普通使用者先学习源码开发流程 |

路径可以是本页的短示例，也可以是准确的外链；是否展开取决于任务能否就此继续，不强求把完整安装矩阵和 API 手册复制到 README。

### 入门教程不能省略决定能否运行的前提

Firecracker 的入门指南先说明演示用途，再列出 Linux/KVM 与 `/dev/kvm` 读写访问等前提。它还在运行步骤前说明：生产运行使用 `jailer` 建立执行隔离，而教程为简化演示不使用它。

反例压缩：“下载镜像，启动 Firecracker，就能部署服务。”它把演示流程包装成生产部署，又删去了决定步骤能否运行的条件。

正面摘要：

> 本演示需要 Linux/KVM 环境及 /dev/kvm 的读写权限。为简化演示，流程省略了 jailer；生产运行使用 jailer 建立执行隔离。

环境前提和演示与生产的区别直接可见；具体检查与部署细节可通过明确入口展开。

### 操作与排错指南给出可观察的反馈

按已有材料写清环境、权限、输入、步骤与预期结果。危险操作的已知影响与既定备份或回退要求应在相应操作前出现；命令、界面入口与输出保持准确。

排错指南从症状和已知状态出发，区分确定原因与候选原因，让每个检查结果导向有依据的下一步。超时不等于失败或回滚；不能在状态未知时默认重试有副作用的操作。运行时错误消息本身的措辞与兼容边界由 [代码表达](code-readability.md#报错与诊断信息) 负责，指南可展开诊断过程，不必把整套流程塞进单条报错。

## 需求说明：先明确要解决的问题

写清用户或系统面临的问题、目标、非目标与真实约束，再给出可观察的验收条件。解决方案不是需求本身；只有架构、技术或协议确为既定约束时，才将其写成必须遵守的条件，并保留依据。

“不够快”“体验更好”“高可用”不足以单独验收。已有指标应保留单位、负载和测量条件；没有约定的 SLO、日期或容量不得编成事实。可以提出待确认指标，但不能把提案悄悄升级为承诺。

**真实案例：Kubernetes KEP-753 的 sidecar 需求。** 该提案要解决普通容器完成后，持续运行的 sidecar 仍妨碍 Job 完成的问题；非目标包括提供任意容器依赖图。这里的 Kubernetes 容器是运行时对象，不是下文 C4 的抽象层级。

反例概括（教学改写）：“支持 sidecar，改善用户体验。”它删掉了可判断的完成语义，也没有界定依赖管理的范围。

正面需求摘要：

> Job 中普通容器完成后，持续运行的 sidecar 不应单独阻止 Job 完成。本项能力不提供任意容器依赖图。

验收围绕 Job 的完成语义设计场景，具体条件与选定版本的规范对应。

## Spec 与独立 API 参考：写出可实现的契约

按对象补足输入、输出、前置条件、状态转换、副作用、错误、资源责任、兼容性和限制；只写与当前契约相关的部分。默认值、空值、单位、超时、重试与幂等语义若影响调用者判断，不能留给其猜测。字段表不能替代字段之间的关系，成功示例也不能替代失败行为。

区分规范要求、解释理由和示例；示例应遵守同一契约。必需与可选、保证与尽力而为不能混写。沿用既有 schema、术语和规范强度，不为统一文风改变机器标识符或公共行为；翻译规范用语时另查 [语言适配](language-adaptation.md)。

规格允许描述尚未实现但已批准的行为，必须明确其状态；现有 API 参考则应准确描述所标版本。新增失败策略或扩大保证属于内容决策，不是普通润色。

### API 说明让成功与失败都可预测

任务是查 Django 的 `QuerySet.get()` 在零个、一个或多个匹配对象时会怎样。

反例压缩：“`get()` 根据查询条件取得对象，异常情况见其他说明。”调用者仍需找出哪些情况属于异常，以及应处理什么异常。

正例，集中呈现这项调用契约：

> `get()` 返回唯一匹配的对象。没有匹配对象时，抛出 `Model.DoesNotExist`；匹配超过一个对象时，抛出 `Model.MultipleObjectsReturned`。这两个异常类属于相应的模型类。

名称、结果与失败条件放在一起，调用者便可按匹配数量确定返回值或异常。

## 架构文档：使用 C4，按问题选择视图

架构文档使用 **C4 模型**，按系统、容器、组件与代码层级组织信息，不用一张混合层级的“全景图”代替边界说明。已有文档沿用其表达约定；层级、职责与关系清楚是共同目标。

- **系统上下文（C1）**：目标软件系统、使用它的人及直接交互的外部系统。解释系统做什么、边界外是谁，不展开内部实现。
- **容器（C2）**：放大一个软件系统，展示其中的应用或数据存储及职责、交互和已知技术。C4 的 container 不是 Docker 容器；部署副本、进程或 Pod 不能机械地各算一个 C4 容器。
- **组件（C3）与代码（C4）**：只有需要解释某个容器内部职责或实现结构时再下钻，不要求所有项目画满四层。
- **动态视图**：当读者需要理解协作顺序、请求或事件流时补充；标明参与元素来自哪些结构视图，不混淆消息先后与静态依赖。
- **部署视图**：当问题涉及运行环境、实例与基础设施映射时补充，明确开发、测试或生产等实际环境；不能从逻辑容器图推断副本数、网络隔离或故障保证。

系统级入门通常从上下文和容器两层开始。局部架构说明可引用已有上层视图，定位本次讨论的元素后只展开必要层级，不为每次改动重画全系统。事实不足时指出缺少的边界或关系，不凭常见技术栈补图。

每张视图给出主题、范围和层级；元素有稳定名称、类型与职责，关系有方向和具体含义。技术或协议只有已知且在该层有用时才标注。相邻视图中的同一对象必须可对应，图中文字应可读，必要含义不能只靠颜色或图形位置传递。

### 正反例：把系统边界与内部职责分开

C4 官方的虚构 Internet Banking System 教学示例（Simon Brown，[系统上下文](https://c4model.com/diagrams/system-context)与[容器图](https://c4model.com/diagrams/container)，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)），可以用以下简化文字摘录区分两层：

| 视图 | 选取的对象与关系 |
|---|---|
| C1：系统上下文 | Personal Banking Customer 使用 Internet Banking System 查询余额、支付；该系统向外部 Core Banking System 获取账户信息、发起支付，并通过 AWS Simple Email Service 发送邮件 |
| C2：放大 Internet Banking System | 系统内有 Static Content、UI、Backend、Statement Store 和 Database；UI 调用 Backend 的 JSON/HTTP API，Backend 访问 Database，并与边界外的 Core Banking System 和邮件系统交互 |

C2 中 UI 是浏览器内的 Angular 应用，Backend 是 Spring Boot 应用，Statement Store 是存储 PDF 的 S3 bucket，Database 是 MySQL schema。它们说明 C4 容器是应用或数据存储的职责边界，而不是统一的部署包装。

反例（教学改写）：把用户、整个银行系统、Backend、某个 Java 方法和三个 Pod 平铺在同一张“C4 容器图”上，箭头一律写“调用”。读者需要自己还原包含关系、抽象层级和部署含义。

正面做法是先在 C1 明确系统与外部对象，再在 C2 展开其内部应用和存储；若要解释 Backend 内部结构或生产副本，分别选择组件或部署视图，而不是继续向 C2 塞入细节。

### 图之外仍要说明关键决定

图回答有哪些对象及其关系，不自动回答为何这样设计。对影响读者判断的决定，写出问题与约束、实际比较过的方案、选择依据和代价；沿用项目已有 ADR 或决策记录，不强制另建系统。

描述现状不能顺便承诺未来架构；提案也不能伪装成既定事实。性能、安全或可用性保证应有相应机制与证据，一条箭头或一个“高可用”标签不构成证明。

## 开发计划：让下一步与完成条件可执行

改写已有计划时，把工作项、依赖、交付物、进入条件与完成判据写清。验证、恢复、回退与发布安排按材料表达，步骤的适用条件和先后关系就近呈现；不借改写改变既定安排。任务要求将设计交给实现时，按设计讨论参考说明下一步能力与完成依据，执行权限仍由当前任务决定。

- 工作项应能对应具体变化或待解决问题，不只写“开发 → 测试 → 上线”。
- 区分已完成、进行中、未开始与受阻。没有实际验证就保留为计划，不能把拟运行的命令写成已通过。
- 依赖应说明“哪个产物或结论可用后才能继续”，不是仅把任务排成列表。
- 负责人、日期、工作量和 SLO 只记录已知或明确标为提议的内容，不填假精确数字。
- 计划足以让执行者从当前材料继续，但小任务无需创建多份状态文件或强制填写空栏目。

**真实组织案例：KEP-753。** 同一份提案把问题与目标、具体方案、Test Plan 和 Graduation Criteria 分开。不同章节分别说明做什么、怎样验证和达到什么条件，读者能找到各自需要的信息。

反例概括（教学改写）：“实现 sidecar；写测试；发布。”执行者无法判断需证明哪项行为，也不知道进入下一阶段需要哪些证据。

正面组织将已有的特性要求、测试内容和阶段条件对应起来，让每个工作项的目标与完成含义可读。

计划中的真实进度、未决问题、决策理由和执行发现属于计划本身的内容，不是应删除的编辑噪声。写“已完成接口定义，兼容性测试尚未运行”有用；写“为了使本文更清晰，我把计划分成四节”则是写作自述，应留在工作材料中。
