# 软件文档

本页处理 README、指南、需求、spec、独立 API 参考、架构与开发计划；源码与注释见[代码表达](code-readability.md)，句段与论证见[文本写作](text-writing.md)，跨章衔接见[长篇组织](long-form-writing.md)。讨论取舍或维护决定时再用[设计讨论与记录](design-discussion.md)。

## 按读者任务组织

按读者当前任务提供内容：

- 判断是否采用、开始使用：适用范围、前提和首次使用路径。
- 确认需求：问题、目标、约束与验收。
- 实现或调用：行为契约。
- 理解架构：边界、职责和选择依据。
- 执行计划：交付、依赖与完成条件。
- 排查故障：症状、已知原因和安全的下一步。

这些职责不等于六份必建文件。复用既有布局，小变更可同页分节；独立查询有稳定入口，完整定义有权威位置，避免在多处各自演化。区分**现状、批准目标、待评审提案和未知项**，标明相关版本、适用范围及实现与 spec 的差异。

## README、教程与操作指南

README 帮读者判断是否适用、完成首次任务并找到后续资料。将使用者与源码贡献者分流，不把构建、测试、发布混入普通安装。

- 使用路径给出已知环境、获取方式、代表任务和预期结果，配置、凭据与权限放在依赖它的动作前。
- 多种安装方式分清替代与连续步骤，模板值换成核实过的内容。
- 详细 API、开发和部署可外链；已有安全报告渠道应可发现，不把敏感报告统一引向公开 issue，也不编联系人。
- 截图可展示交互，不能是必要命令、前提或警告的唯一载体。

**任务分流：** Ruff 分开安装、`ruff check` 与 `ruff format`，dbt 区分入门和贡献入口。将它们混成“依次运行”会让只需检查的人误做写回或贡献者构建；只读检查与写回选项也须区分。

**教程前提：** “下载镜像，启动 Firecracker，就能部署服务”把演示误作生产部署。依据其入门指南，应保留：

> 本演示需要 Linux/KVM 环境及 /dev/kvm 的读写权限。为简化演示，流程省略了 jailer；生产运行使用 jailer 建立执行隔离。

操作指南写清输入、步骤、反馈与失败处理；已知破坏性影响和既定备份、回退要求放在操作前，区分原样命令与占位示意。排错从症状和已知状态推进，区分确定与候选原因；状态未知时不默认重试有副作用的操作。单条[报错](code-readability.md#报错与诊断信息)无需容纳整套指南。

## 需求与验收

写清问题、目标、非目标和真实约束，再给可观察的验收条件。方案不自动等于需求；技术、架构或协议确为既定约束时才作为必须项。

“更快”“高可用”不足以验收。已有指标保留单位、负载和测量条件；未知 SLO、日期与容量不填成承诺，建议标为待确认。

**KEP-753 sidecar 例子：** “支持 sidecar，改善体验”丢失了完成语义。可写为：

> Job 中普通容器完成后，持续运行的 sidecar 不应单独阻止 Job 完成。本项能力不提供任意容器依赖图。

验收对应所选版本的 Job 完成规则。这里是 Kubernetes 运行时容器，不是 C4 抽象层级。

## Spec 与独立 API 参考

按当前契约写输入、输出、前置条件、状态变化、副作用、错误、资源责任及兼容限制。默认值、空值、单位、超时、重试和幂等若影响调用就需交代；字段表不代替字段关系，成功例子不代替失败行为。

区分规范要求、理由与示例，必需与可选、保证与尽力而为；示例遵守契约，沿用 schema 和机器标识符。规范用语翻译见[语言适配](language-adaptation.md)。批准但未实现的 spec 标明状态，现有 API 参考准确对应版本；新增失败策略或保证须有内容变更授权。

例如 Django `QuerySet.get()` 不能只写“取得对象，异常见别处”：

> `get()` 返回唯一匹配的对象。没有匹配对象时，抛出 `Model.DoesNotExist`；匹配超过一个对象时，抛出 `Model.MultipleObjectsReturned`。这两个异常类属于相应的模型类。

## 架构文档：使用 C4，按问题选择视图

架构文档使用 **C4 模型**，按系统、容器、组件与代码层级组织信息，不用一张混合层级的“全景图”代替边界说明。已有文档沿用其表达约定；层级、职责与关系清楚是共同目标。

- **系统上下文（C1）**：目标软件系统、使用它的人及直接交互的外部系统。解释系统做什么、边界外是谁，不展开内部实现。
- **容器（C2）**：放大一个软件系统，展示其中的应用或数据存储及职责、交互和已知技术。C4 的 container 不是 Docker 容器；部署副本、进程或 Pod 不能机械地各算一个 C4 容器。
- **组件（C3）与代码（C4）**：只有需要解释某个容器内部职责或实现结构时再下钻，不要求所有项目画满四层。
- **动态视图**：当读者需要理解协作顺序、请求或事件流时补充；标明参与元素来自哪些结构视图，不混淆消息先后与静态依赖。
- **部署视图**：当问题涉及运行环境、实例与基础设施映射时补充，明确开发、测试或生产等实际环境；不能从逻辑容器图推断副本数、网络隔离或故障保证。

系统级入门通常从上下文和容器两层开始。局部架构说明可引用已有上层视图，定位本次讨论的元素后只展开必要层级，不为每次改动重画全系统。事实不足时指出缺少的边界或关系，不凭常见技术栈补图。

每张视图给出主题、范围和层级；元素有稳定名称、类型与职责，关系有方向和具体含义。技术或协议只有已知且在该层有用时才标注。相邻视图中的同一对象必须可对应，图中文字应可读，必要含义不能只靠颜色或图形位置传递。

### 正反例：把系统边界与内部职责分开

C4 官方的虚构 Internet Banking System 教学示例（Simon Brown，[系统上下文](https://c4model.com/diagrams/system-context)与[容器图](https://c4model.com/diagrams/container)，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)），可以用以下简化文字摘录区分两层：

| 视图 | 选取的对象与关系 |
|---|---|
| C1：系统上下文 | Personal Banking Customer 使用 Internet Banking System 查询余额、支付；该系统向外部 Core Banking System 获取账户信息、发起支付，并通过 AWS Simple Email Service 发送邮件 |
| C2：放大 Internet Banking System | 系统内有 Static Content、UI、Backend、Statement Store 和 Database；UI 调用 Backend 的 JSON/HTTP API，Backend 访问 Database，并与边界外的 Core Banking System 和邮件系统交互 |

C2 中 UI 是浏览器内的 Angular 应用，Backend 是 Spring Boot 应用，Statement Store 是存储 PDF 的 S3 bucket，Database 是 MySQL schema。它们说明 C4 容器是应用或数据存储的职责边界，而不是统一的部署包装。

反例（教学改写）：把用户、整个银行系统、Backend、某个 Java 方法和三个 Pod 平铺在同一张“C4 容器图”上，箭头一律写“调用”。读者需要自己还原包含关系、抽象层级和部署含义。

正面做法是先在 C1 明确系统与外部对象，再在 C2 展开其内部应用和存储；若要解释 Backend 内部结构或生产副本，分别选择组件或部署视图，而不是继续向 C2 塞入细节。

### 图之外仍要说明关键决定

图回答有哪些对象及其关系，不自动回答为何这样设计。对影响读者判断的决定，写出问题与约束、实际比较过的方案、选择依据和代价；沿用项目已有 ADR 或决策记录，不强制另建系统。

描述现状不能顺便承诺未来架构；提案也不能伪装成既定事实。性能、安全或可用性保证应有相应机制与证据，一条箭头或一个“高可用”标签不构成证明。

## 开发计划：让下一步与完成条件可执行

把工作项、依赖、交付物、进入条件和完成判据对应起来；验证、恢复、回退及发布安排按材料保留，不借改写改变政策。

- 工作项指向具体能力或问题，不只写“开发 → 测试 → 上线”。
- 依赖说明哪个产物或结论可用后才能继续。
- 已完成、进行中、未开始与受阻分清；拟运行的命令不写成已验证。
- 负责人、日期、工作量和 SLO 只记已知内容或明确提议，不填假精确数字。
- 小任务不强建多份状态文件，交给实现时沿用设计讨论中的交接方法及原授权。

KEP-753 分开目标、方案、Test Plan 与 Graduation Criteria，使能力、验证和阶段门槛可对应。真实进展、未决项、决定理由和执行发现属于计划正文；“为使本文清晰，我分成四节”属于编辑自述。
