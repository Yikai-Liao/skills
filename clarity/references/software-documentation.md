# 软件文档的重点边界

复用项目布局，区分**当前行为、批准目标、待评审提案与未知项**，标明相关版本。实现与 spec 不一致时让差异可见，不靠改文案决定产品政策。

- README 分开使用者与贡献者路径，替代安装方案不写成连续步骤；不把演示省略的隔离、权限等前提推广为生产条件。
- 操作前就近交代权限、写回或破坏性影响及既有备份回退要求。保留已有私密安全报告入口，不把敏感报告导向公开 issue。
- 需求不擅填 SLO、日期或容量承诺；方案只有确为既定约束时才写成必须项。
- API 和 spec 的改写保留失败、副作用、单位与保证强度，不借“补齐文档”增加重试、幂等或失败策略。独立 API 参考与源码 docstring 各留在读者和工具能找到的位置。
- 计划的依赖、验证、回退和发布要求按已有材料保留。进度、未决项及执行发现属于计划内容，不是编辑噪声；拟执行不写成已验证，小任务不强建多份状态文件。

## 架构文档：使用 C4，按问题选择视图

采用 C4，避免把层级混成一张全景图：

- **系统上下文（C1）**定位系统、使用者和直接交互的外部系统。
- **容器（C2）**展开系统内部应用与数据存储。逻辑 container 不等于 Docker 容器、Pod 或部署副本。
- **组件（C3）与代码（C4）**只在需要解释内部职责或实现时下钻，不要求画满四层。
- **动态视图**解释协作顺序，与静态依赖区分。
- **部署视图**说明实际环境、实例及基础设施映射；不能从逻辑图猜副本数、隔离或故障保证。

局部讨论引用已有上层说明，不重画全系统。各视图中对象能对应，元素职责和关系含义明确；技术、协议与保证只标已知内容。图不代替选择理由与代价，使用已有决定记录。需要讨论或修订决定时再用[设计讨论](design-discussion.md)。

源码命名、注释及单条报错见[代码表达](code-readability.md)；不将完整排错流程塞进报错消息。
