# 代码表达与可预测性

代码既由机器执行，也供人定位、调用、排错和修改。在本次允许的变更范围内降低阅读成本，不能用可读性理由代替设计决策或正确性证明。

本页负责源码组织、命名、源码/API 文档注释、docstring 与运行时报错。README、独立 API 参考、需求、spec、架构说明和开发计划见 [软件文档](software-documentation.md)；短契约可在调用处就近说明，不把完整手册塞进注释。

## 按任务确定需要保留的语义

| 当前任务 | 表达应遵循的约束 |
|---|---|
| 首次编写 | 表达已确定的需求和契约，不凭命名或结构偏好补出业务政策 |
| 早期迭代，已允许破坏性变更 | 可在授权范围内重做名称、接口和结构；保留仍有效的需求及明确保留项，不强加旧版本兼容 |
| 保行为重构或表达改写 | 保持约定的可观察行为和契约，改善内部表达与组织 |
| 功能修改或缺陷修复 | 支持目标行为变化，保留目标变更之外仍有效的语义 |

依据请求和项目约定判断即可，不要求每次填写阶段表。“项目早期”本身不构成破坏性变更授权，已有实现也不自动产生永久兼容义务。

本页负责命名、局部组织、理解路径和必要说明，不制定开发顺序、测试策略、兼容政策、状态管理或内部校验政策。这些决定遵循当前任务与项目约定。

## 表达已确定的意图

调用者应能从签名、名称及必要说明中理解输入、输出、关键条件、副作用、错误和资源责任。只补充当前调用任务所需的信息，不强制另写契约文档或给简单函数套注释模板。

沿用当前有效的领域词汇、数据表示、库能力和语言惯用法。名称和结构应让维护者辨认正常路径、失败条件及其关系，而不是只看到机械步骤。

名称和局部结构表达已有的领域规则，不借改写选择新的业务政策。

## 从读者路径诊断

只追踪判断本次理解问题及改动影响所需的关系。需要诊断跨阶段结构时，可沿以下路径展开：

> 入口 → 参数含义 → 状态来源 → 分支条件 → 副作用 → 结果/错误 → 修改影响

审查发现应能定位到造成负担的代码及依赖；局部命名修改不必记录整条调用链。文件数和跳转数只能提示调查：稳定且清楚的契约可以隐藏大量实现，并不要求读者打开每个 helper。

寻找具体阻力：

- 名称与真实行为不符，例如 `get` 同时删除数据；单位、时区、所有权或数据形状需要猜测。
- 同一状态的多个表示之间存在未说明的同步规则。
- 理解当前分支必须知道远处的隐藏状态、调用顺序或回调协议。
- 一段规则被无语义名称的转发函数拆散，或多个无关规则在同一控制流交错。
- 密集表达式隐藏优先级、短路求值、副作用或错误传播。

## 按调用语境命名函数、类型与变量

同时看定义和代表性调用点：包名、接收者、类型和局部上下文已经说明什么，名称还必须补什么。先确定对象与行为，再选词；职责未清楚时，加长名称不能代替澄清边界。

| 对象 | 名称应帮助读者识别 | 需要核对 |
|---|---|---|
| 函数、方法 | 所做的事、所求的结果或判断，如 `reserve_stock`、`is_expired` | 动作是否真实；读操作是否暗含删除、扣款或持久化；不要让 `get`、`check` 掩盖意外变更 |
| 类、类型、接口 | 领域对象、职责或能力，如 `Invoice`、`RetryPolicy`、Go 的 `Reader` | 名称是否区分值、服务与能力；`Manager`、`Data` 等需结合限定词与职责判断，不按后缀直接判错 |
| 变量、参数、字段 | 当前角色、结果形状及会影响使用的单位，如 `subtotal`、`timeout_seconds` | 是数量还是索引、字节还是字符、输入还是结果；已有单位类型足够明确时不重复编码 |

沿用领域词与目标语言惯例：Python 通常用 `snake_case` 函数和变量、`CapWords` 类；Go 的包前缀和大小写还承担语境与导出语义；.NET 的接口前缀等约定不推广成跨语言要求。短作用域中明确的 `i`、`n`、`src`、`dst` 可以保留；跨较长流程使用的 `data`、`tmp` 若需反复回查，应补出缺失角色。名称更长并不自动更清楚。

布尔名称应让分支读作明确判断，减少需要反复心算的双重否定；准确的否定领域状态仍可保留。`is_`、`has_`、`can_` 只是常见表达，不保证无副作用；名称、类型、注释与行为须共同成立。一个名字也不必塞下完整的错误、幂等性、阻塞和资源契约。

### 真实名称：Go io 与 Python pathlib

Go go1.23.0 的 `io.Reader` 表示读取能力，`io.ReadCloser` 组合读取与关闭能力；`io.Copy(dst Writer, src Reader)` 用短参数名与类型说明数据方向。接口名称不规定具体调用者何时负责关闭，`Copy` 的成功返回规则也须读契约：成功返回的错误是 `nil`，而非 `EOF`。把名称扩成整段协议不会更好。

CPython v3.13.0 的 `PurePath` 提供不访问文件系统的路径操作；`Path` 在此基础上提供可执行系统调用的方法。前者处理路径本身，后者还提供检查或操作磁盘状态的能力；具体调用是否产生 I/O，由所用方法决定。

### 改名时保留外部契约

同一符号在闭包、调用点与动态引用中的名称应保持对应。公开函数和参数、JSON 键、数据库字段、反射注册名、命令行选项或模块导入路径可能被外部使用。改名范围与兼容性遵循当前任务约定；同名对象也可能是不同符号。保留仍受协议或语言约束的拼写，例如 Python 特殊方法。

自拟例子：JSON 协议固定返回 `timeout_ms`，内部处理以秒为单位。保留协议键和单位换算，使用局部变量 `timeout_seconds = payload["timeout_ms"] / 1000`。若原逻辑还有舍入、溢出或缺省值约定，改写须一并保留。

## 让概念和执行关系直接可见

在代码中，结构可见意味着维护者能辨认判断、处理阶段、状态变化与失败边界。若理解某次修改必须先把表达式反解成工作流，或跨多个无意义 helper 拼回一条规则，应指出这些额外操作，而不只统计行数。

- **命名有意义的结果**：表达式中已有小计、折扣、有效范围等概念时，用局部名称让它们可见；不要只增加 `part1`、`temp2` 等解码层。
- **按职责划阶段**：将需要一起理解或修改的规则聚在一起。解析外部表示、领域计算、输出构造可以有不同边界；阶段之间传递明确的数据，不让后续规则反复解释前一阶段的内部表示。
- **区分命名与提取**：给表达式中的概念命名，用局部变量。需要复用一段处理，或隔离包含多个步骤的完整职责时，可以提取函数或模块，让调用者能从名称和契约理解职责，不必展开其内部步骤。简单取值、计算和转发按下文的小 helper 规则处理。
- **让错误结构贴合资源生命周期**：无清理工作的前置失败可以早返回；共享资源的路径可集中清理。不要为了拆条件重复退出逻辑，或为了少写清理代码把不同资源状态混成一个出口。
- **保留完整的单一规则**：共同表达一个概念的布尔式、查表或惯用法可以紧凑。只有它隐藏了独立职责或关系时才展开，不把每次调用、每个运算符都变成独立阶段。

结构改动应有具体收益：让读者直接识别一个概念、独立理解一条规则，或少追踪一项依赖。仅增加换行、`if` 或 helper 数量不构成收益。这是选择改法的依据，不是要求在代码交付前另附说明；审查时再结合具体位置展开。

### 内联小 helper，不压平概念

对本次修改涉及的一两行私有取值、计算或转发 helper，若既没有现有复用，也没有明确的复用计划，默认内联到使用它的函数中。已有复用或明确复用计划的，不套用这条默认内联规则；“也许以后有用”不算明确计划。不要仅为给这一步起名字而保留函数；需要表达概念时，用当前函数内的局部变量命名结果。

例如，`payload` 为普通字典，`_get_items` 只在 `item_names` 中使用，没有动态引用，也没有其他调用方的复用计划：

```python
def _get_items(payload):
    return payload["items"]

def item_names(payload):
    return [item["name"] for item in _get_items(payload)]
```

去掉这个转发函数，在调用处直接取得集合：

```python
def item_names(payload):
    items = payload["items"]
    return [item["name"] for item in items]
```

内联后，若表达式混合了小计、折扣、运费等不同计算阶段，就在同一函数内分别赋给有意义的局部变量，再组合结果，如下面的运费例子。不要把这些阶段压成一个大表达式，也不要为每个阶段重新建一个一行 helper。只表达一个完整判断的布尔式可以直接保留，不必把每个运算都拆开，如后面的版本比较例子。

### 例一：命名计算中的领域概念

任务是调整运费政策而不改变商品折扣。参数为普通数值，读取和计算无副作用。

反例，公式已经换行，读者仍需从乘减运算中分辨各项费用：

```python
return (
    unit_price * quantity
    - max(quantity - discount_after, 0) * unit_price * discount_rate
    + min(unit_price * quantity * shipping_rate, shipping_cap)
)
```

正例，把同一公式中的小计、享受折扣的数量、折扣额和运费直接命名，不新增函数：

```python
subtotal = unit_price * quantity
discounted_units = max(quantity - discount_after, 0)
discount = discounted_units * unit_price * discount_rate
shipping = min(subtotal * shipping_rate, shipping_cap)
return subtotal - discount + shipping
```

原式的运费按折扣前小计计算；命名不能顺手改成按折后金额计算。输入来自 getter、惰性读取或有副作用的调用时，求值次数和时机也是需要保留的语义。

### 例二：让处理阶段与资源责任对应

任务是理解模块编译流程，以及代码生成失败后哪些步骤仍会执行。把 AST 遍历、指令生成、优化组装和作用域清理的全部细节堆进入口，会迫使读者同时追踪不同层次的知识；仅用空行或通用的 `step1()`、`step2()` 包装仍然没有明确边界。

下面的组织保留真正的编译职责与共同的作用域退出路径：

```c
static PyCodeObject *
compiler_mod(struct compiler *c, mod_ty mod)
{
    PyCodeObject *co = NULL;
    int addNone = mod->kind != Expression_kind;
    if (compiler_enter_anonymous_scope(c, mod) < 0) {
        return NULL;
    }
    if (compiler_codegen(c, mod) < 0) {
        goto finally;
    }
    co = optimize_and_assemble(c, addNone);
finally:
    compiler_exit_scope(c);
    return co;
}
```

`compiler_codegen` 负责按 AST 类型生成指令；`optimize_and_assemble` 承接编译单元进行后续处理。进入作用域失败时直接返回，成功进入后则无论代码生成或组装是否成功，都退出作用域。入口显示职责和生命周期，阶段内部承载具体算法。

### 例三：保留已经完整的紧凑规则

以下版本比较是一个完整概念，可以直接表达：

```go
func (t *transferReader) protoAtLeast(m, n int) bool {
    return t.ProtoMajor > m || (t.ProtoMajor == m && t.ProtoMinor >= n)
}
```

这个例子说明不必把主版本比较、相等检查和次版本比较拆成三个 helper，不是要求为版本判断单独建函数。若本次涉及的实现既没有现有复用，也没有明确的复用计划，就把整个判断内联到调用处；需要命名时使用局部布尔变量。类似地，同一错误处置下的一组简单校验可以合并；复杂流程则需要显露阶段。

## 选择最小改动

| 证据 | 可选改动 | 必须防止 |
|---|---|---|
| 名称使人误认对象或单位 | 同时查看定义和调用点，使用最简单且准确的名称 | 删除必要单位；未授权改变公共名称或序列化字段 |
| 缺少一项语义关系 | 补充类型、局部中间量、契约或简短注释 | 为一次局部问题新增通用框架 |
| 嵌套隐藏主路径 | 守卫分支、阶段组织、显式状态处理 | 未经授权改变错误优先级、清理路径或锁的持有范围 |
| 跳转不能提供有用抽象 | 就地合并相关逻辑或消除无意义转发 | 内联已有深模块，扩大调用者必须知道的细节 |
| 表达式中的概念被隐藏 | 用局部变量命名结果 | 仅为给一步计算起名字而新建 helper |
| 多步处理的完整职责混在其他流程中，或有复用需要 | 提取有明确契约的函数或模块；小 helper 遵循前述内联规则 | 为凑短函数拆碎同一不变量 |
| 状态名称混淆当前值、快照或派生结果 | 区分名称，并在必要处说明各自角色与更新关系 | 以命名或说明改进为由擅自删除状态、缓存或同步机制 |

概念重叠不等于可合并。选择取决于知识和变化是否相同，不根据类型字段或代码外形相似作决定。

## 源码注释与 API 文档注释

代码注释是维护信息的一部分。对不直观的实现、bug 修复和性能取舍，应主动留下后续读者需要的解释，不要求仅靠代码表达全部意图。

- 名称表达可直接看见的动作；注释解释读者无法从局部代码推断的原因、契约、单位、算法依据和约束。
- API 文档注释必须说明调用者需要的行为与失败语义，不能把“注释只写 why”理解成禁止说明 what。
- 面向文档工具的内容放在该工具能识别的位置，例如 Python 的 docstring；不能迁到生成文档或 `help()` 无法读取的普通行注释。沿用项目约定，不强制每个私有函数填写完整文档模板。
- 意外处给出已有材料支持的原因，例如某层不重试，因为另一个明确命名的组件负责重试。不编造责任归属来填充注释。
- 可以说明为什么修改旧实现、为什么选现在的方案，以及这样改的收益和代价。只删除没有技术信息的聊天流水账、编辑计划和自评，不因注释提到修复经过或方案比较就删除。
- 文档、签名、示例与实际行为一致；不以易读为名翻译机器必须精确匹配的标识符。

### API 注释不是实现过程的复述

任务是用 Go 的 `strings.IndexRune` 查找字符，并判断是否找到。公共注释说明搜索的是 Unicode 码点、未找到时返回 `-1`，还说明 `utf8.RuneError` 的特殊处理。这些不能仅从函数名推出。

反例压缩：“返回字符的位置。”它没有交代未找到的结果，也没有让读者区分字节偏移与字符序号。

正面说明应保留已有边界，并明确结果单位。普通字符查询的两个例子是：

```go
strings.IndexRune("中国", '国') // 3：字节偏移，不是字符序号。
strings.IndexRune("中国", '美') // -1：未找到。
```

调用者可直接从例子取得普通字符查询的结果单位与未找到状态；特殊输入仍按 API 注释中的约定处理。

### Bug 与性能修复

在关键改动附近，按需要写清触发条件、旧方案为何失效、当前方案避免了什么问题，以及哪些看似更简单的改法会重新引入缺陷。不必每条注释都填满一套模板。

例如，支付接口以幂等键去重时：

```ts
// 超时不代表支付失败，服务端可能已完成扣款。
// 重试必须复用原幂等键；生成新键可能导致再次扣款。
```

性能修复应说明节省了什么工作、适用负载和必要代价。实现因批处理、缓存、预分配、索引或特殊分支而更难读时，把这些原因留在代码旁；不要为了恢复表面的简洁而撤销有依据的优化。

CPython 的 `list_resize` 在源码旁解释了适量预留容量与连续追加的摊销成本。维护者若只看到容量计算公式，可能将额外空间误当成可以直接去掉的浪费。

反例注释：“这里已经优化过，请勿修改。”它没有说明优化依赖什么，也无法支持未来判断。

正例，保留机制与取舍：

```c
/* 按扩容策略预留额外容量，减少连续追加时的反复分配与可能的搬移。
   用一定的空闲容量换取长序列追加的摊销效率，而非每次都按当前长度精确分配。 */
```

有实测数据时可以记录收益，并带上影响解释的负载、环境或可追溯的 benchmark 位置。只有复杂度或机制分析时，说明减少了哪些工作，不编造延迟、吞吐或内存改善数字。

关键原因应在局部可读；长篇复现过程、完整性能报告和方案实验可放到 issue、测试或项目文档，并链接真实存在的记录。链接补充解释，不替代代码旁防止误改所需的最少信息。后续行为或约束变化时同步更新注释，避免留下失效的修复说明。

## 报错与诊断信息

报错信息应帮助目标读者识别失败并决定下一步，不只是宣布“出错了”。修改措辞不自动授权修改错误处理机制。

- 指明失败的操作和对象，以及已经确定的原因或违反的条件。区分确定原因、候选原因与未知原因；不能把所有 I/O 失败都归为权限不足。
- 在影响后续操作时说明已知结果：尚未执行、部分完成，还是状态未知。超时本身不能证明操作失败或已经回滚。
- 给出有依据且在权限范围内可采取的下一步。无法确定修复方式时，提供必要的诊断或求助入口；不编造按钮、参数、文档地址，也不默认建议提权、关闭校验或直接重试。
- 保留有助于定位的文件位置、字段名、错误标识或关联编号；不要为了“上下文完整”输出凭据和无关敏感内容。面向普通用户的消息与维护者诊断可以分层，不默认将全部堆栈展示给每位读者。
- 已有错误码、异常类型、退出状态、输出通道和结构化字段可能被程序使用。人类消息与机器契约各有用途；机器依赖的名称及消息原文按当前任务的兼容约定保留。

### 定位、原因与建议各自承担信息

Rust 的所有权示例中，`let s2 = s1;` 移走一个 `String`，随后 `println!` 又使用 `s1`。编译诊断不仅给出 `E0382`，还标出移动发生处、再次使用处，以及该类型不实现 `Copy` 的原因。

反例改写（教学压缩）：“编译失败，请检查变量。”它保留失败结论，却让读者重新搜索位置并推断关系。

正面案例中的诊断要点包括：

```text
error[E0382]: borrow of moved value: `s1`
```

它将这一摘要与两处源码标记连接，并给出有条件的建议：

```text
help: consider cloning the value if the performance cost is acceptable
```

保留源码位置与性能条件，让维护者按本次任务的所有权和性能要求选择修复。

### 用已知数量与约束解释失败

任务是理解一次资源请求为何被拒绝。已知请求为 2.0 CPUs，`us-central-1` 区域配额为 1.0 CPUs。

反例：“无法获取资源，配额不足。”

正例：

> 请求的 2.0 CPUs 超出 us-central-1 区域的 1.0 CPUs 配额。可申请提高该区域配额；若其他区域有足够配额，且任务允许跨区域执行，也可选择其他区域。

请求量、上限和约束范围让读者能够定位问题；替代区域是有条件的方案，不能忽略数据驻留、资源依赖或权限要求。若系统没有提供请求量，就不能为了凑齐这类消息而猜出数字。

## 跨编程语言适配

原则共同，语法与惯用法各异。Go 的显式错误处理、Python 的常见推导式、Rust 的所有权和匹配、SQL 的集合表达均可能减少本语言读者的工作。不要把所有语言改成同一种逐步命令式风格。

惰性与急切求值、同步与异步异常、空值与真值、整数溢出、Unicode、求值顺序、资源释放和并发都是代码含义的一部分；表达改写应保持任务要求保留的语义。

示例：把 TypeScript 的 `async function load() { return await api.load(); }` 改成普通函数直接返回 `api.load()`，可能改变同步抛错如何暴露给调用者。不能因为少了包装就自动接受。
