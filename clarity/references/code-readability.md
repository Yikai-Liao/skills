# 代码表达的重点边界

表达已有需求与契约，不借可读性决定业务、测试、兼容、状态管理或校验政策。保行为重构保持约定行为；功能修改及获准破坏性迭代遵循目标需求与仍有效的契约，不强加旧行为兼容。

## 命名、内联与概念结构

名称结合定义、类型和调用语境判断，不靠加长名称补救职责不明。短作用域中的清楚惯用名可以保留；公开参数、协议键、反射与动态引用按授权范围改，不为统一风格改机器契约。

**本次涉及的一两行私有取值、计算或转发 helper，若无现有复用且无明确复用计划，默认内联。** “也许以后用到”不算计划；只为给一步计算命名时，用局部变量。

内联不等于压平概念。小计、折扣、运费等不同计算仍用有意义的局部名称，再组合结果，不挤成大表达式。完整的布尔判断、查表或惯用法可紧凑保留，不按运算符拆步骤。

有复用或需隔离多步完整职责时，可提取有清楚契约的函数；稳定的深模块无需为少跳转而内联。依据知识与变化边界选择结构，不按行数或外形相似合并，也不拆碎同一不变量。

## 改写的行为边界

只追踪当前理解问题所需的关系，局部改名不要求全调用链报告。保持仍有效的求值次数与顺序、短路、副作用、同步/异步异常、数值与 Unicode 语义、资源清理及锁范围。少一层包装不自动等价，例如 async 包装可能改变同步抛错的暴露方式。

澄清当前值、快照、派生结果和更新关系，不授权删除状态、缓存或同步机制。没有具体理解问题时不为显示改动而重构。

## 注释与文档工具

非显然实现应主动留下维护理由，不能只靠“代码自解释”或将原因全部外移。bug 修复说明触发条件、旧做法的问题、修复依据及防回退约束；性能取舍说明省了什么工作、适用条件与代价，不因优化让实现更绕就撤销它。

保留有技术信息的修改历史，删聊天流水与自评。长报告可外链，防止误改的关键原因仍在代码旁。没有实测不编收益数字，行为变化时同步更新说明。

API 文档注释需要行为与失败语义，不限于 why；docstring 不迁到文档工具或 `help()` 读不到的普通注释中。私有函数不强填统一模板。

## 报错与诊断信息

区分操作结果、已知原因、候选原因与未知。超时不等于失败或回滚，不默认建议重试、提权或关闭校验；下一步须有事实与权限依据。

保留必要位置、标识及条件，不编按钮、数字或地址，不泄露凭据。人类消息可改写，机器依赖的错误码、异常、退出状态、通道、字段及消息原文遵循兼容约定。措辞修改不授权改错误机制。
