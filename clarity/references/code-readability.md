# 代码表达的重点边界

表达已有需求与契约，不借可读性决定业务、测试、兼容、状态管理或校验政策。保行为重构保持约定行为；功能修改及获准破坏性迭代遵循目标需求与仍有效的契约，不强加旧行为兼容。

## 主流程与局部细节

让读者看清当前操作的阶段、状态变化和外部效果，避免低层遍历、构造与计算反复打断业务决策。名称结合定义、类型和调用语境判断，不靠加长名称补救职责不明；短作用域中的清楚惯用名可以保留。

成功路径埋在多层分支里、阶段交错或临时状态跨很远仍需追踪时，针对具体障碍选择提前返回、局部变量或阶段提取。保留分支优先级、短路与清理关系，不把所有嵌套一律拉平。

**多步完整阶段即使只调用一次，也可提取。** 依据是输入、输出与效果边界清楚，名称能解释阶段职责，调用处能凭契约理解主流程。相关 helper 按项目习惯就近组织。若需要传递大量相互依赖的可变状态、万能上下文或模式开关，或拆散同一不变量、事务与资源生命周期，应重选边界；把复杂块搬入泛称的 process/handle 函数或增加多层转发，并未提供有效概念。

**本次涉及的一两行私有取值、计算或转发 helper，若无现有复用且无明确复用计划，默认内联。** “也许以后用到”不算计划；只为给一步计算命名时，用局部变量。此默认不用于上述多步完整阶段。内联后仍保留有意义的中间概念，不挤成大表达式；完整的布尔判断、查表或惯用法可紧凑保留，不按运算符拆步骤。

函数长、缩进深是检查信号，不是拆分命令。平坦规则表、连贯算法和需要一起审计的状态转换可以保持完整；稳定深模块不为少跳转而内联，也不按外形相似合并。公开参数、协议键、反射与动态引用按授权范围改，不为统一风格改机器契约。

判断结构是否更清楚时，结合完整受影响函数与直接相关的 helper 阅读，检查主路径、阶段职责、状态变化和失败出口。若提取后仍须逐层打开 helper 拼装含义，或不变量与远处状态更难追踪，应调整边界。只修具体阅读问题，不扩大为全调用链检查或例行自评报告。

## 改写的行为边界

只追踪当前理解问题所需的关系，局部改名不要求全调用链报告。保持仍有效的求值次数与顺序、短路、副作用、同步/异步异常、数值与 Unicode 语义、资源清理及锁范围。少一层包装不自动等价，例如 async 包装可能改变同步抛错的暴露方式。

澄清当前值、快照、派生结果和更新关系，不授权删除状态、缓存或同步机制。没有具体理解问题时不为显示改动而重构。

## 注释与文档工具

非显然实现应主动留下维护理由，不能只靠“代码自解释”或将原因全部外移。bug 修复说明触发条件、旧做法的问题、修复依据及防回退约束；性能取舍说明省了什么工作、适用条件与代价，不因优化让实现更绕就撤销它。

保留有技术信息的修改历史，删聊天流水与自评。长报告可外链，防止误改的关键原因仍在代码旁。没有实测不编收益数字，行为变化时同步更新说明。

API 文档注释需要行为与失败语义，不限于 why；docstring 不迁到文档工具或 `help()` 读不到的普通注释中。私有函数不强填统一模板。

## 报错与诊断信息

区分操作结果、已知原因、候选原因与未知。超时不等于失败或回滚，不默认建议重试、提权或关闭校验；下一步须有事实与权限依据。

保留必要位置、标识及条件，不编按钮、数字或地址，不泄露凭据。人类消息可改写，机器依赖的错误码、异常、退出状态、通道、字段及消息原文遵循兼容约定。措辞修改不授权改错误机制。
