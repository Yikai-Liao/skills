# 文本写作

## 从材料写成作品

围绕“读者读完后应知道什么或能做什么”选择内容。材料是证据和素材，不是现成目录。

- 中心问题与回答相称。解释性作品可以围绕问题展开，不必硬造一个争议论点。
- 对象、条件、关系、行动、证据和边界服务于读者任务；只供作者理解的背景不必全部进入正文。
- 组织方式可采用问题到答案、步骤到结果、机制到后果、方案比较、时间演进或叙事推进。
- 段落之间有明确关系。大纲可以是列表，成品不必因此成为清单。
- 会话回复承接双方已有的上下文；持久化正文补上读者未参与对话也需要知道的背景。

不要把“完整”理解成无所不包。必要解释留在主阅读路径；低频细节放在深入说明或附录，并给读者清楚的入口。

## 顺着读者的理解往下讲

先找到读者已经知道的对象、问题或场景，再介绍这次新增的内容。段落持续围绕当前问题推进；转换到原因、后果或另一对象时，交代它与前文的关系。专业背景相同，也不表示读者知道作者刚查到的项目事实。

写清谁做什么，让术语概括已经能理解的内容。连续堆放“责任转移、状态一致性、恢复成本”等词，可能要求读者先自行还原整个过程。需要这些概念时，沿真实场景解释它们怎样发生；具体例子优先取自当前讨论，避免为讲清一件事先引入一套陌生系统。

例如，双方正在讨论精简设计工作流程，已知要删除固定目录和审批表，同时保留决定记录、处理设计与实现差异及保存未完成工作。下面两种说明的信息组织不同：

**难以接续的概括：**

> 去掉形式约束，保留决策连续性、偏移处理与交付闭环。

**展开实际动作：**

> 我会去掉固定目录和审批表。但讨论过的决定仍要记下来。之后代码和设计不一致，要查清原因，再决定改哪边。工作没做完，也要留下记录，方便下次继续。

第二段承接当前话题，让动作之间的关系可见。它不是要求所有说明都用短句；熟悉的抽象、长句与简洁术语可以减少重复解释。判断改写是否有用，要看读者需要自行补出的关系是否减少，不能只看字数、段落数或作者觉得是否顺口。

## 分开正文与编辑材料

普通文本没有供维护代码使用的行内注释层，写进去的话会成为作品内容。不要照搬代码中“这里为什么改、为什么改成这样”的维护习惯，解说本段文字的写作或修改过程。故障复盘、技术方案等若以修复原因和收益为主题，则正常展开这些内容。

将提纲、选材理由、术语选择、取舍备忘、待查标记和质量自评留在工作材料中，不把它们改成流畅句子后放进正文。也不要用 HTML 注释或脚注把未获要求的编辑材料藏在成品里。

| 混入正文的编辑话语 | 处理方式 |
|---|---|
| “为了降低读者的认知负担，本节先给结论。” | 删去写作理由，直接给结论 |
| “下面采用三个维度组织材料，这样更有解释力。” | 删除结构自评；若分类依据关系到主题，写出具体维度和实际依据 |
| “这里保留限制条件，以免过度宣称结果。” | 直接写影响结论的限制条件 |
| “本文依据某写作指南整理，示例由本助手改写。” | 普通成品不收录；需追溯制作来源时放在单独的维护记录中，保留依法或依约要求的署名 |

不要按“因为”“为了”“本章”等字样机械删除。研究报告为什么选择某种采样方法、算法为什么需要某个条件、操作为什么有风险，都可能是读者需要的内容。真实的方法说明、文献引用、证据局限和必要导航应保留；删除的是作者对写作行为的解说与辩护。

例如，把“为保持严谨，这里不把观察写成因果；我们只观察了 200 人且没有对照组”改为“本次观察涵盖 200 人，未设对照组，因果关系尚未确定”。事实和判断仍在，写作自述被移除。

用户要求编辑说明时，将成品与简短的修改摘要分开交付；摘要只列关键变化和待确认项，不复述逐步起草、权衡与自检过程。

## 让解释闭合

关键概念第一次承担推理作用时，给出足够信息：

- 它指什么对象或现象，与熟悉概念有什么关系；
- 在什么条件下，谁对什么做了什么；
- 产生什么结果，为什么与当前问题有关；
- 在什么边界之外不适用。

按读者已有知识决定解释深度，不机械重复这四项。专家文档可以直接使用领域通用术语；面向新人的书需要把必要关系展开。

引用证明或补充说明，不能代替缺失的解释。“采用统一框架后效果更好”若承担核心结论，应说明统一了什么、改变了什么、与什么比较、改善了哪个结果；材料没有这些信息时明确留缺，不能编出机制或数字。

类比可帮助建立初始理解：说明对应关系，再回到实际对象。读者在当前推理中可能误用类比时，指出具体差异；日常解释无需例行附加“类比有局限”。

## 组织段落与句子

- 每段承担一个可命名的概念任务；段内可以有多个支持步骤。转折、因果、例证和条件应能从内容得到支持。
- 常规说明段可先给要点，再给支持它的依据；影响当前判断的条件就近交代。推导或叙事可以先铺垫，让读者知道当前在探索什么。
- 句子主语、动作对象和代词指向应在当前上下文中可恢复。隐藏责任主体会误导时才补出主体，不能因偏好主动句而猜测行为者。
- 一个长句若含多个需要分别判断的条件，可拆成主规则和例外，或用决策表。拆句后重新核对否定范围、因果和限定关系。
- 删除没有新增事实或功能的套话。保留必要的概念复现、风险提示、推导步骤和面向独立阅读者的简短回顾。
- 保留作者适合任务的语气和节奏。不要把专业论述改成宣传口号，也不要把故事改成管理摘要。

### 让对比、纠正与限定回应实际问题

先确认前后内容是补充、细化、条件、因果、比较还是纠正，再选择连接方式。使用“不是……而是……”“虽然……但是……”“这本身不足以”等表达时，检查被纠正的观点来自哪里，以及这次纠正是否回应当前任务。没有否定词的“有人把……当成……，真正重要的是……”也可能虚构反驳对象。

- **比较有对应关系**：在同一问题和相关标准下呈现差异，保留各方实际贡献。互补环节可以同时成立，不为突出后一项而贬低前一项。涉及优劣或“一半对、一半错”的判断，应指出具体维度和依据。
- **纠正有语境动因**：已出现的错误，或有具体材料、措辞或使用情境支持且会影响任务的合理误解，都值得澄清。“没人明确说过”不是判错的充分条件；“读者可能误解”也不能替代具体依据。
- **假设表明身份与用途**：教学、澄清或检验可以设想观点，须明确它是假设，并说明它帮助理解哪个问题。不要用“有人认为”冒充实际群体的立场，或把反驳假设写成已经驳倒对方。
- **评价保持任务、范围与强度**：对“有助于理解”的例子，先检查它是否解释清楚；对“证明普遍结论”的证据，检查支持范围。不把有帮助换成独立解决、部分证据换成足以确证、已有进展换成全部交付、条件有效换成普遍可靠，再以更高标准否定原判断。
- **限定给出实际边界**：保留影响判断的样本范围、反例、风险和不确定性；说明它限制哪个结论或动作。仅说“事情没这么简单”而未增加内容时，补出已知限制，或删去这句空泛评价。

以下是按已给语境改写的教学例子，不是对句式的禁用表：

| 语境与原表达 | 处理 |
|---|---|
| 仅需说明排查方法，且日志与测试都参与定位：“排错不是看日志，而是写测试。” | “日志帮助定位异常路径，测试用于复现并检查修复。”保留互补职责；若某次任务确有理由排除一种方法，再说明具体原因 |
| 前文只说例子帮助理解，回应却是：“但一个例子本身不能证明普遍规律。” | 先评价例子解释了什么、哪里仍不清楚；没有证明任务时，不额外要求它证明普遍规律。若例子确实引出过度概括，则指出越界的具体结论 |
| 用户说“这个 PR 合并后，项目有了实质进展”，回应却是“一个 PR 完成，不代表整个项目已经全部交付”。 | 指出“已有进展”被换成“全部交付”；是否取得进展应按该 PR 的实际贡献判断，不以未全部交付否定进展 |
| 只需总结材料，草稿却写“有人可能认为，存在提案就表示功能已上线”，材料与任务均无此误解依据。 | 删除虚构的纠正对象，按材料总结实际状态；不另造一个群体持有该观点 |
| 任务是说明项目状态审计中各类材料的证据效力：“提案不能当成已上线事实，一个 PR 完成也不等于跨 PR 的目标已经全部交付。” | 直接回答证据判定边界，可保留；不因无人声称已经上线或全部交付而判为空心人论证 |
| 发布页面将“提案获批”与“已上线”放在同一栏，读者要据此判断能否使用功能，尚无人明确误读。 | 可预先区分两种状态；页面的混排及使用判断提供了具体依据，不必等读者说错 |
| 初稿误写周三，现已核实周四：“会议不是周三，而是周四。” | 保留纠正；读者有明确的旧信息需要更新。只问日期且没有误解背景时，直接答“周四”即可 |
| 叙事已交代人物盼望对方认错：“他等的不是一封信，而是一句道歉。” | 可保留这次情感重心转移，不按字面互斥标准删去文学修辞 |

纠正对象明确时，直接给出更正；原稿存在连续设限时，按下一节判断其作用。不要把“不是……而是……”机械换成“不仅……而且……”，制造原本不存在的递进关系。

改写连接关系也受保真和授权约束：材料不足时不能猜成因果、互补或主次关系。需要实质改动主张时，明确提出建议，不冒充纯措辞调整。

### 典型问题：方法说明变成无依据的纠偏

**实验结果：把材料汇总改成统一审计，预先贬低证据。**

> 无论实验由谁执行，都核对相同的信息：目标版本、环境、命令或探针、原始输出、实际观察，以及没有覆盖的部分。探针是用于区分某种行为的具体输入或操作。作者摘要和绿色 CI 只帮助定位结果；旧版本的结果不能自动为已经改变的新机制背书。

当任务是汇总已有实验结果，且没有要求建立审计规范时，这段话没有报告结果，而是新增了统一核对要求。“只帮助定位”还在没有检查摘要内容、CI 检查项及其适用范围前，先行降格了两类材料。末句又引入“用旧结果为新机制背书”的推论，却未指出谁提出了它、哪份材料造成了这种误解，或当前哪项结论受版本变化影响。补充“探针”的定义不能修复这些偏移。

改写应回到已有结果。自拟材料若为“作者报告修复了重复提交；当前提交的 CI 中，重复提交回归测试已通过”，摘要可写为：

> 作者报告已修复重复提交问题；当前提交的 CI 中，重复提交回归测试已通过。

这里保留作者报告与 CI 结果各自的内容及归属。若材料只给出 CI 通过，就只报告这一状态，不补造检查项。任务确实要求审计时，按已有审计要求说明核对项；实际发现版本错配时，指出具体错配。例如，已知报告声称 v2 的重试机制通过测试，而引用日志来自 v1，可以写“所引日志来自 v1，未提供 v2 重试机制的测试结果”。不要将这类具体问题扩写成对所有摘要、CI 或历史结果的统一贬低。

**设计论证：在有效方法后追加两个假想错误。**

> 设计还没有实现代码时，可以用已知上下界证明机制矛盾或资源无界；必须依赖尚未取得的测量时，则说明需要验证的假设及其到期阶段。不要套用代码 base/head 标签，也不因缺少 benchmark 就直接认定设计错误。

前半段在说明设计阶段的论证方法和待验证假设，后半段却转去纠正“套用代码标签”与“缺少 benchmark 就判错”。在没有这些做法或合理误解依据的语境中，两个禁令都没有回应前面的任务。问题不是 `base/head` 或 `benchmark` 这些术语，而是说明被自行添加的反驳对象带偏了。

若当前任务确实要求说明上述设计评审方法，并已要求标明假设的验证阶段，可保留为：

> 设计尚未实现时，可用已知上下界证明机制矛盾或资源无界。结论依赖尚未取得的测量时，列出待验证的假设及应完成验证的阶段。

验证阶段的要求来自该任务，不由 clarity 为所有设计工作新增。若原评审确实把“缺少 benchmark”作为判错理由，则直接回应这项实际判断，并说明它影响哪个结论；不要把这样的纠正例行追加到设计说明中。

### 直接陈述边界，清除防御性套话

**连续否定是检查信号，不是判错依据。** 先检查每项排除是否有明确对象和任务用途。必要的边界可直接说明；当段落围绕自行添加的错误推论展开，或让读者从排除项还原所需事实时，再删除或重组。

- **空泛提醒删除**：“不能一概而论”“事情没有这么简单”“仍需进一步验证”等在语境中没有具体对象或信息贡献时删去。不要为了保留一句提醒而编造缺口、风险或后续工作；必要信息按其实际含义保留。
- **有问题的设限整段重组**：去掉无依据或无关的纠正对象，将有用内容写成结果、条件或具体缺口。逐项否定即使为真，也不能代替相关性判断；改成“尚不足以”“仍难以”、拆成多句或移到脚注，不会消除仍然存在的主张替换。
- **限定落在对象上，信息保持完整**：材料已给单机测试范围和多节点未测状态，就写“本次测试覆盖单机部署，多节点部署尚未测试”。材料未交代测试范围时，保持原有事实，不猜测测试缺陷，也不因此自动追问。
- **结论说完即可结束**：已在结果中写清的样本、时间或条件，不在段尾重复降温。只有任务需要下一步、且材料支持具体行动时才写行动。原稿中已有的验证安排、发布门槛或实质建议按保真要求保留，直接写清对象与动作；“建议进一步验证”不能代替行动内容。

| 已给材料与任务 | 合格表达 |
|---|---|
| 只报告结果：单机测试，吞吐量从 100 提升到 140 请求/秒。草稿另加“这并不意味着所有场景都有效，仍需进一步验证”。 | “单机测试中，吞吐量从 100 提升到 140 请求/秒。” |
| 部署说明已知单机测试通过、多节点和断电恢复尚未测试，原稿却写“仅凭单机通过，不能说多节点已通过，也不能说断电恢复已通过”。 | “单机测试已通过；多节点部署和断电恢复尚未测试。” |
| 研究结论明确写明：观察到相关性，因果关系尚未确定。 | “本研究观察到相关性，因果关系尚未确定。”保留判断本身，不替换成无关的样本描述。 |
| 接口文档要划清职责：“该接口既不负责鉴权，也不负责重试。”两项职责排除均已确认。 | 原句可以保留；它直接说明接口边界，没有虚构待反驳的立场。 |
| 教学任务要求用假设例子解释“获批”和“上线”的区别。 | “假设一项提案周一获批、周五才部署。周二查到批准记录，只能确认提案已获批；功能仍待部署。”假设身份与教学用途明确。 |
| 操作要求：运行期间禁止拔出设备，否则会损坏数据。 | “运行期间禁止拔出设备，否则会损坏数据。”具体禁令直接保留。 |

逐字引语保留原话；文学对话中的迟疑、否认或重复按人物与叙事任务处理。指令中的权限禁令、代码中的否定条件也保留准确含义。整段验收看它是否延续当前问题，以及原有范围、否定判断和未知状态是否仍在，不按否定词数量裁决。

### 让条件、依据与结论各有归属

将共同支持一个判断的内容放在一起，让前提、例外和结果的适用关系直接可见。不要把多个判断压进一串转折，也不要把必要条件移到远处，让读者自己重组规则。

反例，读者需要判断申请是否可以提交：

> 资料完整并获经理批准后可提交申请，不过超过五万元的还要经财务复核，而缺发票的要先补交，复核未通过也不能提交。

正例：

> 提交申请前，资料必须完整，并获得经理批准。缺少发票时，先补交发票。金额超过五万元的申请，还须通过财务复核。

这里分开了共同前提、材料缺失时的动作和额外审批条件，保留金额阈值与通过要求。说明一个完整关系的长句仍可保留；不把所有正文都改成短句或清单。

## 按文体交付

### 会话解释与汇报

用户没有要求写文章时，也要组织好解释、进展和调研结果。先回答当前问题，补上理解这个回答所需的背景；工具输出和研究材料经过选择后再呈现，不把收集顺序直接变成报告目录。

让用户看得出这一轮解决了什么，哪些细节可留待需要时再读。关键原因、代价和条件就近解释，支持材料给准确入口；一串链接或只有术语的摘要会把理解工作推回给读者。没有固定的字数、表格或分层要求，完整推导有需要就充分展开。

用户追问某一处时，先解释那一处，并承接已有名称和结论。用户反馈读起来费劲时，调整内容与解释顺序；不要默认降低专业程度，或反复重发全文。理解问题可以在解释后结束，不必每轮都让用户选择、批准或执行下一步。

会话里有用的解释需要保存时，去掉依赖对话才能理解的指代，补齐实际背景和来源，成为可独立阅读的正文。日常答疑和状态回复不因此自动创建文件。需要持续讨论架构并记录决定时，使用[设计讨论与记录](design-discussion.md)。

### 文档与操作指南

围绕实际任务写出前提、权限、所需输入、执行步骤、预期结果、失败处理。只保留相关项，不用空标题凑模板。

材料中已有的破坏性动作影响、备份或回退要求，放在依赖它们的操作之前。命令的占位符必须可辨识，原样命令与示意片段有清楚区别。

解释页说明为什么与怎样工作；查询页提供稳定定义、参数、默认值和边界；教程帮助读者完成一次有反馈的学习过程。多种角色可以相邻，但不要把读者寻找参数的入口埋在教程中。

软件 README、开发与使用指南、需求、spec、C4 架构文档和开发计划见 [软件文档](software-documentation.md)。

### 报告与决策材料

围绕待作出的判断安排问题、结论与关键依据。材料中影响决策的限制和风险就近交代；任务要求行动时再写有依据的下一步。描述性报告可在结果处结束。

区分观测结果、解释和建议；保留已给材料中影响理解的样本、时间范围、比较基线、单位和证据限制。用这些具体信息界定结论，避免自行追加因果质疑、泛化警告或验证建议。

摘要保留决定是否适用的关键条件和负面结果。把方法细节移到附录可以降低检索成本，但不能把会改变决策的限定一起移走。

### 研究论文：让贡献与证据链对应

以研究问题和材料能支持的贡献组织论文。标题让读者识别对象与主旨，摘要让读者理解问题、做法、关键结果及必要边界；不要为标题响亮而夸大结论，也不要为“只有一个中心”删去相互关联的多面贡献、负面结果或不确定性。

| 阅读入口 | 应提供的信息 |
|---|---|
| 标题与摘要 | 准确的研究对象、问题或贡献；摘要概括所用方法、关键结果和结论范围，保留影响解释的条件 |
| 引言 | 已知背景、真实待解问题及其意义，说明本研究回答什么；不把“尚无人研究”当作可随意补写的创新依据 |
| 方法与结果 | 读者核对结论所需的方法、对照和证据；按论证依赖组织结果，区分观察与解释，不能因方法读者较少就省略复现条件 |
| 讨论 | 结果怎样回答原问题，与已有工作的关系、解释限制及有依据的后续方向；不强行宣布缺口已全部填补 |
| 图表与图注 | 所展示的对象、单位、条件与必要方法，使跳读者能理解图示含义；图标题或醒目图形不能代替图注和证据条件 |

“背景—内容—结论”（CCC）可以检查解释是否闭合：读者为何需要这项内容，看到了什么，从中可得什么。对经验研究论文，它是一种可用组织方式；具体章节、段落顺序和摘要格式仍须服从学科、期刊与读者任务。综述、理论、方法或复现论文也有各自的证据结构，不机械填入同一套实验故事。

相关证据集中呈现，平行论据可以用对应形式，术语保持一致。标题、摘要、结果与讨论允许为不同阅读入口作必要回顾；不要把“减少来回跳转”变成“每个主题只能出现一次”。围绕贡献组织也不能改变实际实验步骤、选择性隐藏不利数据，或倒造预注册的假设与研究时间线。

**真实摘要案例：否定句的语境研究。** Nordmeyer 与 Frank 的研究先提出“为什么真实且合语法的否定句在某些情境中仍显得奇怪”，再报告两项成人情境判断实验，并说明支持性情境中否定句的合宜度评分更高。

反例压缩（教学改写）：“研究证明否定句不好，应全面使用肯定句。”它删除了实验中的语境条件，把特定观察扩成普遍禁令。

正面摘要摘述：

> 研究通过两项成人情境判断实验，考察否定句的合宜度如何随语境变化。在提供支持性语境时，真实否定句获得更高的合宜度评分。这些结果支持从语境中的信息价值解释否定句的合宜度。

这段摘述按问题、实验、结果和解释组织，语境条件与对应的评分结果放在一起。

标题、摘要与图表是重要阅读入口，方法与必要限制同样必须准确。问题、证据与结论的关系应从正文中读出；大纲和段落职责笔记不混入成品。

### 书籍与章节

明确本章在全书中带来的知识或体验变化。知识类章节让概念在需要时出现，并通过例子、解释、反例或练习逐步建立关系；叙事类章节维护时间、视角、人物和信息揭示的连贯性。

章首不必都写“本章将介绍”，章末也不必都列三条总结。回顾应帮助下一个阅读动作，不机械复述。跨章组织和恢复写作见 [长篇组织](long-form-writing.md)。

## 组织文档路径与阅读入口

先看读者要找什么、各页承担什么职责，再决定哪些内容同页、分文件或分目录。目录树、发布导航和源码模块树可以不同；精确参考常按接口对象组织，操作指南按目标组织，版本或受众确有独立需要时再划界。

- **分组有可说出的职责**：把共同服务一项任务或需要一起维护的材料聚在一起。增加一层目录应带来可辨识的主题、权限、版本或生命周期边界；层数没有统一最优值。少量页面可直接由入口页分流，不为套分类建立空目录。
- **入口能帮助选择**：从根 README、站点导航或章节目录给出目的明确的链接；跨主题任务通过导航串联，避免为每种访问路径复制正文。低频参考可另页保存，影响执行的关键条件仍在使用点可得。
- **路径可预测且稳定**：文件名表达长期主题或任务，例如 `configure-access.md`；上级目录已经提供的语境无需逐层重复。`misc.md`、`notes-final-2.md` 若承载长期指导，应按内容职责命名；有实际用途的日期、版本和迁移编号则保留。
- **服从载体约定**：新建面向跨平台发布的路径，可用小写 ASCII 与连字符；既有语言、生成器和项目规范优先。`README.md`、`SKILL.md`、`AGENTS.md` 等机器识别名称保留精确拼写，不为统一外观改名。文件地址与中文页面标题各司其职，无需把所有标题改成英文。

可见标题、文件地址与机器加载名称各有用途。标题不清楚时可以只改标题；文件改名、锚点和已发布 URL 遵循任务既定的兼容约定。导航文字与目标内容应相符。

### 真实入口：Wagtail 区分初学、开发与编辑任务

Wagtail 6.4.1 的文档首页提供 “First steps”“Using Wagtail”“For editors” 三组快捷入口，编辑者被引向单独的指南；完整目录另列教程、主题、参考、部署等内容。“Your first Wagtail site” 则带新手依次准备环境、建立站点、创建管理员并启动服务。入口承诺与代表页内容相符，源码目录并未逐层照搬成读者唯一的导航。

可迁移的是按任务分流的关系，不是目录数量。自拟的小工具只有安装、备份操作和配置项三页时，`docs/install.md`、`docs/backup.md`、`docs/configuration.md` 配合一份入口即可；当恢复与排错材料增长并形成独立任务，再考虑分组。不要先创建四套空壳，或把每次审查报告平铺成长期入口。

## 命名文章、章节与段落

页面标题承诺整篇的主要内容；章节标题区分下属问题，层级表达包含关系。同级标题应有可比较的职责，通用规则不能误放在某个案例标题下。标题级别按语义选择，不用跳级模拟字号；独立 Markdown 页面通常用一个 H1 标识主题，汇编和出版系统遵循其结构约定。

- **按内容职责措辞**：操作节可用“配置访问权限”，概念节可用“权限继承规则”，查询节可用“权限字段”；同页可并用。研究标题按对象、问题或有边界的发现命名，不强制动词化；文学标题可以保留作品需要的隐喻与悬念。
- **在实际入口中辨识**：检查目录、搜索结果、浏览器页签或深链接中，读者能否区分目的地。必要时补对象，如把独立的“其他问题”改为“备份失败排查”；上下文清楚的“安装”不必机械扩成一串关键词。
- **标题与内容互相约束**：正文应兑现标题，标题不能宣称材料未支持的原因、结论或覆盖范围。一个标题下若混有不同层次的任务，先调归属或拆节；不要靠一个更长的标题掩盖混杂，也不凭标题对称补造不存在的内容。
- **段落可命名，不必都挂牌**：可以在草稿中用“提出问题”“解释机制”“交代例外”检查段落职责；成品中的主题句直接表达具体内容，不贴这些编辑标签。只有读者确需定位一组内容时才加小标题；短文和连续叙事可以不设小标题。

自拟例子：一页同时讲令牌过期时间和更新步骤，标题“令牌有效期与续期”可用“有效期规则”“续期步骤”两节。若同页还混入作者的测试流水，应将流水移到合适的工作记录，而不是用“其他说明”吸收它。维护场景确需测试证据时，另给用途明确的入口。

## 版式承担信息功能

- 顺序操作用编号，平行项目用项目符号，稳定维度的比较用表格。需要展开因果、论证或体验时使用连续段落。
- 表格明确列名、单位、条件和缺失值；不把多段推理硬塞进单元格。
- 链接文字说明目的地。关键条件不只放在悬浮提示中；重要差异不只靠颜色传达。图片承载必要信息时提供文字说明或替代文本。
- 交叉引用指向承载所述内容的位置；只剩迁移提示的旧页不适合作为内容入口。已有锚点按当前兼容约定保留。

## 保真改写：主张与指代

### 区分措辞调整与主张变更

原文：

> 本次测试中，采用新缓存配置后，错误率从 4% 降至 2%。这证明它解决了稳定性问题，建议全面推广。

用户已授权删去总体稳定性判断和推广建议，只保留测试结果时：

> 本次测试中，采用新缓存配置后，错误率从 4% 降至 2%。

这里删除了两项实质内容，属于主张变更。只做语言润色时，原主张保持不变。结果句本身无需附带一段因果质疑。

以下写法作为反例排除：

> 这一结果说明测试期间的错误率有所下降，但仅凭这次测试，还不能确定下降由新配置造成，也不能确认其他场景会有相同效果。全面推广前需要补充验证。

它复述数字，连续否定可能的结论，又追加空泛行动。材料没有交代实验设计，改写者却据此追加了因果质疑和推广前的验证要求。修复时删去这段追加内容，停在授权范围内的结果陈述。

### 指代清楚时保留原文

> 服务读取配置后，将它缓存在内存中。

“它”清楚地指向配置，句子可以原样保留。改为“服务读取配置后，将配置缓存在内存中”没有实质改善，也不需要为润色调查缓存实现。

多个指向确实影响理解时，指出具体歧义。改写保持材料已有的含义，不靠替换代词补出新的因果或职责关系。
