# 文本写作

## 从材料写成作品

围绕“读者读完后应知道什么或能做什么”选择内容。材料提供证据和素材，正文按问题、步骤、因果、比较或叙事需要组织，不照搬收集顺序。解释不必硬造争议，大纲是列表也不意味着成品必须是清单。

必要解释留在主阅读路径；只供作者理解的背景可以省去，低频细节给出深入阅读入口。会话承接双方已知内容，持久化文本补齐未参与对话的读者所需背景。

## 顺着读者的理解往下讲

从读者已知的对象、问题或场景引入新内容，再沿动作、原因和结果展开。专业背景相同，不表示读者知道作者刚查到的项目事实。关键概念参与推理时，应能知道它指什么、谁在什么条件下做什么，以及结果为何与当前问题有关。

连续堆放“责任转移、状态一致性、恢复成本”等词，可能让读者自行还原过程。优先用当前讨论中的真实场景解释，再用术语概括；避免为讲清一件事先引入一套陌生系统。

例如，双方正在讨论精简设计工作流程，已知要删除固定目录和审批表，同时保留决定记录、处理设计与实现差异及保存未完成工作。下面两种说明的信息组织不同：

**难以接续的概括：**

> 去掉形式约束，保留决策连续性、偏移处理与交付闭环。

**展开实际动作：**

> 我会去掉固定目录和审批表。但讨论过的决定仍要记下来。之后代码和设计不一致，要查清原因，再决定改哪边。工作没做完，也要留下记录，方便下次继续。

这里展开的是当前话题中的动作，而非只把术语拆成短句。熟悉的抽象可以直接使用；解释深度取决于读者还需补出哪些关系。

引用补充证据，不代替解释。例如，“采用统一框架后效果更好”承担核心结论时，要说明统一了什么、与什么比较、改善了哪个结果及适用范围；材料缺少的机制或数字不能编造。类比先说明对应关系，再回到实际对象；只在当前推理可能误用时指出具体差异，无需例行附加“类比有局限”。

## 分开正文与编辑材料

正文呈现主题内容，提纲、选材与选词理由、待查标记和质量自评留在工作材料中，也不藏进 HTML 注释或脚注。用户要求修改说明时，将关键变化和待确认项与成品分开交付。

| 混入正文的编辑话语 | 处理方式 |
|---|---|
| “为了降低读者的认知负担，本节先给结论。” | 直接给结论 |
| “下面采用三个维度组织材料，这样更有解释力。” | 写出与主题有关的维度和分类依据，删除结构自评 |
| “这里保留限制条件，以免过度宣称结果。” | 直接写影响结论的限制条件 |
| “本文依据某写作指南整理，示例由本助手改写。” | 普通成品不收录；需追溯制作来源时放在单独的维护记录中，保留依法或依约要求的署名 |

研究方法、文献引用、证据局限、操作风险和必要导航属于主题内容。故障复盘以修复原因为主题，代码注释也需要维护理由；不能因为出现“为什么改”“为了”就删除。

## 组织段落与句子

- 每段推进一个问题或概念；说明通常先给要点和依据，推导或叙事可以先铺垫。转换对象或进入原因、例证时，关系应可辨认。
- 主语、动作对象和指代在当前上下文中可恢复。隐藏主体会误导时才补出主体，不因偏好主动句而猜测行为者。
- 多个需分别判断的条件可分成主规则与例外，或用决策表；保留原有否定范围、因果与限定关系。
- 删除无贡献的套话，保留必要回顾、推导、风险提示及作者适合任务的语气，不把故事改成管理摘要。

### 让对比、纠正与限定回应实际问题

先确认内容之间是补充、条件、因果、比较还是纠正，再选择连接方式。比较应针对同一问题和相关标准，保留各方实际贡献；纠正应有原主张或具体误解语境，保持其任务、范围与强度。教学假设标明身份与用途，不冒充实际立场。

以下场景用于区分内容关系，不是句式禁用表：

| 语境与原表达 | 处理 |
|---|---|
| 日志与测试都参与排查，却写“排错不是看日志，而是写测试”。 | 写清互补职责：“日志帮助定位异常路径，测试用于复现并检查修复。” |
| 前文只说例子帮助理解，却回应“一个例子不能证明普遍规律”。 | 评价解释是否清楚；确有过度概括时，再指出越界的结论 |
| 对“这个 PR 带来实质进展”回应“一个 PR 不代表全部交付”。 | 按实际贡献评价进展，不将主张换成“全部交付”再否定 |
| 汇总材料时凭空加上“有人认为有提案就已上线”。 | 删除虚构立场，报告实际状态 |
| 状态审计要求区分证据效力：“提案不能当成已上线事实。” | 保留；说明直接回应审计问题，无需等到有人说错 |
| 发布页混排获批与上线，读者要据此判断功能能否使用，尚无人反馈误读。 | 可以预先澄清两种状态；依据是混排和使用情境 |
| 已核实日期，纠正原通知：“会议不是周三，而是周四。” | 保留明确更正；没有旧信息需要更正时，直接答日期 |
| 人物盼望对方认错：“他等的不是一封信，而是一句道歉。” | 保留符合叙事的情感重心转移 |

无否定词的“有人把……当成……，真正重要的是……”也可能虚构立场。判断内容关系后再改写，不机械把“不是……而是……”换成“不仅……而且……”，也不猜造因果、互补或主次关系。

### 典型问题：方法说明变成无依据的纠偏

**实验结果：把材料汇总改成统一审计，预先贬低证据。**

> 无论实验由谁执行，都核对相同的信息：目标版本、环境、命令或探针、原始输出、实际观察，以及没有覆盖的部分。探针是用于区分某种行为的具体输入或操作。作者摘要和绿色 CI 只帮助定位结果；旧版本的结果不能自动为已经改变的新机制背书。

任务只要求汇总实验结果时，这段话却新增审计要求，未经核对就降格摘要与 CI，并纠正没有语境依据的“旧结果为新机制背书”。补充术语定义不能解决偏题。

若材料确已给出修复报告和对应回归测试结果，可直接写：

> 作者报告已修复重复提交问题；当前提交的 CI 中，重复提交回归测试已通过。

只给出 CI 通过时，不补造检查项。任务要求审计时按已有要求核对；若实际发现报告声称 v2 重试机制通过测试，所引日志却来自 v1，应指出：“所引日志来自 v1，未提供 v2 重试机制的测试结果。”具体错配不代表所有历史结果无效。

**设计论证：在有效方法后追加两个假想错误。**

> 设计还没有实现代码时，可以用已知上下界证明机制矛盾或资源无界；必须依赖尚未取得的测量时，则说明需要验证的假设及其到期阶段。不要套用代码 base/head 标签，也不因缺少 benchmark 就直接认定设计错误。

任务已要求说明论证方法及假设的验证阶段，却没有上述两种误判的语境时，末句添加了无关纠偏。保留任务所需内容：

> 设计尚未实现时，可用已知上下界证明机制矛盾或资源无界。结论依赖尚未取得的测量时，列出待验证的假设及应完成验证的阶段。

若评审确实以“缺少 benchmark”判错，再回应那项判断。这里的验证阶段要求来自给定任务，不是所有设计工作的新流程。

### 直接陈述边界，清除防御性套话

主文件的直接表达规则在这里按场景展开。**连续否定是检查信号，不是判错依据**：删除无依据的纠偏和无信息的提醒，把有用内容写成结果、条件或具体缺口。仅换词、拆句或移到脚注，不能修复主张替换。

| 已给材料与任务 | 合格表达 |
|---|---|
| 只报告结果：单机测试，吞吐量从 100 提升到 140 请求/秒。草稿另加“这并不意味着所有场景都有效，仍需进一步验证”。 | “单机测试中，吞吐量从 100 提升到 140 请求/秒。” |
| 部署说明已知单机测试通过、多节点和断电恢复尚未测试，原稿却写“仅凭单机通过，不能说多节点已通过，也不能说断电恢复已通过”。 | “单机测试已通过；多节点部署和断电恢复尚未测试。” |
| 研究结论明确写明：观察到相关性，因果关系尚未确定。 | “本研究观察到相关性，因果关系尚未确定。”保留判断本身，不替换成无关的样本描述。 |
| 接口文档要划清职责：“该接口既不负责鉴权，也不负责重试。”两项职责排除均已确认。 | 原句可以保留；它直接说明接口边界，没有虚构待反驳的立场。 |
| 教学任务要求用假设例子解释“获批”和“上线”的区别。 | “假设一项提案周一获批、周五才部署。周二查到批准记录，只能确认提案已获批；功能仍待部署。”假设身份与教学用途明确。 |
| 操作要求：运行期间禁止拔出设备，否则会损坏数据。 | “运行期间禁止拔出设备，否则会损坏数据。”具体禁令直接保留。 |

材料未给出的范围和缺陷不自行补写，也不为保留提醒而增加追问。结论说完可结束；原有验证安排、发布门槛和实质建议仍须保留，写清对象与动作。逐字引语保持原话；文学对话按叙事需要处理，权限禁令与代码否定条件保留准确含义。

### 让条件、依据与结论各有归属

把共同前提、额外条件与对应动作放在一起，让读者能直接判断规则怎样适用。

反例，读者需要判断申请是否可以提交：

> 资料完整并获经理批准后可提交申请，不过超过五万元的还要经财务复核，而缺发票的要先补交，复核未通过也不能提交。

正例：

> 提交申请前，资料必须完整，并获得经理批准。缺少发票时，先补交发票。金额超过五万元的申请，还须通过财务复核。

改写区分了共同前提和额外审批条件，保留金额阈值及通过要求。长句本已清楚表达完整关系时，可以保留。

## 按文体交付

### 会话解释与汇报

先回答这一轮的问题，再补必要背景、原因、代价与条件，给支持材料的准确入口；不以一串链接或术语摘要代替解释。需要完整推导时就展开，不限定字数、表格或分层形式。

用户追问某一处时，先解释那一处，并承接已有名称和结论。用户反馈读起来费劲时，调整内容与解释顺序；不要默认降低专业程度，或反复重发全文。理解问题可以在解释后结束，不必每轮都让用户选择、批准或执行下一步。

会话里有用的解释需要保存时，去掉依赖对话才能理解的指代，补齐实际背景和来源，成为可独立阅读的正文。日常答疑和状态回复不因此自动创建文件。需要持续讨论架构并记录决定时，使用[设计讨论与记录](design-discussion.md)。

### 文档与操作指南

围绕实际任务写出前提、权限、所需输入、执行步骤、预期结果、失败处理。只保留相关项，不用空标题凑模板。

材料中已有的破坏性动作影响、备份或回退要求，放在依赖它们的操作之前。命令的占位符必须可辨识，原样命令与示意片段有清楚区别。

解释页说明为什么与怎样工作；查询页提供稳定定义、参数、默认值和边界；教程帮助读者完成一次有反馈的学习过程。多种角色可以相邻，但不要把读者寻找参数的入口埋在教程中。

软件 README、开发与使用指南、需求、spec、C4 架构文档和开发计划见 [软件文档](software-documentation.md)。

### 报告与决策材料

围绕待作出的判断安排结论与依据，区分观测、解释和建议。样本、时间、比较基线、单位、证据限制与风险就近界定相关结论；摘要同样保留影响判断的条件和负面结果，方法细节可放附录。

描述性报告可在结果处结束；需要行动时再给有依据的下一步，不例行追加因果质疑或验证建议。

### 研究论文：让贡献与证据链对应

以研究问题和材料能支持的贡献组织论文；保留相互关联的多面贡献、负面结果与不确定性，不为突出中心而删去。

| 阅读入口 | 应提供的信息 |
|---|---|
| 标题与摘要 | 准确的研究对象、问题或贡献；摘要概括所用方法、关键结果和结论范围，保留影响解释的条件 |
| 引言 | 已知背景、真实待解问题及其意义，说明本研究回答什么；不把“尚无人研究”当作可随意补写的创新依据 |
| 方法与结果 | 读者核对结论所需的方法、对照和证据；按论证依赖组织结果，区分观察与解释，不能因方法读者较少就省略复现条件 |
| 讨论 | 结果怎样回答原问题，与已有工作的关系、解释限制及有依据的后续方向；不强行宣布缺口已全部填补 |
| 图表与图注 | 所展示的对象、单位、条件与必要方法，使跳读者能理解图示含义；图标题或醒目图形不能代替图注和证据条件 |

“背景—内容—结论”（CCC）可检查读者为何需要这项内容、看到了什么、从中可得什么；章节与摘要仍服从学科、期刊和论文类型，不将综述、理论或复现论文套进同一实验故事。

相关证据集中呈现，术语一致；不同阅读入口可有必要回顾。不能为组织贡献而改写实际实验步骤、隐藏不利数据，或倒造预注册假设和研究时间线。

**真实摘要案例：** Nordmeyer 与 Frank 研究真实且合语法的否定句为何在某些情境中仍显得奇怪。

反例压缩（教学改写）：“研究证明否定句不好，应全面使用肯定句。”它删除了实验中的语境条件，把特定观察扩成普遍禁令。

正面摘要摘述：

> 研究通过两项成人情境判断实验，考察否定句的合宜度如何随语境变化。在提供支持性语境时，真实否定句获得更高的合宜度评分。这些结果支持从语境中的信息价值解释否定句的合宜度。

语境条件与评分结果在同一段中，不会因摘要而丢失。

### 书籍与章节

明确本章在全书中带来的知识或体验变化。知识类章节让概念在需要时出现，并通过例子、解释、反例或练习逐步建立关系；叙事类章节维护时间、视角、人物和信息揭示的连贯性。

章首不必都写“本章将介绍”，章末也不必都列三条总结。回顾应帮助下一个阅读动作，不机械复述。跨章组织和恢复写作见 [长篇组织](long-form-writing.md)。

## 组织文档路径与阅读入口

先看读者要找什么、各页承担什么职责，再决定哪些内容同页、分文件或分目录。目录树、发布导航和源码模块树可以不同；精确参考常按接口对象组织，操作指南按目标组织，版本或受众确有独立需要时再划界。

- **分组有可说出的职责**：把共同服务一项任务或需要一起维护的材料聚在一起。增加一层目录应带来可辨识的主题、权限、版本或生命周期边界；层数没有统一最优值。少量页面可直接由入口页分流，不为套分类建立空目录。
- **入口能帮助选择**：从根 README、站点导航或章节目录给出目的明确的链接；跨主题任务通过导航串联，避免为每种访问路径复制正文。低频参考可另页保存，影响执行的关键条件仍在使用点可得。
- **路径可预测且稳定**：文件名表达长期主题或任务，例如 `configure-access.md`；上级目录已经提供的语境无需逐层重复。`misc.md`、`notes-final-2.md` 若承载长期指导，应按内容职责命名；有实际用途的日期、版本和迁移编号则保留。
- **服从载体约定**：新建面向跨平台发布的路径，可用小写 ASCII 与连字符；既有语言、生成器和项目规范优先。`README.md`、`SKILL.md`、`AGENTS.md` 等机器识别名称保留精确拼写，不为统一外观改名。文件地址与中文页面标题各司其职，无需把所有标题改成英文。

可见标题、文件地址与机器加载名称各有用途。标题不清楚时可以只改标题；文件改名、锚点和已发布 URL 遵循任务既定的兼容约定。导航文字与目标内容应相符。

### 真实入口：Wagtail 区分初学、开发与编辑任务

Wagtail 6.4.1 的文档首页用 “First steps”“Using Wagtail”“For editors” 分流读者，编辑者进入单独的指南；“Your first Wagtail site” 带新手依次准备环境、建站、创建管理员并启动服务。导航按使用任务组织，而非照搬源码目录。

可迁移的是按任务分流的关系，不是目录数量。自拟的小工具只有安装、备份操作和配置项三页时，`docs/install.md`、`docs/backup.md`、`docs/configuration.md` 配合一份入口即可；当恢复与排错材料增长并形成独立任务，再考虑分组。不要先创建四套空壳，或把每次审查报告平铺成长期入口。

## 命名文章、章节与段落

页面标题承诺整篇的主要内容；章节标题区分下属问题，层级表达包含关系。同级标题应有可比较的职责，通用规则不能误放在某个案例标题下。标题级别按语义选择，不用跳级模拟字号；独立 Markdown 页面通常用一个 H1 标识主题，汇编和出版系统遵循其结构约定。

- **按内容职责措辞**：操作节可用“配置访问权限”，概念节可用“权限继承规则”，查询节可用“权限字段”；同页可并用。研究标题按对象、问题或有边界的发现命名，不强制动词化；文学标题可以保留作品需要的隐喻与悬念。
- **在实际入口中辨识**：检查目录、搜索结果、浏览器页签或深链接中，读者能否区分目的地。必要时补对象，如把独立的“其他问题”改为“备份失败排查”；上下文清楚的“安装”不必机械扩成一串关键词。
- **标题与内容互相约束**：正文应兑现标题，标题不能宣称材料未支持的原因、结论或覆盖范围。一个标题下若混有不同层次的任务，先调归属或拆节；不要靠一个更长的标题掩盖混杂，也不凭标题对称补造不存在的内容。
- **段落可命名，不必都挂牌**：可以在草稿中用“提出问题”“解释机制”“交代例外”检查段落职责；成品中的主题句直接表达具体内容，不贴这些编辑标签。只有读者确需定位一组内容时才加小标题；短文和连续叙事可以不设小标题。

自拟例子：一页同时讲令牌过期时间和更新步骤，标题“令牌有效期与续期”可用“有效期规则”“续期步骤”两节。若同页还混入作者的测试流水，应将流水移到合适的工作记录，而不是用“其他说明”吸收它。维护场景确需测试证据时，另给用途明确的入口。

## 版式承担信息功能

- 顺序操作用编号，平行项目用项目符号，稳定维度的比较用表格。需要展开因果、论证或体验时使用连续段落。
- 表格明确列名、单位、条件和缺失值；不把多段推理硬塞进单元格。
- 链接文字说明目的地。关键条件不只放在悬浮提示中；重要差异不只靠颜色传达。图片承载必要信息时提供文字说明或替代文本。
- 交叉引用指向承载所述内容的位置；只剩迁移提示的旧页不适合作为内容入口。已有锚点按当前兼容约定保留。

## 保真改写：主张与指代

### 区分措辞调整与主张变更

原文：

> 本次测试中，采用新缓存配置后，错误率从 4% 降至 2%。这证明它解决了稳定性问题，建议全面推广。

用户已授权删去总体稳定性判断和推广建议，只保留测试结果时：

> 本次测试中，采用新缓存配置后，错误率从 4% 降至 2%。

这里删除了两项实质内容，属于主张变更。只做语言润色时，原主张保持不变。结果句本身无需附带一段因果质疑。

以下写法作为反例排除：

> 这一结果说明测试期间的错误率有所下降，但仅凭这次测试，还不能确定下降由新配置造成，也不能确认其他场景会有相同效果。全面推广前需要补充验证。

材料没有交代实验设计，这段改写却添加了因果质疑、泛化警告和验证要求。应删去追加内容，停在授权保留的结果处。

### 指代清楚时保留原文

> 服务读取配置后，将它缓存在内存中。

“它”清楚地指向配置，句子可以原样保留。改为“服务读取配置后，将配置缓存在内存中”没有实质改善，也不需要为润色调查缓存实现。

多个指向确实影响理解时，指出具体歧义。改写保持材料已有的含义，不靠替换代词补出新的因果或职责关系。
