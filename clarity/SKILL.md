# 面向读者的清晰写作

让目标读者以尽可能少的**不必要工作**，找到所需内容，建立准确理解，并据此阅读、判断、操作或修改。必要的推导、专业概念和文学体验可以保留；降低理解成本不等于减少信息量。

## 先确定交付

- **起草**交付作品，**改写**交付修订内容，**审查**交付有证据的问题。不要用诊断替代用户要的正文，也不要在只要求审查时修改源文件。
- 读者、任务、体裁、阅读方式和必须保留的含义，以请求和现有材料为准。信息足够就动笔；只有缺口会改变实质内容、结构或语义时才提问。
- 产物使用用户指定的语言；未指定时沿用已有作品的语言，新作品沿用请求的语言。不要因为技能说明是中文而把英文稿改成中文。
- 局部改写只读取必要上下文，不建立全书工作区或全仓库审查流程。多受众可用摘要、主文和深入说明分层服务。

## 共同判断

先判断阻力来自意图、结构、依赖还是措辞，在根因处修复，不把所有任务都变成逐句润色。

- **用途和阅读路径**：读者知道当前内容解决什么。决策材料通常先给结论，将影响决策的条件就近写清；教程按知识依赖推进，操作提示先于危险动作；叙事和推导不强制答案先行。
- **概念与名称**：同一概念保持稳定称呼，不同概念保持区别。名称应在读者实际看到的路径、标题或调用语境中说明对象与职责；简单且准确比最短更重要，不能为统一词汇而把相近对象合并。
- **局部理解**：必要条件、证据关系和不变量在使用点可得。用足够解释与直接引用减少回查，而不是复制全部定义或内联所有实现。
- **结构可见**：让表达结构显露内容的概念边界与关系，不把结构还原的工作留给读者。过度压缩会迫使读者自行拆解，过度拆散会迫使读者跨处拼装；按有意义的概念组织，不按句长、行数或层数机械拆分。
- **足够信息**：写清必要的对象、操作、因果和边界；删除无贡献的噪声。标签、连接词、引用和简短表达不能替代缺失的解释。
- **关系与评价相称**：按内容的真实关系组织比较、转折与限定，回应原主张的任务和强度。纠正应有可指认的对象或合理预期；不要先强化对方的主张，再以更高标准否定它。
- **意外可解释**：在违反合理预期处说明真实原因或约束，不复述显然行为，也不编造原因填补空白。

检查结构时，选一个读者任务，指出理解前必须自行拆分、命名或拼装的部分及关系。若这些额外操作由表达方式造成，就通过清晰分组、局部命名或有意义的抽象使结构直接可见。熟悉的惯用法和必要的领域复杂性不因此被判错。

## 直接表达（必读）

以下规则适用于本技能所有任务中自己撰写的正文、审查回复、交付说明和代码注释。直接给出事实、判断、条件和动作；**防御性设限是需要消除的表达模式**，即使夹有有效信息，也要重写。

- **空泛设限整句删除**：“不能一概而论”“事情没有这么简单”“仍需进一步验证”等没有具体内容的句子，直接删去，不再润色，也不为保留它们编造风险或后续工作。
- **连续否定必须重组**：遇到“仅凭……还不能……也不能……”“这并不意味着……更不意味着……”及同义表达，直接交代结果、适用范围或具体缺口，不逐项罗列读者“不该得出什么”。限制属实也要重组；换成“尚不足以”“仍难以”、拆成多句或移入脚注，均不算修复。
- **有明确否定对象，直接说清**：材料已确认故障仍存在，就写“该配置未消除故障”，不用“这并不意味着该配置已经消除了故障”绕着说。否定判断有自己的含义；数据、未知状态与无效结论分别保留，不能互相代换。
- **限定写在对象上**：材料已知测试只覆盖单机，就写“本次测试覆盖单机部署”，不写成“仅凭本次测试，不能确认其他场景也有效”。材料没有给出的范围或缺陷，不自行补写。
- **结论说完即可结束**：不给每个结果机械配上让步、反驳、风险提醒和“有待研究”。任务需要下一步时才给出具体行动；已有的验证安排、发布门槛和实质建议直接写清对象与动作。

具体禁令、失败条件和否定结论保留准确含义，例如“运行期间禁止拔出设备，否则会损坏数据”。逐字引语保持原话，文学对话按人物与叙事任务处理。普通说明中的防御性套话不得以“保留作者声音”为由放行。

本节规则直接执行；需要更多正反例时，参阅[文本写作](references/text-writing.md#直接陈述边界清除防御性套话)。

## 取舍边界

保留事实、数字、单位、否定含义、条件、例外、证据强度、引用归属、作者声音与当前仍有效的代码契约。缺口影响当前交付时，补查获准取得的证据，或提出具体问题。普通改写不自动变成全面事实调查；保真也不要求新增免责声明、质疑或验证建议。

代码表达在本次允许的变更范围内改善：保行为重构保持约定行为；首次编写、功能修改和获准的破坏性迭代以目标需求及仍有效的契约为准，不强制保留已获准废弃的旧行为。本技能不规定编写顺序、测试策略、兼容政策或状态与校验机制。

专业术语、被动语态、长句、重复、类比、抽象和间接层都可以有用。按当前读者与任务判断，不按单个词、词源或统一长度阈值裁决。

在已授权范围内完成组织、措辞和表达改进，无需为每次局部调整申请许可。若需要改变业务规则、公共 API、法律义务、研究主张或实质范围，区分表达修复与内容变更，只对尚未授权的决定寻求确认。

## 文本正文与代码注释

**普通文本**直接呈现读者需要的内容，不混入编辑批注、起草计划、内部推演、写作策略说明、自我评价，或为措辞和组织方式辩护的话。不要在成品中宣告遵循了哪些 skill、写作规范或审查要求。

**代码**鼓励在非显然实现旁写注释：说明 bug 的触发条件、旧做法的问题、当前修复的原因、收益、代价，以及后续修改必须保留的约束。修复或性能优化使实现更难读时，尤其需要这些维护信息；不要把它们当成写作辩护删掉，也不要只留在提交历史或外部文档中。

写作笔记和操作流水留在工作材料中；仅在用户要求或有必要沟通交付限制时，另附简短说明，不输出逐步思考过程。用户只要正文时，不加这些说明；确有影响正确交付的缺口，应先澄清或明确标为未完成稿。

普通文本保留主题本身的论证、研究方法、证据出处、适用条件和必要警告。代码注释保留技术决策及必要历史，排除聊天流水账和空泛自评。判断依据是信息能否帮助读者理解、使用或维护对象，而不是是否提到了“为什么改”。

## 完成标准

交付前确认三件事：**必要语义仍在**，**代表性读者任务能从作品本身完成**，**表达直接，不靠连续设限或空泛提醒收尾**。逐段清理防御性套话是正文验收项；只换连接词、拆成多句或藏进脚注，均不算修复。其余核对按风险选择。

起草和改写先给成品：普通文本清除编辑口吻与写作过程，代码检查非显然修复是否留下足够的维护注释。审查允许没有发现，每项问题须有“读者与任务 → 准确位置 → 额外理解操作或表达阻力 → 可避免的影响 → 保真修复”的依据；不默认附送第二个完整版本。

允许附交付说明时，代码改写列出相关行为检查及未验证项；用户只要代码时不追加验证过程，也不把它写入代码注释。长篇分批说明实际完成范围与续写入口，不把大纲说成全书。信息足够且任务可继续时，完成约定产物和必要修订，不在首版后无故停下等待认可。

验证记录注明实际方法：作者自查、模型模拟或读者测试。人类理解效果的结论须有相应的读者测试数据。
