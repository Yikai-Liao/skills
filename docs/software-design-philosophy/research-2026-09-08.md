# 软件设计哲学：经典原则与 2026 年协作开发研究

日期：2026-09-08  
对象：本仓库 software-design-philosophy 的维护者与使用者  
修改基线：`35f754a`；本轮评估用例版本：0.7.0

## 研究结论

现有的信息隐藏、深模块、真实变化与失败契约主线仍适合作为本 skill 的判断尺度。本轮值得增加的是：识别实际消费者依赖，用可核验契约约束生成实现，把知识放在权威位置，按共享契约划分并行任务，并确认验证是否覆盖最终组合的真实行为。

这些结论已融入原有七份参考中的相关方法。AI 是本 skill 的使用者，因此没有新增“AI 使用时另读”的分支。模型参数、特定编排框架和研究数字保留在维护资料，运行时只保留会改变设计决定的准则。

范围包含经典设计经验、2026 年一手工程材料与五篇 arXiv 论文，重点核查 GPT-5.6 发布以后，以及 GPT-6 Astra 发布后至本日的资料。报告采用 Markdown，作为仓库维护交付；不是穷尽式文献综述，也没有进行模型之间的实测比较。

## GPT-5.6 到 Astra：哪些变化值得采纳

| 时间与来源 | 已核实的变化或经验 | 对本 skill 的决定 |
|---|---|---|
| GPT-5.6：2026-07-09 发布；当前官方指南 | 指南建议从有效基线逐组删减重复提示和工具，复测并保留承载产品要求或修正实测缺陷的内容。 | 保持入口精简；不因“模型更强”删除个人取舍或业务约束。模型升级后的消融方法留在维护评估中。 |
| 2026-07-20，Codex 自定义审查规则 | 官方案例说明，实验性接口仍可能已有真实消费者；局部 diff 无法独自揭示这些依赖。 | 把隐式兼容面与就近的权威说明纳入边界判断。 |
| GPT-6 Astra：2026-09-03 发布；当前官方指南 | 官方提醒其对 skill 指令更敏感，可能出现额外澄清、过度验证；委派方式需要按使用场景校准。 | 保留用户目标优先、按授权交付与相称验证；检查通过后仅因新变化或具体未决疑点追加验证。 |
| Astra 的异步工具与中途调整 | 工具结果可在后续返回；中途调整不自动撤回已输出内容、撤销动作或取消已启动工具。 | 交接保存需求和代码基线，迟到结果先判适用性；实际副作用单独核实。 |

发布时间来自 [OpenAI API Changelog](https://developers.openai.com/api/docs/changelog)。上述建议分别核对了 [GPT-5.6 官方指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)、Hari Srikanth 的 [Custom Code Review rules for Codex（2026-07-20）](https://developers.openai.com/blog/custom-code-review-rules-for-codex)、[GPT-6 Astra 官方指南](https://developers.openai.com/api/docs/guides/latest-model)、[Async tool calling](https://developers.openai.com/api/docs/guides/async-tool-calling) 和 [Mid-turn steering](https://developers.openai.com/api/docs/guides/steering)。动态指南按访问日记录，不把抓取日期冒充首次发表日期；模型发布日期也不代表每条实践始于该日。

Astra 发布后的直接工程案例中，Thomas Ricouard 的 [Building games with Astra（2026-09-04）](https://developers.openai.com/blog/how-to-build-games-with-astra) 特别有用：可重复的测试场景降低了重现成本，但作者仍通过真实控制路径验证旅程。由此吸收“场景初始化负责起点，真实操作验证转换”，放入已有调试面设计。案例的浏览器性能数据来自软件渲染环境，不能解释为实际 GPU 帧率，也不能据单项目推广固定测试体系。

## 经典设计经验补在哪里

Hyrum Wright 的 [Hyrum’s Law](https://www.hyrumslaw.com/) 来自基础设施迁移经验，指出消费者逐渐依赖未正式承诺的可观察行为。原 skill 已讨论未知依赖，但演化规则偏重“已承诺行为”。现在区分正式保证、已观察依赖与未知项，针对本次变化采样消费者；决定可以是保持、同步迁移或明确破坏性切换。该经验不要求永久冻结每个细节，尤其不能覆盖用户明确要求的直接切换。作者网页未标发布日期。

Andrew Trenk、Dillon Bly 在 Google 的 [Test Doubles（2020，Software Engineering at Google 第 13 章）](https://abseil.io/resources/swe-book/html/ch13.html) 说明测试替身的维护与保真成本。现在明确：替身接缝落在真实不可控或昂贵依赖处；数据库 mock 不能证明事务和约束；共享 fake 有明确维护者，必要时与真实实现接受公共契约检查。它支持按契约选择验证，不能推出所有 mock 都有害或所有测试都应访问真实生产服务。

本轮也复核了 Danilo Sato 的 [Parallel Change（2014-05-13）](https://martinfowler.com/bliki/ParallelChange.html) 与 Saltzer、Reed、Clark 的 [End-to-End Arguments in System Design（1984）](https://web.mit.edu/Saltzer/www/publications/endtoend/endtoend.pdf)。其分期迁移并最终收缩、应用端承担完成语义的要点已由现有演化和系统契约覆盖，未再增加一套流程。没有重新逐章审计原书；这里是针对当前缺口的补充核查。

## arXiv 证据：指导是否有用，取决于具体缺口和实验

论文均按精确版本读取。下面的实验研究与工程案例证据强度不同，不能汇总成一个通用提速比例。

| 论文与版本 | 实际比较和发现 | 可以支持的判断与限制 |
|---|---|---|
| ETH Zurich / LogicStar 的 [Evaluating AGENTS.md（2026；v2，6 月 23 日）](https://arxiv.org/abs/2602.11988v2) | 在 SWE-bench Lite 与 CTXbench 上比较无文件、生成文件及可用的开发者文件。生成文件增加成本，解决率变化不显著；人工文件相对无文件的提升也不显著。 | 不支持“AGENTS.md 普遍有害”。长度和指令类别消融未显示显著准确率影响；主要测试 Python 问题解决，不能直接推导长期维护效果。 |
| Williams College 的 [Probe-and-Refine Tuning of Repository Guidance（2026；v2，6 月 19 日）](https://arxiv.org/abs/2606.20512v2) | 用合成故障探针修订指导；在 Qwen3.5-35B-A3B、200 步预算、四次试验下，平均解决率为 33.0%，静态指导 28.3%，无指导 25.5%。收益主要来自生成可评估补丁的覆盖面。 | 支持从可复现失败改进指导的候选方法。指导平均更长且未做等长消融；跨模型迁移退化，不能把该收益外推到 GPT-5.6 或 Astra。 |
| Prakhar Khatri 的 [Do Context Files Help Coding Agents?（2026；v1，7 月 28 日）](https://arxiv.org/abs/2607.27250v1) | 3 个 Python 仓库、17 个任务、288 次有效运行，比较不注入、持续注入与按需取回。使用 Sonnet 4.6 与 GPT-5.5，未检测到显著正确率收益。 | 日期在 GPT-5.6 发布后，实验却未使用它。样本小，按需语料在两个仓库中也更大；不能把未检出解释成零效应，或把收益归因于单一投递方式。 |
| Google DeepMind / Google、MIT、Stanford 的 [Design Docs Are All You Need（2026；v1，9 月 4 日）](https://arxiv.org/abs/2609.05364v1) | SMART 以设计文档和依赖顺序重生成性能建模库，用展开的小算例与人工核对的参考模型对齐结果。工具明确为 Claude Code，未交代具体底层模型。 | 吸收可核对实例与独立参考的作用；“整库再生成更便宜”没有等预算维护对照，文中债务归零依赖其自定义度量，不能解释为所有技术债消失。 |
| Pi School / Translated 的 [RefactorPlatform（2026；v1，9 月 4 日）](https://arxiv.org/abs/2609.04898v1) | 仓库级重构评估比较检索粒度、提示和执行方式；其匹配任务中，带检索的单 agent 优于所测多 agent 配置。 | 主实验并未使用 Astra；主要 Python 成功信号是 AST 检查，且单次运行。结构检查不能独自证明行为等价，附录不同样本量的结果不能当作公平提升对照。 |

这组证据的共同启示是**先辨别缺少什么**：缺少必要事实时补充权威知识；已经找到事实却实现错误时，修复接口、实现或验证。有价值的信息可能需要增加文字；重复规则也可能增加检查成本。原始研究不能证明单一最优文档长度。

两篇 9 月 4 日论文属于 Astra 发布后的新资料，但不是 Astra 效果证据。按 9 月 3–8 日窗口、提交时间倒序进行的有限 arXiv 检索没有找到可纳入本报告的 GPT-6 专门论文；这不证明此类研究不存在。

## 协作、验证和效率的取舍

Anthropic 的 [Demystifying evals for AI agents（2026-01-09）](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 区分执行记录与环境结果：完成声明不能替代实际状态。这支持把验收锚定在用户目标、领域不变量与实际产物。需要独立审查时，让评估者看原始任务和必要约束；对有误判的验证器，用已知失败校准，而不是只增加评估者数量。

Nicholas Carlini 的 [Building a C compiler with a team of parallel Claudes（2026-02-05）](https://www.anthropic.com/engineering/building-c-compiler) 记录了多个 agent 同时追逐同一失败并覆盖修改，后来借助 GCC 参照拆出可独立定位的任务。这支持沿依赖与验收边界分工，并检查组合失败；它是能力边界实验，不能证明固定人数或特定角色配置最优。

Prithvi Rajasekaran 的 [Harness design for long-running application development（2026-03-24）](https://www.anthropic.com/engineering/harness-design-long-running-apps) 记录了模型升级后删除部分编排机制，也指出评估者仍可能过度宽容。案例比较的时间、费用和最终产品范围不同，因此无法孤立证明多 agent 的因果收益。本 skill 保留验收责任，具体编排按任务决定。

METR 的 [Developer Productivity Experiment Design 更新（2026-02-24）](https://metr.org/blog/2026-02-24-uplift-update/) 说明任务选择、参加意愿和并发工时记录使新效率估计难以解释。维护评估因此要在完成质量约束下记录返工、人类实际投入、端到端耗时及费用，不能用生成代码量、token 或旧模型时期的百分比替代当前收益。

保持现有七份 references，不添加泛 AI 编排参考、模型名称分支或固定审批/角色数量。不采用默认 TDD 生成架构、无依据的全库再生、永久兼容所有隐式行为，或每次设计都创建调试入口。当前个人取舍继续有效。

## 如何维护这份 skill

OpenAI 的 [Build skills](https://learn.chatgpt.com/docs/build-skills) 建议范围清晰并验证触发；Dominik Kundel、Gabriel Chua 的 [Testing Agent Skills Systematically with Evals（2026-01-22）](https://developers.openai.com/blog/eval-skills) 给出记录实际运行与产物后检查结果的方法。本轮沿用已有用例，新增对应行为边界，没有把文档格式校验当作设计质量证明。

后续模型升级或真实误用可触发定向评估：保留相同任务、反例、必要约束、工具和预算，记录模型与 skill 版本，逐组增删指令，比较行为与代价。一次成功只支持该次结果；有明确失败时可先局部修复，不把整套对照实验变成修复前置流程。该维护办法不随每次架构任务加载。

本轮执行情况与限制见 [研究增补验证记录](../../tests/software-design-philosophy/research-validation-2026-09-08.md)。独立场景验证只检查设计判断；没有真实业务系统集成测试，也没有获得本次增补的统计效果量。
