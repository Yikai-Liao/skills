# 以证据收敛性能优化

交付在目标环境与约束下有收益、质量合格、结构清楚的实现。优先消除重复工作和不必要的状态，再考虑并行、布局和硬件调优；收益与新增复杂度一起裁决。

## 固定比较对象

开始实验前，从任务和项目中确定以下边界；缺失项先用已有信息推进，不为完整表格阻塞工作。

- **目标与分母**：优化哪个阶段、相对哪个实现，以耗时、吞吐还是尾延迟衡量。局部内核与完整应用分别报告；公共瓶颈是否在本次范围内。
- **交付环境**：编译器、构建参数、最低 ISA、依赖与真实输入。诊断构建和分发构建分别保存结果；提高 ISA 或启用 fast-math 不是纯源码优化。
- **行为与预算**：必须保持的语义、既有质量参照、允许误差、关键路径的回退容限，以及预计算、内存和初始化成本。
- **覆盖维度**：选择会改变执行路径的精度、数据格式、尺寸、步长、边界和状态。用真实输入确认机会覆盖率，也保留足以反驳候选的反例。

对承诺守住的路径，明显回退未解决前不晋级。没有约定时采用这个保守默认；不要把某次实验的百分比门槛固化为通用规则。

冻结基线源码、完整命令、输入与二进制哈希。上游或环境变化后，旧数据只复用其仍然覆盖的部分；保留版本标签，不把跨轮结果伪装成配对实验。

## 从热点提出可否证的假设

先确定实际工作花在哪里，再检查编译结果。Linux 原生 CPU 优化按 **perf → toplev → LLVM-MCA** 组织主线，模型之前检查实际汇编/IR；toplev 适用的 Intel PMU 不可用时明确缺失证据。解释器、数据库或网络任务使用对应的剖析手段。

进入原生 CPU 分析时，读取[工具链与可执行命令](references/native-tools.md)：包括工具准备、perf record/report/annotate/stat、toplev 原始计数校验、实际构建到 MCA 的提取步骤，以及按需使用 llvm-exegesis、Cachegrind、uiCA、OSACA 的条件和故障处理。

| 待回答的问题 | 可用证据 |
|---|---|
| 哪段路径实际耗时 | 真实负载的 profiler；原生代码可用 perf |
| SIMD、拷贝、转换或分支是否真的发生 | 实际构建的汇编、IR、向量化报告 |
| 已知指令流为何受限 | LLVM-MCA 等模型，必要时用 uiCA、OSACA 或指令微测交叉检查 |
| 硬件执行是否支持这个解释 | 可用的 PMU 计数；toplev 等工具须检查底层事件有效性 |

工具只为区分当前假设服务，不机械跑全套。检查 multiplex、not-counted、计数范围及模型假设；无效计数不能解释为零开销，静态吞吐预测不能替代运行结果。

每个候选记录：**观察 → 机制假设 → 最小改动 → 什么结果会否定它**。先独立消融，再组合有收益的改变。源码、ISA、编译器与输入同时变化时，拆开归因；例如 native 的收益可能同时包含向量宽度、FMA 和调度变化。

## 用完整成本筛选

先做能区分假设的短实验。失败即停止晋级；有明确收益后再扩展路径、质量和完整应用验证。筛选只覆盖了 interior，就不能写成边界也已通过。

把候选新增的工作计入计时：缓存的检查与回退、打包的 gather/转置/写回、SIMD 的生产与消费、重复状态的维护。若稳态计时排除准备工作，另报冷启动、内存和摊销条件。区分静态预留、懒初始化、实际触页和动态分配。

特别选择会破坏摊销的输入：短块、短循环、频繁边界、稀疏命中、大步长或高失效率。新增快速路径即使保留原 fallback 源码，也可能改变其机器码、栈帧或布局；回退路径要实际测。

对候选使用交替或轮换顺序的 A/B，并以适量 A/A 估计同一基线波动；预热和每臂工作量保持可比。采用实际完成的工作量作分母。计时足以超过计时器分辨率与主要扰动，不固定套用某个重复次数或毫秒数。避免同时运行互相竞争的计时任务。

保留全部原始数据、顺序和失败记录；需要补测时先写明新问题或原测量失效原因。A/A≈1、A/B耗时比≈1.2 是回退信号，不能仅凭“可能是噪声”删除。CPU 与 wall、调度和宿主状态可帮助归因，但不能未经验证就指定根因。

## 以质量和局部回退裁决

先核对输出、状态更新、边界和已有质量标准，再判断收益。契约要求逐字相等时使用精确比较；允许数值差异时用独立参照及误差预算。对已测输入保持原行为，不等于原行为正确，也不能用有限核误差替代应用质量。

同时检查逐路径结果、A/A 和完整负载。平均收益不能自动抵消关键路径的明显回退；质量相同也不代表性能可接受。对机制清楚、可能小改解决的失败，给出有限修复预算；预算用尽或证据不支持时撤回候选，保留实验，而不是堆叠分支、hint 或调参挽救它。

保留的改动既要有可复现收益，也要有明确的数据归属、生命周期和回退行为。缓存、特化或硬件指令并非禁区，其维护成本需要收益支持。某个 C++ 原型失败，只能否定已测实现，不能据此否定整个 SIMD 维度或算法家族。

组合候选后验证实际交付源码。不能直接相乘独立加速比，也不能只拿临近原型的结果为最终实现背书。若撤回到已测版本，通过源码树、相关依赖、构建参数和二进制核对证明证据仍适用；不声称重新运行了未重跑的测试。

## 报告与停止

- 写清指标方向和统计量。`median(A/B)` 不应混称为 `median(A)/median(B)`；`median(A/B)` 与 `1/median(B/A)` 在样本数为偶数时也可能不同。
- 若以一个默认实现归一化为 1，两版候选共享同一匹配的参照；参照可按精度或工作负载分组，但分组与分母须一致可查。
- 将冷启动、局部调用和完整应用分开；有时限的任务同时检查尾延迟与超期。吞吐余量不能单独证明每次请求按时完成，模拟探针与真实设备也应区分。
- 当候选缺少真实覆盖、收益未超过可辨波动、存在未解决回退，或修复复杂度不值得时停止。剩余方向说明重开的证据条件，不把有界搜索的结果写成全局最优。
- 交付源码、验证范围、实际基线、收益与回退、成本和可复现证据。实验档案留在代码变更之外；是否提交、整理提交或发布沿用用户要求。

保留简短实验日志：候选、机制、版本/参数、输入覆盖、质量、逐路径 A/B 与 A/A、准备成本、结论和停止理由。需要理解这些规则如何改变取舍时，读 [一次缓存与 SIMD 优化的取舍](references/case-study.md)。
